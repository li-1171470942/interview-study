📘 学习手册 07 · JVM

配套《面试八股复习计划》第 2 节 JVM + PDF 第 56-60 页 模板：一句话结论 → 详细解释 → 面试话术/例题 Java 岗（酷开/工行/银行系）必考；Node.js 岗问到概率低但你会了是加分

1. JVM 内存区域划分（运行时数据区）

一句话结论：线程私有（程序计数器、虚拟机栈、本地方法栈）+ 线程共享（堆、方法区/元空间）；堆管对象、栈管方法调用。 详细解释：

区域 线程 内容 异常
程序计数器 私有 当前执行字节码行号 无
虚拟机栈 私有 栈帧：局部变量表/操作数栈/方法返回 StackOverflowError
本地方法栈 私有 native 方法（类比 node-ffi 调 C） StackOverflowError
堆 共享 对象实例（新生代 Eden/S0/S1 + 老年代） OutOfMemoryError
方法区/元空间 共享 类信息/常量/静态变量（JDK8+ 元空间用本地内存） OOM
直接内存 — NIO DirectBuffer 堆外 OOM

话术/例题：画图 + "栈管方法、堆管对象、元空间存类"。追问：JDK8 为什么用元空间替代永久代？→ 永久代大小固定易 OOM，元空间用本地内存天然不受 JVM 堆限制。

2. 类加载机制（加载-验证-准备-解析-初始化）

一句话结论：加载→验证→准备→解析→初始化，五个阶段；准备阶段给静态变量赋默认值，初始化阶段执行静态代码块。 详细解释： 1. 加载：读 .class 字节码 → 生成 Class 对象 2. 验证：校验字节码合法性（安全） 3. 准备：为静态变量分配内存并赋默认值（0/null），final 常量直接赋值 4. 解析：符号引用 → 直接引用（常量池解析） 5. 初始化：执行 <clinit>（静态代码块、静态变量赋值） - 触发初始化时机：new/getstatic/反射/主类；被动引用（子类引用父类静态、数组、常量）不触发 话术/例题：背五阶段 + "准备=默认值，初始化=真正赋值"。追问：什么时候类不会初始化？→ 静态常量（编译期常量池）、数组定义、通过子类引用父类静态字段。

3. 类加载器与双亲委派

一句话结论：Bootstrap → Extension/Platform → Application 三层，子先委派父，父加载不了才自己加载——防核心类被篡改、保证类唯一。 详细解释： - Bootstrap：加载 JDK 核心（rt.jar），C++ 实现，没有父 - Extension/Platform：JDK9+ 改名，加载扩展库 - Application：加载 classpath 应用类 - 双亲委派流程：加载请求 → 逐级向上委托 → 父能加载就用父的 → 全失败才自己 loadClass - 好处：安全（自定义 java.lang.String 不会覆盖）、避免重复加载（类唯一性） - 破坏：SPI 场景（JDBC DriverManager）用线程上下文加载器反向加载 话术/例题：背"委派链 + 两个好处"。追问：Tomcat 为什么打破双亲委派？→ 多个 WebApp 要隔离自己的类库，用子优先加载。

4. 对象在内存中的布局

一句话结论：对象 = 对象头（Mark Word + 类型指针）+ 实例数据 + 对齐填充；Mark Word 存锁状态/GC 年龄/hash。 详细解释： - Mark Word：64 位，存 hashCode、GC 分代年龄（4bit）、锁标志位（无锁/偏向/轻量/重量）、偏向线程 id——这就是 synchronized 锁升级的载体 - 类型指针：指向方法区的 Class（开启压缩指针时省略优化） - 实例数据：字段值（按对齐规则排列） - 对齐填充：对象大小是 8 字节整数倍 话术/例题：重点说"Mark Word 里存锁状态"——串起 synchronized。追问：对象头大小？→ 64 位 JVM 压缩指针下 12 字节（Mark Word 8 + 类型指针 4）。

5. 垃圾回收：判断 + 算法

一句话结论：可达性分析（GC Roots）判垃圾；回收算法：标记清除（碎片）、复制（新生代）、标记整理（老年代）。 详细解释： - 可达性分析：从 GC Roots（栈帧局部变量、静态变量、常量引用、native 引用）出发，不可达即垃圾；引用计数有循环引用缺陷不用 - 四种引用：强（不回收）/软（内存不足回收，缓存）/弱（下次 GC 就回收）/虚（跟踪回收） - 算法： - 标记-清除：标记垃圾后清除 → 碎片多 - 复制：把存活对象复制到另一块 → 无碎片、浪费一半空间（新生代 Eden:S0:S1=8:1:1 就是） - 标记-整理：存活对象移到一端 → 无碎片、慢（老年代） - 分代：新生代（复制，Minor GC 频繁）+ 老年代（标记整理，Major/Full GC） 话术/例题：答"可达性 + 三种算法对应两个分代"。追问：为什么新生代用复制？→ 存活率低，复制成本低；老年代存活率高，用标记整理。

6. 垃圾回收器：G1 与 CMS

一句话结论：CMS 并发标记清除（低停顿但碎片多），G1 是 JDK9+ 默认（Region 化、可预测停顿、无碎片）。 详细解释： - CMS：初始标记（快）→ 并发标记（与业务并发）→ 重新标记 → 并发清除；优点低停顿，缺点：标记清除碎片、并发阶段占 CPU、并发失败退化为 Full GC - G1：堆划分为多个 Region（新生代/老年代逻辑分区），跟踪每个 Region 垃圾占比，优先回收垃圾最多的（Garbage First）；可设置停顿目标 -XX:MaxGCPauseMillis；无碎片（复制整理）；JDK9 默认 - 对比：

CMS G1
停顿 低但不稳定 可预测（目标控制）
碎片 有 无
内存布局 连续分代 Region 化
大对象 直接进老年代 Humongous Region
话术/例题：结论"默认 G1，低延迟场景"，对比表背住。追问：G1 怎么实现可预测停顿？→ 基于回收成本模型（每个 Region 预估回收收益，选性价比最高的集合）。

7. JMM（Java 内存模型）与可见性

一句话结论：JMM 定义线程间共享变量的可见性规则：主内存 + 线程工作内存，靠 volatile/synchronized/final 保证。 详细解释： - 模型：所有变量存主内存，线程操作在自己的工作内存（副本）→ 线程间不直接共享，靠主内存同步 - 问题：可见性（改了别线程看不见）、原子性、有序性 - volatile：保证可见性（写立即刷主存，读从主存取）+ 禁止指令重排（内存屏障）——不保证原子性 - synchronized：可见性 + 原子性（进入清空工作内存，退出刷回） - happens-before 规则：程序顺序、锁（解锁 happens-before 加锁）、volatile（写 happens-before 读）、线程启动/终止、传递性 话术/例题："volatile 可见性不原子，synchronized 全都要"是核心。追问：volatile 能替代 synchronized 吗？→ 只能保证单读写的可见性，复合操作（i++）不行。

8. JVM 常见命令与调优

一句话结论：jps 找进程、jstat 看 GC、jmap 出堆转储、jstack 看线程栈、jinfo 看参数；调优核心是减少 Full GC、控制堆与停顿。 详细解释：

命令 用途
jps 列出 JVM 进程
jstat -gcutil pid GC 统计（频繁/停顿）
jmap -heap pid 堆详情
jmap -dump:format=b,file=x.hprof 堆转储（OOM 分析）
jstack pid 线程栈（死锁/阻塞定位）
jinfo 查看/修改运行参数
jvisualvm / MAT 可视化 + 内存分析
- 常用参数：-Xms/-Xmx（堆大小）、-XX:MaxMetaspaceSize、-XX:+HeapDumpOnOutOfMemoryError（OOM 自动转储）、-XX:MaxGCPauseMillis
- 调优思路：先看 GC 日志 → 堆是否合理 → 停顿是否可接受 → 对象分配是否异常
话术/例题：背命令表 + "OOM 先开 HeapDumpOnOutOfMemoryError"。追问：线上 CPU 100% 怎么查？→ top 找进程 → top -Hp 找线程 → jstack 对照线程 id（nid 转十六进制）看栈。

9. 逃逸分析与栈上分配

一句话结论：JIT 逃逸分析发现对象不逃逸出方法 → 栈上分配/标量替换，减少 GC 压力。 详细解释： - 逃逸：对象被方法外引用（返回/赋值给静态/全局）即逃逸 - 优化： - 栈上分配：不逃逸对象直接栈上分配（随方法结束销毁，免 GC） - 标量替换：对象字段拆成局部变量 - 锁消除：无竞争锁直接去掉 - 触发：-XX:+DoEscapeAnalysis（默认开） 话术/例题：一句"逃逸分析让局部对象不进堆"。追问：为什么字符串拼接优化也用它？→ StringBuilder 逃逸分析后消除。

10. 大对象与 GC 调优实践

一句话结论：大对象（如超长字符串/数组）直接进老年代（避免新生代反复复制），频繁创建大对象是 Full GC 元凶。 详细解释： - 大对象直接分配老年代（-XX:PretenureSizeThreshold 阈值） - 对象晋升：Minor GC 后存活且年龄达 -XX:MaxTenuringThreshold（默认 15）→ 老年代；大对象/动态年龄判断 - 常见 OOM：堆太小（Xmx）、内存泄漏（集合无限增长）、大对象过多、元空间满 - 实践：类比你的 rrmcompute OOM 排查——调堆大小/限制任务并发/检查缓存无界增长 话术/例题：结合你实际的 OOM 经验讲最有说服力（rrmcompute 内存 5Gi→5.5Gi 调整案例、大场所并发任务内存暴涨）。追问：Full GC 频繁怎么查？→ jstat 看 FGC 次数 + jmap 转储分析谁占内存。
