一面 Q3. Redis 使用场景；三穿雪崩如何处理

一句话结论：使用场景 = 缓存/分布式锁/幂等/计数；三穿雪崩是 Redis 面试第一送分题，必须形成"现象→原因→方案"三件套。
详细解释：
- 穿透（查不存在的 key，请求直达 DB）：空值缓存（短 TTL）+ 布隆过滤器（先过 BF）+ 参数校验
- 击穿（热点 key 过期瞬间并发打 DB）：分布式锁（setnx，只让一个线程回源）+ 逻辑过期（不设真过期，写时异步续期）+ singleflight（Go 概念，Java 用 ConcurrentHashMap keyLock）
- 雪崩（大量 key 同时过期/Redis 挂了）：过期时间打散（±10% 随机）+ Redis 高可用（哨兵/Cluster）+ 多级缓存（Caffeine + Redis）+ 熔断降级（Sentinel/Resilience4j）
话术（背）："穿透用空值缓存+布隆，击穿用分布式锁或逻辑过期，雪崩用过期时间打散+多级缓存+熔断。我在 RRM 项目里 Redis 主要做幂等键和 shop 模式开关，热点配置是热加载到本地缓存防击穿。"
追问预演：
- 「布隆过滤器误判怎么办？」→ 误判只会让少量请求穿透到 DB，不会丢数据；BF 误判率可配（0.01% 量级），够用
- 「分布式锁用 Redis 怎么实现？」→ SET key value NX EX 30 + Lua 释放锁（看原子性），见手册 21 RRM 场景模式库
- 「逻辑过期怎么续期？」→ 单独异步线程每 30s 查 TTL < 10s 的 key 续期；或读写分离+消息队列

一面 Q4. MySQL 事务 ACID；项目遇到脏写幻读怎么规避

一句话结论：ACID 4 字母展开 1 句；脏写/幻读/脏读/不可重复读是 4 个不同概念，RR 隔离级别用 MVCC + 临键锁兜底防幻读。
详细解释：
- ACID：A 原子性（undolog 回滚）/ C 一致性（约束+业务双写）/ I 隔离性（锁+MVCC）/ D 持久性（redolog+binlog）
- 4 个并发问题（必背）：脏写（最严重，A 写完未提交被 B 覆盖）/ 脏读（A 读到 B 未提交）/ 不可重复读（A 同一事务两次读 B 改的数据不同）/ 幻读（A 同一事务两次范围读 B 插入的行数不同）
- 隔离级别（SQL 标准）：RU → RC → RR → Serializable；InnoDB 默认 RR
- 防幻读 3 件套（RR 级别下）：①MVCC 快照读（普通 SELECT）；②临键锁（Next-Key Lock，SELECT FOR UPDATE）；③间隙锁（Gap Lock）
- RR 解决脏写：行锁（X 锁）互斥
话术（背）："ACID 是原子性/一致性/隔离性/持久性，靠 undolog/redolog/binlog 三大日志+锁+MVCC 实现。脏写最严重靠 X 锁防，幻读靠临键锁+MVCC 防。RR 是 InnoDB 默认级别。我在 RRM 项目里 MongoDB 为主，MySQL 只用事务管用户/订单类，配置过 RR + 显式 SELECT FOR UPDATE 兜底。"
追问预演：
- 「RR 就完全没幻读了吗？」→ 当前读（SELECT FOR UPDATE）走临键锁防；快照读（普通 SELECT）靠 ReadView 防。特殊场景（事务内先快照读再当前读）仍可能幻读
- 「binlog 三种格式？」→ STATEMENT（记录 SQL，主从数据不一致风险）/ ROW（记录行数据，安全但日志大）/ MIXED（混合）

一面 Q5. 线程池核心参数；IO 密集型、计算密集型线程数配置

一句话结论：7 大参数（corePoolSize / maxPoolSize / keepAliveTime / BlockingQueue / ThreadFactory / RejectedExecutionHandler / allowCoreThreadTimeout）；线程数公式：「CPU 密集 = N+1 / IO 密集 = 2N / 混合 = 分段计算」。
详细解释：
- 7 大参数（必背顺序）：①corePoolSize 核心线程数；②maxPoolSize 最大线程数；③keepAliveTime 空闲线程存活时间；④workQueue 任务队列（Array/Linked/Synchronous/Priority）；⑤threadFactory 线程工厂（命名+daemon）；⑥handler 拒绝策略（Abort/CallerRuns/Discard/DiscardOldest）；⑦allowCoreThreadTimeout 核心线程超时开关
- 公式（背）：CPU 密集 = N+1（N = CPU 核数；+1 是兜底线程切换）；IO 密集 = 2N 或 N/(1-阻塞系数)，阻塞系数 0.8-0.9 时 ≈ 10N
- 真实落地：压测为准，先用公式估算，再 jstack + jvisualvm 看线程状态/等待时长/上下文切换
- 避坑：任务队列别用无界 LinkedBlockingQueue（OOM）；拒绝策略别用默认 Abort（直接抛）
话术（背）："7 大参数核心是 core/max/queue/handler；线程数公式 CPU 密集用 N+1，IO 密集用 2N，混合用压测调。RRM 项目里 rrmcompute 是 IO 密集（Mongo+Redis+HTTP 远程调用多），配 2N；纯计算的下游算法服务用 N+1。"
追问预演：
- 「为什么 CPU 密集 +1？」→ 多一个兜底，万一某线程 IO 切换或 GC 暂停，CPU 不会空转
- 「任务队列怎么选？」→ 瞬时高峰用 SynchronousQueue（直接交给 max 线程）；平稳流量用 ArrayBlockingQueue（容量可控）；千万别用无界
- 「线程池异常会怎么样？」→ execute 提交异常会终止该线程（线程池补一个新）；submit 提交异常存在 Future 里，get() 才会抛

一面 Q6. 场景题：高频查询接口，设计「缓存+布隆过滤器+本地二级缓存」，保证数据一致性

一句话结论：先 BF 挡穿透 → 本地缓存（Caffeine）挡热 key → Redis 挡批量 → DB 兜底；一致性方案：Cache Aside + 延迟双删 + 订阅 binlog 兜底。
详细解释：
- 架构图（必画，5 层）：Client → Caffeine（本地 L1）→ Redis（分布式 L2）→ 布隆过滤器（BF，挡不存在 key）→ MySQL（DB 兜底）
- 读流程：①查 Caffeine，命中返回；②查 Redis，命中回填 Caffeine；③查 BF，不在直接返空；④查 DB，回写 Redis + 失效 Caffeine
- 写流程（Cache Aside）：①写 DB；②删 Redis（不是更新）；③延迟双删（异步 500ms 后再删一次，防写 DB 期间并发读回写旧值）；④订阅 binlog（Canal 监听 binlog，异步删本地缓存，最终兜底）
- 一致性等级：强一致用分布式锁（性能差）/ 最终一致用延迟双删 + binlog（推荐）
- 数字锚点：命中率 95%+ / 延迟 < 5ms / DB QPS 降 80%
话术（背）："5 层架构：Caffeine L1 挡热 key（TTL 5s）→ Redis L2 挡批量 → BF 挡不存在 key → DB 兜底。一致性用 Cache Aside + 延迟双删 + Canal 订阅 binlog 失效本地缓存。RRM 项目里配置查询接口就是这个套路，命中率 99%。"
追问预演：
- 「延迟双删的 500ms 怎么定？」→ 看业务读链路最大耗时，宁可长不可短（不够就还会读到旧值）
- 「BF 怎么保证不过期？」→ 定期重建（凌晨低峰全量重建）+ 增量更新（写 DB 时同步写 BF）
- 「Caffeine 比 Guava Cache 强在哪？」→ 性能（接近 O(1)）+ 淘汰策略（LRU/LFU/SoftReference）+ 统计（命中率/加载时间）

一面 Q8. Java + SpringAI/LangChain4j 实现 Tool Calling，Tool 注册与执行链路如何设计

一句话结论：Tool 接口标准化 + Spring Bean 注册 + LLM 选 Tool → 框架调度 → 反射执行 → 结果回填 LLM → LLM 继续 ReAct。
详细解释：
- Tool 标准化接口（LangChain4j）：
java @Tool("查询RRM调优历史") public String queryOptHistory(@P("taskId") String taskId) { return mongoTemplate.findById(taskId, OptHistory.class).toString(); }
- 注册链路：①Tool 类加 @Component 注入 Spring 容器；②LangChain4j 扫 @Tool 注解生成 JSON Schema（给 LLM 看）；③Agent 构建时 tools(toolList) 注册
- 执行链路（5 步）：
① LLM 输出 tool_call(name, args) → ② 框架解析 → ③ 反射找 Bean + Method → ④ invoke 执行 → ⑤ 结果作为 tool_result 拼回 Prompt → ⑥ 重新调 LLM
- 企业级增强（面试加分）：
- 权限隔离：Tool 加 @PreAuthorize（Spring Security）
- 限流：Tool 加 Resilience4j @RateLimiter
- 审计：AOP 切面记录 Tool 调用日志
- 幂等：Tool 入参加 requestId，Redis 去重
- 超时：Tool 加 @TimeLimiter（CompletableFuture + 超时取消）
- 防幻觉 3 件套（必背）：①参数 JSON Schema 强校验；②Tool 失败有兜底返回值；③高危 Tool 加人工确认节点
话术（背）："Tool Calling 链路 5 步：LLM 选 Tool → 框架解析 JSON → 反射调 Bean → 结果回填 → LLM 继续思考。LangChain4j 用 @Tool 注解+JSON Schema 自动注册。生产环境要加权限/限流/审计/幂等/超时 5 道防线。我 personalAgent 框架跑了 RRM 调优历史查询 Tool，跑通完整链路。"
追问预演：
- 「Tool 失败怎么办？」→ 返回错误信息给 LLM，让 LLM 决定重试或换 Tool；强失败直接终止 Agent
- 「怎么避免 LLM 瞎编参数？」→ JSON Schema 强校验（类型/必填/枚举）；参数化查询防 SQL 注入
- 「Tool 同步/异步？」→ 默认同步；长任务用异步（CompletableFuture + 回调结果回填）

一面 Q9. 算法：两数之和 LeetCode 1

一句话结论：哈希表 O(n)，一遍扫描边存边查。
代码模板（必背）：

public int[] twoSum(int[] nums, int target) {
    Map<Integer, Integer> map = new HashMap<>();
    for (int i = 0; i < nums.length; i++) {
        int complement = target - nums[i];
        if (map.containsKey(complement)) return new int[]{map.get(complement), i};
        map.put(nums[i], i);
    }
    return new int[0];
}

复杂度：时间 O(n)，空间 O(n)
追问：「为什么不用排序+双指针？」→ 排序 O(nlogn) 比哈希慢，且会改原数组下标（如果要求返回原下标就不能排）

二面 Q2. 最复杂模块，遇到什么难点

一句话结论：rrmcontrol 渐进式优化（incremental tuning） 是你从 0 到 1 的活，难点 = "边学边写 + 与现网 AI 调优结果融合"。
详细解释：
- 背景：H3C 老 AI 优化（aioptimize）有环境白名单，新 AP 调优效果不错但存量 AP 优化不增量；现网 50 万存量 AP 重调一遍成本极高
- 你的活：rrmcontrol 加增量调优，对比上次调优结果只调变化项
- 技术栈：Node.js + MongoDB aggregation pipeline（算 diff） + Redis 任务锁 + Kafka 异步触发
- 3 大难点（STAR 讲法）：
① MongoDB 索引设计（taskId+apSN+RI 联合索引，但 RI 单调递增要避免热点页）
② 对比算法（500 万行级全量 diff 太慢，分批 + 布隆）
③ MQ 积压（高峰期任务积压 30 分钟，加批量 + 跳过不变项兜底）
- 结果：单次调优任务从 15 分钟 → 90 秒，CPU 降 60%
话术（背）："rrmcontrol 渐进式优化模块是我从 0 到 1 做的——对比上次调优结果只调变化项。难点三件：MongoDB 联合索引热点页、500 万行全量 diff 太慢、MQ 积压。最终把单次任务从 15 分钟压到 90 秒，CPU 降六成。详见手册 22 RRM 讲述卡。"
追问预演：
- 「为什么不直接用老 AI 调优？」→ 老的有环境白名单 + 重调全量成本高
- 「diff 怎么做的？」→ 算 hash + 分段布隆 + aggregation $lookup 对比
- 「线上效果怎么验证？」→ 灰度 10% 跑一周看 AP 调优成功率 + 用户投诉率

二面 Q3. MQ 为什么引入；怎么保证消息不丢失、不重复消费

一句话结论：解耦 + 异步 + 削峰（三件套背熟）；不丢 = 生产者 ack + 持久化 + 消费者手动提交；不重 = 业务幂等 + 去重表。
详细解释：
- 三件套（背）：解耦（上下游不互相依赖）/ 异步（不等下游返回）/ 削峰（突发流量进队列）
- Kafka 不丢（3 道防线）：
① 生产者：ack=all（等所有 ISR 副本确认）+ 重试（retries=3）+ 幂等（enable.idempotence=true，PID+SeqNumber）
② Broker：log.flush 落盘（log.flush.interval.messages=1）+ min.insync.replicas=2（至少 2 副本才写）
③ 消费者：手动提交 offset（处理完再提交）+ 失败重试 + 死信队列
- Kafka 不重（3 道）：①业务幂等（数据库唯一约束）；②Redis 去重（setnx requestId）；③消费位点 + 业务位点双记录
- RRM 项目实战（最强弹药）：
- 引入原因：rrmcontrol 触发 → rrmcompute 计算 → yw-aioptimize 落库，任务 30 分钟必须完成，解耦后 rrmcontrol 立即返回
- 不丢：ack=all + log.flush 落盘 + 手动 offset
- 不重：MongoDB clbDetail 唯一索引 (taskId+apSN+RI) + Redis setnx 防并发
话术（背）："三件套：解耦/异步/削峰。Kafka 不丢靠生产者 ack=all + Broker 副本 + 消费者手动提交；不重靠业务幂等 + Redis 去重。RRM 项目 wlan_apcomp_lb/wlan_rrmopt/wlan_clb 三 topic 跑了一年，零丢失靠的就是这套配置。详见手册 21 RRM 场景模式库第 1 节。"
追问预演：
- 「为什么不用 RocketMQ？」→ 团队基线 + 日志型业务可重放；RocketMQ 优势在事务消息（金融场景更适合）
- 「顺序消息怎么保证？」→ 单 partition 单 consumer + 业务 key hash 到同一 partition
- 「消息积压怎么办？」→ 临时扩 consumer + 紧急扩 partition + 业务降级（丢弃非关键）

二面 Q4. 场景题：银行 OpenAPI 网关设计（限流/鉴权/防重放）

一句话结论：网关 5 件套 = 路由/限流/鉴权/防重放/熔断；Spring Cloud Gateway + Sentinel + JWT + Nonce 是经典组合。
详细解释：
- 架构（必画）：Client → [API Gateway] → 微服务集群
网关做的事：路由 / 限流 / 鉴权 / 防重放 / 熔断 / 日志 / 协议转换
- 限流（4 种算法）：①固定窗口（简单，突刺）；②滑动窗口（精确，内存大）；③令牌桶（推荐，Guava RateLimiter / Sentinel）；④漏桶（流量整形）
- 鉴权（OAuth2.0）：Access Token + Refresh Token；JWT 自包含（Header.Payload.Signature）；网关统一校验，下游服务只解析 userId
- 防重放（4 道防线）：①Nonce 随机数（一次一用，Redis 存 5min）；②Timestamp 时间戳（±5min 窗口）；③Sequence 序列号（业务流水号）；④TLS 双向认证（防中间人）
- 熔断：Sentinel / Resilience4j 三态（CLOSED/OPEN/HALF_OPEN）
- 金融专属：国密 SM2/SM4 算法 + 等保 2.0 三级 + 审计日志 6 个月留存
话术（背）："5 件套：路由/限流/鉴权/防重放/熔断。Spring Cloud Gateway + Sentinel（令牌桶限流）+ JWT 鉴权 + Nonce+Timestamp 防重放 + Sentinel 熔断。金融场景还要加国密算法和审计日志。RRM 项目对外接口走的是 K8s Ingress + Redis 限流 + JWT，原理一致只是规模小。"
追问预演：
- 「限流维度？」→ IP/用户/接口/全局，多维度组合（限流 ID 拼接）
- 「JWT 比 Session 强在哪？」→ 无状态（服务端不存）/ 跨服务（多服务共用）/ 防 CSRF（不用 Cookie）
- 「JWT 被盗怎么办？」→ 短有效期（15min）+ Refresh Token + 黑名单（Redis 存已撤销 jti）

二面 Q9. 算法：二叉树最大深度 LeetCode 104

一句话结论：DFS 后序（自底向上），左右子树深度取 max + 1。
代码模板（必背）：

public int maxDepth(TreeNode root) {
    if (root == null) return 0;
    int left = maxDepth(root.left);
    int right = maxDepth(root.right);
    return Math.max(left, right) + 1;
}

复杂度：时间 O(n)，空间 O(h)（递归栈，h = 树高）
追问：「BFS 怎么写？」→ 队列层序遍历，每层 size++；时空同 DFS，但BFS 适合求最小深度（找到第一个叶子就停）

三面 Q4. Redis 分布式锁场景；注意点：续期/误删/集群红锁

一句话结论：SET NX EX + 唯一 UUID + Lua 释放 + Watchdog 续期；集群 = Redlock（过半节点成功才算获锁）。
详细解释：
- 基础 4 件套（必背代码）：
java // 1. 加锁 Boolean ok = redisTemplate.opsForValue().setIfAbsent( "lock:" + key, uuid, 30, TimeUnit.SECONDS); // 2. 释放锁（Lua 原子：检查 UUID 再删） String lua = "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end"; redisTemplate.execute(new DefaultRedisScript<>(lua, Long.class), Collections.singletonList("lock:" + key), uuid); // 3. 续期（Watchdog，每 10s 检查一次，剩 5s 续 30s） ScheduledExecutorService.scheduleAtFixedRate(() -> renew(), 10, 10, SECONDS);
- 3 大坑（背）：
①过期误删（业务没跑完锁过期，别人抢到，你跑完删了别人的锁）→ UUID 唯一标识 + Lua 校验
②未续期（业务慢于锁 TTL，锁提前释放，并发出问题）→ Watchdog 续期（Redisson 内置）
③主从切换丢锁（master 写完锁没同步 slave，master 挂了，slave 升主没锁）→ Redlock 过半节点 或 ZK
- Redlock（5 步）：①记录 t1；②依次向 5 个独立 master SET NX EX；③记录 t2；④t2-t1 < TTL 且过半成功才算获锁；⑤否则全部释放
- RRM 实战：自动开关切换（autoSwitch）+ shop 模式防并发抢锁
话术（背）："Redis 分布式锁 4 件套：SET NX EX + UUID + Lua 释放 + Watchdog 续期。3 大坑：过期误删、TTL 跑不完、主从切换丢锁。集群下用 Redlock 过半节点。RRM 项目自动开关切换用过 Redisson 的 lock.tryLock(30, 300, SECONDS)，自带 Watchdog。"
追问预演：
- 「Redlock 争议？」→ Martin Kleppmann 写过《How to do distributed locking》质疑时钟漂移问题；Antirez 回复；实际生产用 ZK/etcd 更稳
- 「为什么不直接用 ZK？」→ 性能 Redis 更高；ZK 适合强一致场景（如 master 选举）
- 「锁粒度怎么选？」→ 业务维度（订单锁到 userId）越小并发越高；不能太粗（订单维度）

三面 Q9. 算法：反转链表 LeetCode 206

一句话结论：双指针/头插法/递归 3 种——双指针最常考。
代码模板（必背双指针）：

public ListNode reverseList(ListNode head) {
    ListNode prev = null, curr = head;
    while (curr != null) {
        ListNode next = curr.next;
        curr.next = prev;
        prev = curr;
        curr = next;
    }
    return prev;
}

复杂度：时间 O(n)，空间 O(1)
追问：「递归怎么写？」→ head.next.next = head; head.next = null; return 新头
