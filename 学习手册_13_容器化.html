容器 vs 虚拟机

概念

容器共享宿主机内核（进程隔离，秒级启动、GB 级小），虚拟机有独立内核（硬件虚拟化，分钟级启动、GB 级重）。

面试官会怎么问
  • 容器 vs 虚拟机？
查看答案与原理
容器 虚拟机
隔离 namespace+cgroup（进程级） Hypervisor + 完整 Guest OS
内核 共享宿主机 独立内核
启动 秒级 分钟级
体积 MB 级 GB 级
密度 一台几十上百个 一台十几个
隔离强度 弱（内核共享） 强（完全隔离）
- 容器本质：普通进程 + 隔离技术（namespace 隔离视图、cgroup 限制资源）
话术/例题："容器是进程隔离，虚拟机是硬件隔离"。追问：容器安全吗？→ 相对弱，内核漏洞可能影响所有容器，所以生产要加固（非 root/只读/安全基线）。

镜像分层与 UnionFS

概念

镜像由只读层叠加（UnionFS 合并视图），每层 = Dockerfile 一条指令；层可复用缓存，删除文件是加一层"白化"记录。

面试官会怎么问
  • 为什么 RUN 放前面 COPY 放后面能加速构建？→ 代码变化只影响 COPY 之后的层，前面的层走缓存
查看答案与原理
  • Dockerfile：FROM base（基础层）→ RUN apt install（加层）→ COPY（加层）→ CMD（配置层）
  • 层特性：只读、可复用（多个镜像共享基础层）、变更产生新层不修改旧层
  • 容器层：运行时可写层（最上层），删除 = 写标记遮蔽底层，镜像本身不变
  • 好处：构建缓存（未变层直接复用）、镜像传输只传差异层、省磁盘
拓展
"分层 + 缓存复用"两个词。追问：为什么 RUN 放前面 COPY 放后面能加速构建？→ 代码变化只影响 COPY 之后的层，前面的层走缓存。

Dockerfile 最佳实践 + 多阶段构建

概念

多阶段构建（builder 装依赖 → 产物拷进精简镜像）+ 非 root + 最小基础镜像，镜像又小又安全。

面试官会怎么问
  • Dockerfile 最佳实践 + 多阶段构建？
查看答案与原理

详细解释（Node.js 示例）：

# 阶段1：构建
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
# 阶段2：运行（精简）
FROM node:20-alpine
WORKDIR /app
COPY --from=builder /app/node_modules ./node_modules
COPY dist ./dist
USER node          # 非 root
EXPOSE 3000
CMD ["node", "dist/main.js"]
  • 最佳实践：多阶段（构建产物不留在运行镜像）、alpine/slim 小镜像、非 root（USER node）、.dockerignore、层合并（RUN 里 && 一条）、固定版本标签
  • 镜像大小：node:20-alpine ~50MB vs node:20 ~350MB 话术/例题："多阶段 + alpine + 非 root"是标准答案。追问：npm ci 和 npm install 区别？→ ci 按 lockfile 精确安装，构建可复现。

容器隔离原理：namespace + cgroup

概念

namespace 隔离"看得见"（进程/网络/文件系统/主机名），cgroup 限制"用得了"（CPU/内存/IO）——容器的一切隔离基于这两个内核机制。

面试官会怎么问
  • 容器内存超限会怎样？→ OOM，可能被内核 kill（这就是你 rrmcompute OOM 重启的底层机制）
查看答案与原理
  • namespace（隔离视图）：PID（进程号独立）、Network（独立网络栈）、Mount（独立文件系统）、UTS（主机名）、User（用户隔离）、IPC
  • cgroup（资源限制）：cpu（份额/配额）、memory（上限，超限 OOM kill）、blkio（磁盘）、pids（进程数）
  • 所以容器 = 进程 + 一组 namespace + 挂到 cgroup
拓展
"namespace 管视角、cgroup 管资源"一句本质。追问：容器内存超限会怎样？→ OOM，可能被内核 kill（这就是你 rrmcompute OOM 重启的底层机制）。

Docker 网络模式

概念

bridge（默认，NAT 隔离）、host（共享宿主机网络）、none（无网络）、overlay（跨主机，K8s 用）。

面试官会怎么问
  • K8s 里 Pod 之间怎么通信？→ CNI（Calico/Flannel）实现 overlay/路由网络，Pod IP 全局可路由
查看答案与原理
  • bridge：默认，容器虚拟网卡 + NAT，容器间互访，外部要端口映射 -p
  • host：直接用宿主机网络栈，无隔离（性能好但端口冲突）
  • none：无网络（安全/离线任务）
  • overlay：跨多主机容器互通（VXLAN），K8s Pod 网络就是 overlay（CNI 实现）
  • 还有 macvlan（容器直接拿物理 IP）
拓展
bridge 默认 + overlay 跨机。追问：K8s 里 Pod 之间怎么通信？→ CNI（Calico/Flannel）实现 overlay/路由网络，Pod IP 全局可路由。

数据管理：Volume vs Bind Mount

概念

volume 由 Docker 管理（推荐，可备份迁移），bind mount 挂宿主目录（开发调试方便）；容器删除数据不丢。

面试官会怎么问
  • 数据库容器怎么存数据？→ 挂 volume + 备份策略
查看答案与原理
  • volume：docker volume create / -v myvol:/data；存在 /var/lib/docker/volumes，docker 管理生命周期
  • bind mount：-v /host/path:/data，直接挂宿主目录，文件即时同步（开发改代码不用进容器）
  • tmpfs：内存挂载（临时）
  • 容器层数据：容器删除即丢 → 持久化必须用 volume/bind
拓展
一句"要持久化必须挂卷"。追问：数据库容器怎么存数据？→ 挂 volume + 备份策略。

容器安全

概念

非 root 运行、只读文件系统、镜像扫描、资源限制（防逃逸/DoS）、最小权限——生产容器安全五件套。

面试官会怎么问
  • K8s 里怎么配？→ securityContext（runAsNonRoot/readOnlyRootFilesystem）+ ResourceQuota
查看答案与原理
  • 非 root：USER node（root 容器被攻破 = 宿主机 root）
  • 只读：--read-only + tmpfs 写临时（防止写入恶意文件）
  • 镜像扫描：Trivy 扫 CVE
  • 资源限制：--memory/--cpus（防一个容器打爆整机）
  • 能力裁剪：--cap-drop ALL --cap-add 必要（去掉高危 capabilities）
  • 运行时安全：seccomp/AppArmor、K8s 安全上下文（securityContext）
拓展
"非 root + 只读 + 限资源"是面试标准答案。追问：K8s 里怎么配？→ securityContext（runAsNonRoot/readOnlyRootFilesystem）+ ResourceQuota。

K8s 整体架构

概念

Master（控制面：API Server/etcd/Scheduler/Controller-Manager）+ Node（数据面：kubelet/kube-proxy/容器运行时）；声明式 API 驱动。

面试官会怎么问
  • etcd 挂了会怎样？→ 控制面不可用（不能调度/变更），存量 Pod 继续跑（数据面不依赖 etcd）
查看答案与原理
  • API Server：所有操作的唯一入口（REST），认证鉴权
  • etcd：集群状态存储（强一致键值库）
  • Scheduler：决定 Pod 调度到哪个 Node
  • Controller-Manager：各种控制器（Deployment/ReplicaSet 等）确保实际状态 = 期望状态
  • kubelet：Node 上执行（创建/管理 Pod）
  • kube-proxy：Service 负载均衡实现（iptables/IPVS）
  • 容器运行时：containerd/docker（现在默认 containerd）
  • 核心思想：声明式——你声明期望状态（Deployment 3 副本），控制器持续调和（reconcile）
拓展
画出"Master 四组件 + Node 三组件"是基础。追问：etcd 挂了会怎样？→ 控制面不可用（不能调度/变更），存量 Pod 继续跑（数据面不依赖 etcd）。

核心对象：Pod / Deployment / Service / Ingress

概念

Pod 最小调度单位、Deployment 管副本与滚动更新、Service 提供稳定访问入口、Ingress 七层路由进集群。

面试官会怎么问
  • 为什么需要 Service 不直接访问 Pod？→ Pod IP 会变、多副本要负载均衡
查看答案与原理
  • Pod：一个或多个容器共享网络/存储卷/命名空间；Pod 是临时实体（IP 会变）
  • Deployment：声明副本数 → 管 ReplicaSet → 滚动升级/回滚（maxUnavailable/maxSurge 控制）
  • Service：给一组 Pod 提供稳定虚拟 IP + DNS 负载均衡；类型 ClusterIP（集群内）/ NodePort（节点端口）/ LoadBalancer（云 LB）
  • Ingress：七层（域名/路径 → Service），nginx-ingress 实现；TLS 证书挂载
  • 链路：用户 → Ingress（域名）→ Service（ClusterIP）→ Pod（容器）
拓展
把访问链路画出来（这就是你 RRM 服务对外暴露路径）。追问：为什么需要 Service 不直接访问 Pod？→ Pod IP 会变、多副本要负载均衡。

其他控制器：StatefulSet / DaemonSet / Job

概念

StatefulSet 有状态（稳定网络标识/顺序部署，数据库用）、DaemonSet 每个 Node 都跑一个（日志/监控）、Job 一次性任务（CronJob 定时）。

面试官会怎么问
  • 为什么数据库一般不用 Deployment？→ 数据要持久化+稳定标识，StatefulSet 的 PVC 和固定名称合适
查看答案与原理
  • StatefulSet：Pod 名称固定（mysql-0/1/2）、稳定存储（PVC 绑定）、顺序启停；适合数据库/Redis 集群
  • DaemonSet：每个 Node 一个 Pod（flannel/calico 网络插件、filebeat 日志采集、node-exporter 监控）
  • Job：跑完即完成（数据迁移）；CronJob：定时任务（备份/清理）
  • 对比：Deployment 无状态、StatefulSet 有状态、DaemonSet 全节点、Job 一次
拓展
四种控制器一句话各一个场景。追问：为什么数据库一般不用 Deployment？→ 数据要持久化+稳定标识，StatefulSet 的 PVC 和固定名称合适。

ConfigMap / Secret

概念

ConfigMap 存非敏感配置（明文），Secret 存敏感信息（base64，可配加密），注入方式：环境变量 / 文件挂载。

面试官会怎么问
  • 配置中心一键部署怎么实现？→ 动态生成 ConfigMap → kubectl apply → 触发滚动更新（结合实战讲）
查看答案与原理
  • ConfigMap：kubectl create cm app-config --from-literal=key=value；注入 env / volume 挂载（挂载可热更新）
  • Secret：类型 Opaque（通用）/ tls / docker-registry；base64 只是编码不是加密，敏感数据要外部加密方案（SOPS/云 KMS）
  • 更新注意：环境变量注入不会自动更新（重启才生效），文件挂载方式可以热更新（kubelet 定期同步）
  • 结合你 RRM：你们的配置中心本质上就是"ConfigMap 管理平台"（统一管理 → 生成 → 校验 → 下发 → 回滚）
拓展
"明文 ConfigMap、敏感 Secret、挂载可热更"。追问：配置中心一键部署怎么实现？→ 动态生成 ConfigMap → kubectl apply → 触发滚动更新（结合实战讲）。

存储：PV / PVC / StorageClass

概念

PV 是存储资源（管理员提供），PVC 是使用声明（应用申请），StorageClass 动态供给（按需自动创建 PV）。

面试官会怎么问
  • MongoDB 在 K8s 怎么存？→ StatefulSet + PVC + StorageClass 动态云盘
查看答案与原理
  • PV：独立于 Pod 的存储资源（NFS/云盘/本地卷），生命周期独立
  • PVC：应用声明需要多大/什么类型 → 绑定匹配的 PV
  • StorageClass：动态供给（云厂商自动建云盘 + 创建 PV），reclaimPolicy（保留/删除）
  • 访问模式：ReadWriteOnce（单节点读写）/ ReadWriteMany（多节点共享）
拓展
"PV 供资源、PVC 声明需求、SC 自动创建"。追问：MongoDB 在 K8s 怎么存？→ StatefulSet + PVC + StorageClass 动态云盘。

K8s 网络与服务发现

概念

每个 Pod 有独立 IP（CNI 实现 overlay/路由），Service 提供 DNS 名（my-svc.ns.svc.cluster.local）自动负载均衡。

面试官会怎么问
  • Pod 重启 IP 变了服务怎么找到？→ Service 的 selector 按标签匹配，永远指向存活 Pod
查看答案与原理
  • CNI：Calico（BGP 路由，性能好）/ Flannel（VXLAN overlay）/ Cilium（eBPF）
  • 服务发现：同命名空间直接用服务名，跨命名空间用完整 DNS
  • kube-proxy 实现：iptables（规则多时慢）/ IPVS（性能好）
  • Service 会话保持：sessionAffinity
  • 你的场景：rrmcontrol → rrmserver 内部调用用 Service DNS
拓展
"Pod 有 IP、Service 有名字"一句。追问：Pod 重启 IP 变了服务怎么找到？→ Service 的 selector 按标签匹配，永远指向存活 Pod。

滚动更新与回滚

概念

Deployment 更新镜像触发滚动更新（逐个替换 Pod，maxUnavailable/maxSurge 控节奏），kubectl rollout undo 一键回滚。

面试官会怎么问
  • 滚动更新卡住了怎么办？→ kubectl rollout status 看进度 → 查新 Pod 事件（CrashLoopBackOff/ImagePullBackOff）→ 回滚
查看答案与原理
  • 更新：新 ReplicaSet 起新 Pod → 就绪后旧 Pod 逐步减少（默认 maxUnavailable=25%）
  • 参数：maxSurge（最多多起几个新 Pod）、maxUnavailable（最多允许几个旧 Pod 不可用）
  • 就绪门控：readinessProbe 通过才继续滚动（新 Pod 起不来会卡住回滚）
  • 回滚：kubectl rollout undo deployment/rrmcontrol；kubectl rollout history 看版本
  • 你踩过的坑：滚动更新卡住 = 新 Pod 探针失败/镜像拉取失败/启动超时
拓展
"滚动逐个替换 + readiness 门控 + undo 回滚"。追问：滚动更新卡住了怎么办？→ kubectl rollout status 看进度 → 查新 Pod 事件（CrashLoopBackOff/ImagePullBackOff）→ 回滚。

HPA 与资源配额

概念

HPA 按指标（CPU/自定义）自动调副本数；requests 是调度保证、limits 是上限，超出会 OOM/节流。

面试官会怎么问
  • 为什么你项目把内存从 5Gi 调到 5.5Gi？→ 高量任务 OOM 重启，分析堆/内存峰值后调优（结合实战讲）
查看答案与原理
  • HPA：kubectl autoscale deployment x --cpu-percent=70 --min=2 --max=10；指标源 metrics-server/Prometheus 自定义指标
  • requests/limits：requests 决定调度位置（Node 满足才调度）、limits 限制使用（CPU 节流、内存 OOM kill）
  • 生产坑：只设 limits 不设 requests 会被调度器高估负载；内存超 limits 直接 OOM（这就是你 rrmcompute 调内存的实战点：requests=3Gi、总 5.5GiB）
  • ResourceQuota：命名空间资源总量限制；LimitRange：默认值
拓展
"requests 调度、limits 上限、内存超限 OOM"是重点。追问：为什么你项目把内存从 5Gi 调到 5.5Gi？→ 高量任务 OOM 重启，分析堆/内存峰值后调优（结合实战讲）。

探针：liveness / readiness / startup

概念

liveness 决定是否重启（救活）、readiness 决定是否接流量（摘除）、startup 保护慢启动（防误杀）。

面试官会怎么问
  • 只配 liveness 不配 readiness 会怎样？→ 启动中 Pod 也接流量，请求全失败
查看答案与原理
  • livenessProbe：失败 → 重启容器（卡死/死锁场景）
  • readinessProbe：失败 → 从 Service 摘除（不接新流量，依赖未就绪/启动加载）
  • startupProbe：启动阶段专用（慢启动应用，避免 liveness 在启动期反复失败重启）
  • 探测方式：httpGet / exec / tcpSocket；参数 initialDelaySeconds/failureThreshold
  • 结合你 RRM：启动时加载配置/连接 Mongo/Kafka 慢 → 用 startupProbe 避免误杀
拓展
"liveness 管死活、readiness 管流量、startup 管慢启动"。追问：只配 liveness 不配 readiness 会怎样？→ 启动中 Pod 也接流量，请求全失败。
19

调度：nodeSelector / 亲和 / 污点容忍

概念

nodeSelector 简单标签选择、nodeAffinity 复杂匹配（硬/软要求）、taint/toleration 是"污点拒入 + 容忍进入"。

面试官会怎么问
  • 为什么 master 不调度业务 Pod？→ master 默认打了 NoSchedule 污点
查看答案与原理
  • nodeSelector：nodeSelector: {disktype: ssd} 精确匹配标签
  • nodeAffinity：requiredDuringScheduling（硬）/ preferredDuringScheduling（软），支持 In/NotIn 等操作符
  • 污点 Taint + 容忍 Toleration：Node 打污点（NoSchedule/PreferNoSchedule/NoExecute）拒绝大部分 Pod，特定 Pod 加容忍才调度——用于专用节点（GPU 节点、master 隔离）
  • 场景：把计算密集型（rrmcompute）调度到高配节点
拓展
"nodeSelector 精确选、亲和灵活选、污点主动拒绝"。追问：为什么 master 不调度业务 Pod？→ master 默认打了 NoSchedule 污点。

故障排查：kubectl 命令全家桶

概念

get/describe/logs/exec/events 五件套定位一切问题，再加 rollout/port-forward/top。

面试官会怎么问
  • 故障排查：kubectl 命令全家桶？
查看答案与原理

详细解释（背熟，面试+实战都用）：

命令 用途
kubectl get pods -A 看状态（Pending/Running/CrashLoopBackOff）
kubectl describe pod xxx 看事件（调度失败原因/拉镜像失败）
kubectl logs -f pod 看日志（--previous 看崩溃前日志）
kubectl exec -it pod -- sh 进容器排查
kubectl get events --sort-by=.lastTimestamp 集群事件
kubectl rollout status/undo 滚动更新状态/回滚
kubectl port-forward svc/xxx 8080:80 本地调试
kubectl top node/pod 资源占用
- 常见状态：ImagePullBackOff（镜像拉不到）、CrashLoopBackOff（启动即崩）、Pending（资源不足/调度失败）、OOMKilled
话术/例题：你日常排障顺序（get → describe → logs → events）讲一遍就是实战。追问：CrashLoopBackOff 怎么查？→ logs --previous 看上次退出原因 + describe 看重启原因（OOM/健康检查失败）。

RBAC 与命名空间

概念

Namespace 逻辑隔离（多环境/多团队），RBAC（Role/ClusterRole + RoleBinding）控制谁能对什么资源做什么操作。

面试官会怎么问
  • Pod 怎么访问集群 API？→ ServiceAccount + RBAC 授权
查看答案与原理
  • Namespace：资源分组隔离（dev/prod）、资源配额独立、网络策略可隔离；kubectl -n 指定
  • RBAC：Role（命名空间内权限）/ ClusterRole（集群级）→ RoleBinding/ClusterRoleBinding 绑定到用户/ServiceAccount
  • ServiceAccount：Pod 身份（访问 API 用）
  • 最小权限原则：应用只给需要的权限
拓展
"Namespace 隔离空间、RBAC 隔离权限"。追问：Pod 怎么访问集群 API？→ ServiceAccount + RBAC 授权。

日志与监控

概念

日志用 EFK/ELK 或 Loki 采集（容器日志到 stdout → DaemonSet 采集），监控用 Prometheus + Grafana，告警 Alertmanager。

面试官会怎么问
  • Kafka 积压怎么监控？→ Prometheus exporter 暴露 lag 指标 + 告警阈值
查看答案与原理
  • 日志：容器输出到 stdout（12-factor）→ filebeat/fluentd（DaemonSet）→ ES/Loki → Kibana/Grafana 查询；日志文件在 /var/log/containers
  • 监控：Prometheus（指标抓取）→ 采集 node-exporter/kube-state-metrics/业务指标 → Grafana 面板；Alertmanager 告警
  • 指标：CPU/内存/网络/自定义业务指标（你的调优成功率、Kafka 积压）
  • 结合你 RRM：现网排查靠日志 grep traceId 串联 4 微服务（无链路系统时的土办法），未来可上 OTel
拓展
"日志 stdout + EFK 采集，指标 Prometheus + Grafana"。追问：Kafka 积压怎么监控？→ Prometheus exporter 暴露 lag 指标 + 告警阈值。
