📘 学习手册 08 · 并发与锁

配套《面试八股复习计划》第 2 节并发锁 + PDF 第 60-62 页 模板：一句话结论 → 详细解释 → 面试话术/例题 Java 岗重点；分布式锁部分与你 Node.js 日常强相关（Redis 锁）

1. 乐观锁 vs 悲观锁

一句话结论：悲观锁假设一定冲突（先加锁再操作，synchronized/DB 行锁）；乐观锁假设不冲突（CAS/版本号，失败重试）。 详细解释： - 悲观锁：操作前加锁，串行执行——安全但并发低 - 乐观锁：读时不加锁，提交时校验（CAS 比较值 / 版本号字段 + 1），冲突则重试——并发高但频繁冲突时浪费 - 适用：悲观锁适合写多；乐观锁适合读多写少（秒杀扣库存用乐观锁+重试） - 数据库实现：悲观=SELECT FOR UPDATE；乐观=UPDATE SET version=version+1 WHERE version=? 话术/例题：一句"悲观锁先锁后做，乐观锁做完校验"。追问：秒杀库存怎么实现？→ 乐观锁（CAS 更新库存 where 库存>0）+ 限流削峰。

2. 公平锁 vs 非公平锁

一句话结论：公平锁按请求顺序排队（FIFO），非公平锁允许插队（性能高）；synchronized 非公平，ReentrantLock 可配置。 详细解释： - 公平锁：先到先得（AQS 队列顺序），无饥饿——维护队列开销大、吞吐低 - 非公平锁：新线程先抢一次，抢不到再排队——减少线程唤醒开销（上下文切换少），吞吐高；可能饥饿 - synchronized 天生非公平；ReentrantLock 构造参数 new ReentrantLock(true/false) 话术/例题：一句"非公平=插队，性能好；公平=排队，不饿死"。追问：为什么非公平反而快？→ 减少线程挂起唤醒的上下文切换。

3. 共享锁 vs 独占锁

一句话结论：独占锁只有一个线程持有（写锁/普通锁），共享锁允许多个线程同时持有（读锁/CountDownLatch）。 详细解释： - 独占（排他）：synchronized、ReentrantLock、ReentrantReadWriteLock 的写锁 - 共享：ReentrantReadWriteLock 的读锁（多读并发）、Semaphore（N 个许可） - 读写锁：读读并发、读写互斥、写写互斥——读多写少场景吞吐翻倍 话术/例题：读写锁场景（缓存）一句话。追问：读写锁什么时候会退化/死锁？→ 写锁等待时新读线程进入会饿死写锁（StampedLock 解决）。

4. 可重入锁

一句话结论：同一线程可多次获取同一把锁（计数累加），不会自己锁死自己；synchronized 和 ReentrantLock 都可重入。 详细解释： - 场景：递归方法、A 方法加锁后调 B 方法又加同锁 - 实现：ReentrantLock 里 state 计数，每次 lock+1，unlock-1，归零才真正释放；线程持有者记录在 owner - 对比不可重入：自己锁自己会死锁 话术/例题：一句"可重入=同线程重复进，计数释放"。追问：可重入怎么实现的？→ AQS state + 持有线程判断。

5. 什么是死锁？产生条件

一句话结论：线程互相持有对方需要的资源并等待，形成环；四条件：互斥、持有等待、不可剥夺、循环等待，破一个即可。 详细解释（结合 C/C++ 手册 58 题，这里 Java 视角）： - 例子：线程 A 持锁1 等锁2，线程 B 持锁2 等锁1 - 四条件缺一不可： 1. 互斥（资源一次一人用） 2. 持有并等待（拿着一个等另一个） 3. 不可剥夺（锁不能强抢） 4. 循环等待（A→B→A 成环） - 避免：按固定顺序加锁、一次拿所有锁、tryLock 超时放弃、锁粒度小 - 排查：jstack 会输出 "Found one Java-level deadlock" 话术/例题：背四条件 + "jstack 直接检测"。追问：怎么预防？→ 锁排序 + 超时。

6. 获取锁失败后线程会怎样

一句话结论：synchronized 失败进入 BLOCKED 等 monitor；ReentrantLock 失败入 AQS 队列（可中断/超时）；CAS 失败自旋重试。 详细解释： - synchronized：竞争失败 → 线程阻塞（BLOCKED 状态），由 JVM 管理，不可中断 - ReentrantLock.lock()：入 AQS 同步队列等待（WAITING），可被 lockInterruptibly 中断 - tryLock()：失败立即返回 false，不阻塞 - CAS：失败返回 false/自旋循环重试（AtomicInteger） 话术/例题：对比三种"失败后去哪"（阻塞/排队/自旋）。追问：自旋会有什么问题？→ 空转耗 CPU，所以要自适应自旋或限制次数。

7. 除了锁，还有哪些并发方式

一句话结论：原子类（CAS）、并发容器（ConcurrentHashMap）、同步工具（Semaphore/CountDownLatch/CyclicBarrier）、不可变对象、ThreadLocal 线程隔离。 详细解释： - 原子类：AtomicInteger/LongAdder（无锁，高并发计数用 LongAdder 分片） - 并发容器：ConcurrentHashMap、CopyOnWriteArrayList（读多写少） - 同步工具：Semaphore（信号量限流）、CountDownLatch（等 N 个完成）、CyclicBarrier（N 个到齐一起跑）、Exchanger - 不可变对象：final + 无 setter，天然线程安全（String、LocalDate） - ThreadLocal：线程内副本，隔离变量 - Future/CompletableFuture：异步结果 话术/例题：能说出 5 类"无锁/工具"方案就是知识面广。追问：CountDownLatch 和 CyclicBarrier 区别？→ Latch 一次性等 N 个，Barrier 可循环复用且都到齐才放行。

8. synchronized 深入（与 volatile 对比）

一句话结论：synchronized 管可见性+原子性+有序性（重量级能力），volatile 只管可见性+有序性（轻量）；i++ 用 volatile 照样丢更新。 详细解释：

volatile synchronized
可见性 ✅ ✅
原子性 ❌ ✅
禁止重排 ✅ ✅
阻塞 无 有
- volatile 场景：状态标志位（boolean running）、双重检查锁（DCL）的实例字段
- 经典错误：volatile int count; count++ 不是原子（读-改-写三步）
- DCL 为什么需要 volatile：new 对象三步（分配-初始化-赋值）可能重排，别的线程读到未初始化的半成品 → volatile 禁止重排
话术/例题：结论"volatile 轻量可见性，synchronized 全都要"。追问：DCL 单例为什么 double check + volatile？→ 防重排导致读到半初始化对象。

9. ThreadLocal 深入（关联 Java 基础 20 题）

一句话结论：线程内共享、线程间隔离；Thread 里 ThreadLocalMap（key 弱引用），用完 remove 防泄漏。 详细解释： - 结构：每个 Thread 一个 ThreadLocalMap；key 是 ThreadLocal（弱引用），value 是值 - 泄漏链：ThreadLocal 被回收 → key 变 null，但 value 仍被 map 强引用 → 线程池长线程永远清不掉 - 防：finally 里 remove()；ThreadLocal 设 static 防误回收 - 场景：请求上下文、SimpleDateFormat（非线程安全）每个线程一份 话术/例题：能讲"弱 key 强 value"机制即深度题。追问：为什么 key 要弱引用？→ 让 ThreadLocal 对象可被回收；value 靠手动 remove。

10. 分布式锁（Redis 视角，Node/Java 通用）

一句话结论：SETNX + 过期时间 + 唯一值 + Lua 释放（详见手册 03 第 6 题）；强一致选 etcd/ZK。 详细解释： - Java 实现：SET lockKey value NX EX 30（StringRedisTemplate/Redisson） - Redisson 封装：RLock，自动续期看门狗，可重入 - 场景：分布式任务防重（定时任务多实例）、库存扣减、幂等 - 结合你 RRM：多个 rrmcontrol 实例同时触发同一 AP 调优 → Redis 分布式锁串行化 话术/例题：把 Redis 锁 + 看门狗 + 你的实际用法讲一遍。追问：锁过期业务没完成？→ 看门狗续期；锁误删？→ 唯一值 + Lua 比对删除。
