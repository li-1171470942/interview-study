线程基础：进程/线程/协程、六种状态、创建方式与中断

概念

进程是资源分配单位，线程是 CPU 调度的最小单位，同进程内的线程共享堆和方法区，各自独占栈和程序计数器（这也是并发问题的物理来源）。 Java 线程有 6 种状态：NEW / RUNNABLE / BLOCKED / WAITING / TIMED_WAITING / TERMINATED。 记忆钩子：BLOCKED 是被动等锁（synchronized 进不去），WAITING 是主动等人（wait/join/park）。

面试官会怎么问

  • 创建线程有几种方式？为什么都说要用线程池？

Java 六态与 OS 状态不是一一对应

Java 状态 触发条件 对应 OS
NEW new Thread() 后、start() 前 不存在

关键坑：Java 的 RUNNABLE 包含了内核里的阻塞 IO 等待（socket read 时 jstack 显示 RUNNABLE + socketRead0）。所以「jstack 里 RUNNABLE 很多 = CPU 打满」是错的判断，必须配合 top -Hp 看实际 CPU 占用。

为什么必须用线程池：线程创建要走内核（pthread_create），栈默认 1MB（-Xss），创建/销毁开销大且数量不可控。1000 个线程 = 1GB 栈内存，很容易撞上 OutOfMemoryError: unable to create new native thread（详见第 10 题）。

start() vs run()

Thread t = new Thread(() -> System.out.println(Thread.currentThread().getName()));
t.run();    // 输出 main      —— 就是个普通方法调用，当前线程执行
t.start();  // 输出 Thread-0  —— JVM 调用 start0() 本地方法，真正创建内核线程

start() 内部有 synchronized + threadStatus != 0 校验，一个 Thread 对象只能 start 一次，第二次抛 IllegalThreadStateException。

中断机制（唯一的优雅停止方式）

public class InterruptDemo {
    public static void main(String[] args) throws Exception {
        Thread t = new Thread(() -> {
            // 循环里主动检查中断标志
            while (!Thread.currentThread().isInterrupted()) {
                try {
                    Thread.sleep(1000);              // 阻塞点：被 interrupt 会抛 InterruptedException
                } catch (InterruptedException e) {
                    // ！！sleep/wait/join 抛异常时会【清除】中断标志
                    Thread.currentThread().interrupt();  // 必须补回来，交给上层处理
                    System.out.println("收到中断信号，清理资源后退出");
                    break;
                }
            }
            System.out.println("工作线程已停止");
        });
        t.start();
        Thread.sleep(300);
        t.interrupt();      // 只是「设置标志位 + 唤醒阻塞」，不是强杀
    }
}

操作步骤： 1. 业务循环里用 while (!Thread.currentThread().isInterrupted()) 做条件 2. 捕获 InterruptedException 后立刻 Thread.currentThread().interrupt() 恢复标志 3. 在 catch 里做资源清理（关连接、回滚事务、提交 offset），然后退出 4. 用 executor.shutdownNow() 或 future.cancel(true) 触发中断

为什么 Thread.stop() 被废弃：它会在任意字节码位置强杀线程并释放它持有的所有锁 → 被保护的数据处于不一致的中间态（比如转账扣了 A 没加 B）。同理 suspend()/resume() 被废弃是因为 suspend 期间不释放锁，极易死锁。

虚拟线程（JDK21 JEP 444，JDK19 预览）

// 平台线程：1 个 Java 线程 = 1 个内核线程，栈 1MB
// 虚拟线程：M:N 调度，栈存在堆里，可创建百万级，阻塞时自动 unmount 释放载体线程
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 10_000).forEach(i ->
        executor.submit(() -> { Thread.sleep(Duration.ofSeconds(1)); return i; }));
}

适用：IO 密集型、高并发短任务（HTTP 调用、DB 查询）。不适用：CPU 密集型（无收益）、有 synchronized 长临界区的代码（会把载体线程 pin 住，JDK21 里 synchronized 会 pin，JDK24 已修复）。

daemon 守护线程：setDaemon(true) 必须在 start() 前调用。JVM 退出条件是所有非守护线程结束。GC 线程、JIT 编译线程都是守护线程。

线程优先级：setPriority(1~10) 只是给 OS 的建议，跨平台不可靠，不要靠它做同步。

daemon 与线程池：线程池默认创建的是非守护线程（除非自定义 ThreadFactory 里 setDaemon(true)），所以 JVM 不会因为 main 结束而退出——这是「本地跑单测不退出」的常见原因。

继续追问（面试官下一步会问什么）

Q：sleep() 和 wait() 有什么区别？ ① sleep 是 Thread 的静态方法，不释放锁；wait 是 Object 的方法，释放锁并进入该对象的 WaitSet。② sleep 可在任何地方调用；wait 必须在 synchronized 块内（否则抛 IllegalMonitorStateException）。③ sleep 时间到自动醒；wait 需要 notify/notifyAll 或超时。

Q：那 park() 和 wait() 呢？ LockSupport.park() 是 Unsafe 层面的原语，不需要持有锁，底层也是基于 monitor 的 ParkEvent，许可机制（unpark 可以先给许可，park 就立即返回）。AQS 里用的就是 park/unpark，而不是 wait/notify——因为 wait/notify 必须先抢到 synchronized 锁，而 AQS 是要绕开 monitor 自己实现同步。

Q：线程怎么「真正」停下来？ 没有安全的强制停止。标准答案是：用一个 volatile 标志位 + interrupt() 唤醒阻塞点，业务代码在循环里检查标志并做清理。这也是为什么线程池的 shutdownNow() 本质是「给每个 worker 发中断」而不是「杀线程」。

Q：Java 线程数开多少合适？ CPU 密集型：N + 1（N = Runtime.getRuntime().availableProcessors()）。IO 密集型：N × (1 + 等待时间/计算时间)，经验值 2N。但真正的答案是压测出来的——要看下游（DB/Redis/第三方）能承受多少并发，线程数超过下游承载能力只会把压力转移成排队超时。

悲观锁 vs 乐观锁

概念

悲观锁：假设一定冲突，先加锁再操作（synchronized、ReentrantLock、DB 的 SELECT ... FOR UPDATE）。 乐观锁：假设不冲突，改完提交时校验（CAS、版本号字段）。冲突率低时乐观锁赢，冲突率高时乐观锁的重试会浪费大量 CPU。 记忆钩子：悲观锁是「排队进厕所」，乐观锁是「进去前踹一脚门，锁着就回去重来」。

  • 数据库层面怎么实现乐观锁？版本号和 CAS 更新有什么区别？
  • 秒杀扣库存怎么实现？会有超卖吗？
  • 乐观锁重试次数太多怎么办？

核心对比

维度 悲观锁 乐观锁
加锁时机 操作前加锁 不加锁，提交时校验
实现手段 synchronized / ReentrantLock / SELECT FOR UPDATE / TableLock CAS（AtomicXxx）/ 版本号 / WHERE stock > 0
并发度 低（串行化临界区） 高（无锁读、乐观写）
冲突代价 等待（线程挂起 + 上下文切换） 重试（自旋消耗 CPU、失败业务回滚）
死锁风险 有（多锁顺序不当） 无（无锁）
适用 写多、冲突率高、临界区长 读多写少、冲突率低
典型场景 转账、库存扣减（强一致） 秒杀、点赞、状态更新、防并发重复提交

数据库乐观锁两种写法

-- 方式一：版本号（最通用）
-- 表结构：id, stock, version
UPDATE product SET stock = stock - 1, version = version + 1
 WHERE id = 1001 AND version = 7;
-- 影响行数 = 0 → 被人抢先改了，业务层重试（读最新 version 再 UPDATE）

-- 方式二：条件更新（CAS 思想，无额外字段）
UPDATE product SET stock = stock - 1
 WHERE id = 1001 AND stock > 0;
-- 影响行数 = 0 → 库存不足或已被抢完
-- 靠 InnoDB 行锁 + 当前读保证原子，不会超卖

关键结论：方式二才是防超卖的正确姿势。方式一在高并发下重试风暴严重（1000 个线程抢同一行，999 个白跑）。「WHERE 条件里带业务约束 + 一次 UPDATE」永远优于「先查再比对再更新」，因为后者在 READ COMMITTED 下会读到过期数据。

Java 层乐观锁实现

public class OptimisticStock {
    // 方式一：CAS 自旋（AtomicInteger）
    private final AtomicInteger stock = new AtomicInteger(100);

    public boolean deductCas() {
        while (true) {
            int cur = stock.get();
            if (cur <= 0) return false;                       // 无库存
            if (stock.compareAndSet(cur, cur - 1)) return true; // CAS 成功
            // 失败：说明有人改了，循环重读再试
        }
    }

    // 方式二：版本号 + 重试上限（避免无界自旋）
    public boolean deductVersion(int maxRetry) {
        for (int i = 0; i < maxRetry; i++) {                  // 重试上限是关键
            int cur = stock.get();
            if (cur <= 0) return false;
            try { Thread.sleep(ThreadLocalRandom.current().nextInt(1, 5)); } // 退避
            catch (InterruptedException e) { Thread.currentThread().interrupt(); return false; }
            if (stock.compareAndSet(cur, cur - 1)) return true;
        }
        return false;                                          // 重试耗尽 → 快速失败
    }
}

乐观锁重试风暴怎么破（按优先级）

  1. 加退避：失败后随机睡 1~5ms，避免所有线程同步自旋打满 CPU
  2. 设重试上限：超过就返回「系统繁忙」让前端稍后再试（快速失败 > 无界自旋）
  3. 减小冲突面：把「一个总库存」拆成「N 个子库存」分桶扣减（Redis 分片、DB 分库分表思路）
  4. 前置削峰：Redis 预扣减 + 消息队列异步落库（秒杀标准架构）
  5. 换成悲观锁：冲突率超过 30~50% 时，乐观锁的重试成本会超过加锁成本，该换 FOR UPDATE 或分布式锁

什么时候乐观锁反而更慢

冲突率 乐观锁 悲观锁
< 10% ✅ 无锁快 加锁开销大
10% ~ 50% 重试可接受 相当
> 50% ❌ 大量 CPU 空转在重试 ✅ 排队反而稳定

这也解释了为什么 ConcurrentHashMap 在单桶高竞争时会把 CAS 升级成 synchronized（见第 12 题）——JDK 自己就是这么做的。

拓展

JVM 里的乐观锁：偏向锁就是极致的乐观

偏向锁（第 4 题）假设「这把锁以后只有第一个线程会拿」，连 CAS 都不做，只在 Mark Word 里记个线程 ID。一旦第二个线程来了才撤销。这就是「乐观到极致」的锁策略，也解释了它为什么在竞争场景下反而成为负担。

ABA 问题在乐观锁里的真实体现

版本号方案本身就是 ABA 的防御手段——version 单调递增，即使库存值回到原样，version 也变了，WHERE version = 7 不会误判。用值做 CAS 会有 ABA，用版本号不会（见第 6 题）。

Node.js 视角的对比

你们 RRM 用 Node.js，单线程事件循环下 stock-- 不存在竞态（没有真并行），所以不需要乐观锁。但一旦引入 worker_threads 或多进程（cluster）共享 MongoDB 状态，就必须回到「版本号 or 条件更新」上 —— MongoDB 的 findOneAndUpdate({_id, version}, {$inc:{version:1}}) 就是标准乐观锁写法，跟 clbDetail 这类集合的更新是同一套思路。

继续追问（面试官下一步会问什么）

Q：乐观锁真的「无锁」吗？ 不是。DB 层 UPDATE ... WHERE 依然要靠 InnoDB 行锁（当前读加 X 锁）保证原子。乐观锁省的是应用层长时间持锁，不是底层完全不加锁。准确说法是「应用层无悲观锁，靠一次原子写解决问题」。

Q：分布式环境（多 pod）下乐观锁还够用吗？ 够，而且通常是首选。因为版本号/条件更新是数据库层面的原子操作，天然跨进程有效，不需要引入 Redis/ZK。只有在「跨多个资源/跨服务」时才需要分布式锁（见第 14 题）。

Q：秒杀完整方案说一遍？ ① 前端限流（按钮置灰 + 验证码）；② 网关/Nginx 限流；③ Redis 预扣库存（DECR 原子，返回 < 0 则回补并拒绝）；④ 扣减成功发 MQ；⑤ 消费端异步创建订单 + DB 落库（WHERE stock > 0 兜底）；⑥ 未支付超时回补库存。每一层都不是为了「正确」而是为了「保护下一层」。

挂到我的项目上

你们 MongoDB 的 clbDetail / optHistory / autoSwitch / autoOptConfig 集合，更新是单文档操作——MongoDB 单文档更新天生原子，不需要额外加乐观锁。但如果你做过「先查 RI/AP 状态、再决定要不要写回」这种多步骤逻辑，就存在并发窗口（多 pod 同时判断同一 AP 需要调优）。

面试时这样讲比较稳：「我们的防重入主要靠 {taskId, apSN, RI} 复合索引保证数据不重复写入 + 定时任务在多 pod 场景下做幂等判断；如果要做严格的跨 pod 串行化，最合适的是 Redis 分布式锁按 apSN 加锁。」 不要编造「我们用了版本号乐观锁」，因为你没直接改过那部分。

synchronized 的用法与 Monitor 底层实现

概念

synchronized 锁的是对象，不是代码块。三种用法对应三个锁对象：实例方法锁 this、静态方法锁 Class 对象、代码块锁括号里的对象。 底层是 monitor（管程 / ObjectMonitor），字节码上是 monitorenter / monitorexit，同步方法上是 ACC_SYNCHRONIZED 标志。

三种用法与锁对象

用法 写法 锁对象 字节码
实例方法 public synchronized void m() this ACC_SYNCHRONIZED
静态方法 public static synchronized void m() 当前类的 Class 对象 ACC_SYNCHRONIZED
同步代码块 synchronized (obj) { ... } obj（任意对象） monitorenter / monitorexit

验证「锁的是对象」的经典现场

public class LockObject {
    private static final Object LOCK = new Object();

    public void wrong1() { synchronized (this)     { sleep(2000); System.out.println("A"); } }
    public void wrong2() { synchronized (new Object()) { sleep(2000); System.out.println("B"); } } // 每次 new，锁不住！
    public void right()  { synchronized (LOCK)     { sleep(2000); System.out.println("C"); } }

    // 下面两个互不互斥？
    public synchronized void m1() { sleep(2000); }          // 锁 this
    public static synchronized void m2() { sleep(2000); }   // 锁 Class 对象
    // 答案：不互斥！锁对象不同 → 可以同时执行
}

javap -c -p LockObject.class 能看到 monitorenter 和两条 monitorexit（正常出口一条 + 异常出口一条），这就是编译器自动帮你加的 try-finally。

ObjectMonitor 的关键字段（HotSpot 源码 src/hotspot/share/runtime/objectMonitor.hpp）

class ObjectMonitor {
    void*     volatile _owner;      // 持有锁的线程（关键）
    ObjectWaiter* volatile _cxq;    // 竞争队列：新来的线程先塞这里
    ObjectWaiter* volatile _EntryList; // 入口列表：有资格抢锁的队列
    ObjectWaiter* volatile _WaitSet;   // 调用了 wait() 的线程在这里等 notify
    volatile int _count;            // 重入计数（记录 owner 重入了多少次）
    volatile int _recursions;       // 重入次数（不同 JDK 版本字段职责有调整）
};

加锁流程

  1. 线程执行到 monitorenter → 尝试用 CAS 把 _owner 设为自己
  2. 成功 → 成为 owner，_recursions++，进入临界区
  3. 失败 → 判断 _owner 是不是自己（可重入）→ 是则 _recursions++ 直接进
  4. 都不是 → 自旋尝试（自适应自旋）→ 仍失败 → 包装成 ObjectWaiter 入 _cxq，park() 挂起
  5. 释放时 monitorexit → _recursions--，减到 0 才真正释放 _owner，然后从 _EntryList/_cxq 唤醒一个线程

为什么重入要靠 _recursions：递归调用同一个同步方法会反复 monitorenter，如果没有计数，第一次 monitorexit 就把锁放了，另一个线程就能闯进还在执行的临界区。

wait() / notify() 与 WaitSet 的关系（这是常被追问的点）

synchronized (lock) {          // ① 必须先成为 lock 的 owner
    while (conditionNotMet) {  // ② 必须用 while，防虚假唤醒
        lock.wait();           // ③ 释放锁 + 线程进入 lock 的 _WaitSet
    }
    // ④ 被 notify 唤醒后，从 _WaitSet 移到 _EntryList，重新竞争锁
}

while 而不是 if 的原因：wait() 可能虚假唤醒（没有 notify 也返回，JVM 规范允许），且唤醒后条件是别人改的——必须重新检查。wait() 会释放锁，sleep() 不会，这是最常考的区别。

拓展

monitorenter 的锁记录：为什么等待时间无法统计

synchronized 的阻塞在 ObjectMonitor 里没有超时机制，_EntryList 里排队的线程是不可中断、不可超时的。所以「统计 synchronized 锁的等待耗时」只能靠 -XX:+UnlockDiagnosticVMOptions 或 JFR 事件，不能靠业务代码埋点。这也是 ReentrantLock 的存在意义之一（有 tryLock(timeout)、lockInterruptibly()、可统计）。

继续追问（面试官下一步会问什么）

Q：synchronized 能保证什么？ 原子性（临界区互斥）+ 可见性（解锁前把工作内存刷回主内存，加锁时清空工作内存重新读）+ 有序性（临界区内不会和临界区外重排）。三样都管，「重量级能力」——这是它和 volatile 最本质的差别。

Q：为什么说 synchronized 是非公平锁？ 因为释放锁时并不保证按等待顺序唤醒，且新来的线程可以在被唤醒线程拿到锁之前抢先 CAS 成功。JVM 不做 FIFO 保证，这就是「插队」。好处是减少线程挂起/唤醒的上下文切换开销，吞吐更高；代价是理论上可能饥饿。

Q：锁消除（Lock Elision）是什么？ JIT 的逃逸分析发现某个锁对象只在单线程内使用（比如方法内 new StringBuffer() 然后 append），就会把它的 monitorenter/monitorexit 直接删掉。这是 JIT 对 synchronized 的优化，不是语言特性。手册 07 第 8 题提过，这里从并发角度看。

Q：锁粗化（Lock Coarsening）呢？ 循环里反复 synchronized 同一个对象，JIT 会把锁范围扩大到循环外，减少反复加锁释放的开销。所以「在循环里写 synchronized」不一定会真的加锁 N 次。

synchronized 锁升级：无锁 → 偏向锁 → 轻量级锁 → 重量级锁 ★

概念

锁状态记录在对象头 Mark Word 里，随竞争程度单向升级（不可逆）：无锁 → 偏向锁 → 轻量级锁 → 重量级锁。 一句话记：偏向锁抢「独占署名」（一次 CAS）、轻量级锁抢「栈上指针」（CAS 自旋）、重量级锁抢「管程」（内核阻塞）。

查看答案与原理

Mark Word 64 位布局（这是整道题的物理基础）

锁状态 62/54 位内容 分代年龄(4bit) biased_lock(1bit) lock(2bit)
无锁 unused(25) + identity_hashcode(31) + unused(1) 有 0 01
偏向锁 JavaThread*(54) + epoch(2) + unused(1) 有 1 01
轻量级锁 指向栈中 Lock Record 的指针(62) — — 00
重量级锁 指向 ObjectMonitor 的指针(62) — — 10
GC 标记 空（不存 hashCode） — — 11

关键细节：hashCode() 一旦被调用，对象就无法进入偏向锁（31 位 hashCode 和 54 位线程 ID 抢同一块空间）。所以 -XX:+PrintFlagsFinal | grep BiasedLocking 里能看到「有对象调用过 hashCode 就撤销偏向」。这也是为什么「偏向锁在 hashCode 场景下会退化」— 面试官很爱追问这个。

升级四步详解

① 无锁 → 偏向锁（第一次进入同步块）

// 触发条件：只有一个线程访问同步块，且对象 hashCode 未被调用
// 依赖参数：-XX:+UseBiasedLocking（JDK15 起默认 false，JDK18 移除）
// -XX:BiasedLockingStartupDelay=4000  默认延迟 4 秒才启用（避开启动期竞争）

流程： 1. 检查 Mark Word 的 biased_lock=1 且线程 ID 为空 2. CAS 把当前线程 ID 写进 Mark Word（这一次 CAS 是唯一的开销） 3. 之后同一线程再进出同步块，只比较线程 ID，不做任何原子操作 —— 零成本

② 偏向锁 → 轻量级锁（第二个线程来了）

撤销流程（必须到 safepoint）： 1. 线程 B 尝试获取锁，发现 Mark Word 里的线程 ID 是 A 2. 检查 A 是否还活着。A 已死 → 直接把对象改为无锁（一次「重偏向」） 3. A 还活着 → 等到 A 到达安全点（safepoint），暂停 A 4. 遍历 A 的栈帧，找到对应的 Lock Record，把 Mark Word 恢复成无锁状态（或升级为轻量级锁） 5. 唤醒 A，A 继续（此时 A 拿到的是轻量级锁）

为什么必须 safepoint：撤销偏向锁要修改 A 栈帧里的 Lock Record（因为当初 A 加锁时可能已经把 Mark Word 存了一份进自己的栈）。要安全地遍历和修改另一个正在运行的线程的栈，就必须让它停在安全点上——这是 JVM 里唯一能保证「栈内容稳定可读」的时刻。safepoint 意味着 STW，这就是偏向锁成本高的根源。

批量重偏向 / 批量撤销（BiasedLockingBulkRebiasThreshold）

操作 默认阈值 触发条件 效果
批量重偏向 20 同一个类的对象撤销偏向达 20 次 认为「这个类不适合偏向」，重新偏向给新线程（后续对象直接偏向新的）
批量撤销 40 同一类撤销达 40 次 把该类的偏向功能整体关掉，之后新建对象直接是无锁状态

这两个阈值（-XX:BiasedLockingBulkRebiasThreshold=20、-XX:BiasedLockingBulkRevokeThreshold=40）就是「偏向锁在竞争场景下反而拖后腿」的量化证据。

③ 轻量级锁（CAS 自旋抢锁）

流程： 1. 在当前线程栈帧里开辟一块 Lock Record（存一份 Mark Word 的副本，叫 Displaced Mark Word） 2. CAS 把对象头的 Mark Word 替换成指向该 Lock Record 的指针 3. CAS 成功 → 拿到锁（lock=00） 4. CAS 失败 → 自适应自旋重试 5. 自旋期间成功 → 拿锁；自旋结束仍失败 / 出现第三个线程竞争 → 膨胀为重量级锁

为什么「第三个线程来了」就直接膨胀：轻量级锁的设计前提是「竞争很少、稍等就能拿到」。一旦有第三方在等，自旋就变成了纯粹的浪费，不如直接进内核阻塞队列。

自适应自旋（Adaptive Spinning）：同一个锁上一次自旋成功过，这次就允许自旋更多次；上一次没成功，这次就少转甚至不转。参数 -XX:+UseSpinning（JDK7 起默认开启并强制），自旋次数由 JVM 动态决定，不再是固定的 -XX:PreBlockSpin=10。

④ 重量级锁（ObjectMonitor）

膨胀后对象头指向 ObjectMonitor，等待线程 park() 挂起，涉及用户态 → 内核态的切换（约几微秒到几十微秒），但换来的是不消耗 CPU 的排队。

为什么不能降级

设计上就是单向的。理由：① 降级需要判断「以后不会再有竞争」，而 JVM 无法预测未来，判断成本比收益高；② 降级本身要修改 Mark Word 和线程栈，需要 safepoint，又是一次 STW。代价太高，收益不确定，所以干脆不做。

JDK15 为什么默认关闭偏向锁（JEP 374）

  1. 收益变小：现代应用大量使用 java.util.concurrent（ConcurrentHashMap、ReentrantLock），synchronized 的竞争场景变多，偏向锁的「单线程零成本」优势被摊薄
  2. 撤销成本高：撤销要 safepoint（STW），在高并发下撤销开销反而超过收益
  3. 维护成本高：偏向锁的代码深度侵入 HotSpot 的同步子系统（biasedLocking.cpp），每次 GC/类布局改动都要同步改它，是 bug 高发区
  4. 实际影响很小 —— 关闭后基准测试吞吐几乎无变化，且可用 -XX:+UseBiasedLocking 手动打开（JDK18 前）

JDK18（JEP 删实现）：既然默认关闭，代码就彻底删了，减少 HotSpot 复杂度。面试可以直接说「JDK15 默认关闭，JDK18 移除实现」这个版本时间线，非常显功底。

Q：锁升级是不可逆的，那「批量重偏向」算降级吗？ 不算。批量重偏向后对象仍然是偏向锁状态，只是把偏向量从旧线程改到新线程。真正的「重量级 → 轻量级」降级 JVM 从来不做。

Q：Object.hashCode() 和偏向锁冲突，具体怎么表现？ 对象调用 hashCode() 时要在 Mark Word 里写 31 位 hashCode，而偏向锁要用这 53 位存线程 ID → 一旦写了 hashCode，该对象的偏向锁就被撤销（-XX:+PrintBiasedLockingStatistics 能看到）。JVM 会优先保证 hashCode 正确，因为 hashCode 是 HashMap 的基础。

Q：轻量级锁的 Lock Record 里存什么？ 存一份 Displaced Mark Word（加锁前的对象头副本）。解锁时用 CAS 把这份副本还原回对象头。注意：Lock Record 是分配在线程栈帧上的，所以「轻量级锁」才叫「轻量」——它不需要向操作系统申请任何资源。

Q：自旋在什么时候是有害的？ ① 临界区很长（自旋半天还是等不到）；② 单核 CPU（自旋的时候持有锁的线程根本没机会跑，纯浪费）；③ 竞争线程数远超核数。JVM 的自适应自旋就是为了自动规避这些情况。

Q：为什么 synchronized 在 JDK6 之后性能「突然」变好了？ JDK6 一次性加入了四样东西：偏向锁、轻量级锁、自适应自旋、锁消除/锁粗化。前三个是锁升级链路，后两个是 JIT 优化。这四样组合起来才让「无竞争时 synchronized 几乎零成本」成立。

JMM 与 happens-before、volatile 的并发语义 ★

概念

JMM 定义了多线程读写共享变量时的可见性与有序性规则：所有变量存主内存，线程把变量拷到自己的工作内存（CPU 缓存 + 寄存器）操作，靠 volatile / synchronized / final / 锁来同步。 volatile 保证可见性 + 禁止重排，但不保证原子性 —— 它的正确用法只有两种：状态标志位 和 DCL 的实例字段。

JMM 的抽象模型

┌──────── 线程 A ────────┐         ┌──────── 线程 B ────────┐
│  工作内存（副本 a=0）   │         │  工作内存（副本 a=0）   │
└───────────┬────────────┘         └───────────┬────────────┘
            │ save/load                         │ save/load
            ▼                                   ▼
┌──────────────── 主内存：共享变量 a ─────────────────┐
└────────────────────────────────────────────────────┘

JMM 定义了 8 种原子操作：lock / unlock / read / load / use / assign / store / write。read+load 是主内存→工作内存，store+write 是工作内存→主内存，必须是原子配对出现。理解这个的意义：volatile 的 store+write 会强制立即执行，不让副本滞留。

并发三大特性与解决手段

特性 问题描述 解决手段
可见性 线程 A 改了，线程 B 读到的还是旧副本 volatile、synchronized、final、原子类（AtomicXxx 内部靠 volatile 读）
原子性 i++ 是「读-改-写」三步，可被插入 synchronized、Lock、AtomicXxx（CAS）
有序性 编译器/CPU/内存系统会重排指令 volatile（内存屏障）、synchronized、happens-before

volatile 的三重语义

public class VolatileSemantics {
    // ① 可见性：写立即刷主内存，读直接读主内存，作废其他线程副本
    private volatile boolean running = true;

    // ② 禁止重排：前后插入内存屏障
    private volatile int flag = 0;
    private int data = 0;

    public void writer() {
        data = 42;          // 普通写
        flag = 1;           // volatile 写 —— 前的 StoreStore 屏障保证 data=42 先刷出
    }
    public void reader() {
        if (flag == 1) {    // volatile 读 —— 后的 LoadLoad 屏障保证后面的读不提前
            int r = data;   // 一定读到 42，不会读到 0
        }
    }

    // ③ 不保证原子性 —— 反面教材
    private volatile int count = 0;
    public void wrong() { count++; }   // 多线程必然丢更新！

四种内存屏障与插入位置

屏障类型 作用 插入位置
LoadLoad 禁止后面的读越过前面的读 volatile 读之后
StoreStore 禁止前面的写被推迟到 volatile 写之后 volatile 写之前
LoadStore 禁止后面的写越过前面的读 volatile 读之后
StoreLoad 全能屏障（最贵），禁止上面的写和下面的读写重排 volatile 写之后

为什么 StoreLoad 最贵：其他三种在 x86 上基本是空操作（x86 是 TSO 强内存模型），只有 StoreLoad 需要真正执行 mfence 或 lock 前缀指令——它会清空 store buffer，让后续读必须等。所以「一个 volatile 写的代价 ≈ 一次内存屏障指令」，比普通写贵 10~100 倍。

happens-before 八条规则（JLS §17.4.5）

规则 内容 实战意义
程序顺序 同线程内，前面 hb 后面 只保证单线程语义，多线程下不保证
监视器锁 对锁的 unlock hb 后续对该锁的 lock 这就是 synchronized 保证可见性的原理
volatile 对 volatile 变量的写 hb 后续对它的读 写线程的所有操作对读线程可见（含普通字段）
线程启动 Thread.start() hb 新线程的任何操作 所以 new Thread 前赋的值，子线程一定看得到
线程终止 线程所有操作 hb 其他线程检测到它结束 join() 返回后能读到该线程的所有结果
中断 interrupt() hb 被中断线程检测到中断 中断前设的值可见
终结器 对象构造完成 hb finalize() 开始 基本用不到
传递性 A hb B，B hb C ⇒ A hb C 组合出复杂可见性链

反过来用：happens-before 不是「时间上先发生」，而是「前一个操作的结果对后一个操作可见」。两条操作没有 hb 关系 → JVM 可以任意重排 → 才会出现诡异 bug。

DCL 单例为什么必须 volatile（并发视角重讲）

public class Singleton {
    private static volatile Singleton INSTANCE;   // volatile 不可省！

    public static Singleton getInstance() {
        if (INSTANCE == null) {                   // 第一次检查：无锁，性能路径
            synchronized (Singleton.class) {      // 加锁
                if (INSTANCE == null) {           // 第二次检查：防重复创建
                    INSTANCE = new Singleton();   // ① 分配 ② 初始化 ③ 赋值
                }
            }
        }
        return INSTANCE;
    }
}

new Singleton() 的 ② 和 ③ 可能重排：如果先执行 ③（INSTANCE 已非 null，但对象字段全是默认值），线程 B 在第一次 if 检查时看到 INSTANCE != null → 直接 return 一个半成品对象（field 是 null/0）。后续 B 对它的使用会 NPE 或读到脏值。

更优写法（面试可以主动补充）：静态内部类 Holder 单例（靠 <clinit> 的线程安全，见手册 07 第 2 题），或直接用枚举（《Effective Java》推荐，防反射和序列化破坏）。

MESI 协议与伪共享

为什么 Node.js 不需要 volatile（你的知识优势）

Node 主线程单线程执行 JS，不存在共享内存的可见性问题（worker_threads / cluster 之间靠消息传递而非共享变量）。而 JVM 里线程是真并行、共享堆。所以「为什么 JS 不需要 volatile」这个问题的答案，恰好证明了 JMM 存在的意义 —— 面试里主动做这个对比，比只会背八条规则强得多。

final 字段的特殊语义：final 字段在构造器写完后，JMM 禁止「写 final 字段」与「把对象引用发布出去」重排 → 其他线程不需要同步就能看到 final 字段的正确值。这是 String 天然线程安全的底层原因之一。

Q：volatile 写之后，其他线程「立刻」能看到吗？ 不能保证「立刻」。volatile 保证的是「下一个读一定看到新值」（happens-before），不保证延迟时间。实际上写要经过 store buffer → MESI 广播 → 其他核 invalidate，有几十到几百纳秒延迟。但语义上，只要读发生在写之后且存在 hb 关系，就一定能读到新值。

Q：synchronized 是怎么保证可见性的？ 加锁时清空工作内存从主内存重读，解锁前把工作内存刷回主内存。对应 happens-before 的监视器锁规则。所以「进临界区一定看到上一个持有者的全部修改」。

Q：volatile 变量在哪个内存区？ 概念上「主内存」，物理上就是堆里的对象字段（或静态区）。JMM 是抽象模型，不是真实的内存分区。

Q：AtomicInteger 和 volatile int 什么关系？ AtomicInteger 内部就是 private volatile int value; + Unsafe.compareAndSwapInt。volatile 保证可见性，CAS 保证原子性，两者组合才等价于一个「原子的 int」。这也是第 6 题的起点。

Q：为什么说「volatile 不能替代锁」？ 因为它不保证原子性。只要操作是「读-改-写」或是「检查后行动」，就必须用锁或 CAS。判断口诀：这个操作能不能用一条 CPU 指令完成？ 能（如 x = 1）→ volatile 够；不能（如 x++、if (x) y++）→ 需要锁。

CAS 原理与三大问题、原子类与 LongAdder ★

概念

CAS（Compare And Swap）= 比较并交换，一条 CPU 原子指令：if (当前值 == 期望值) { 设为新值; return true } else return false。 Java 入口是 sun.misc.Unsafe.compareAndSwapInt/Object/Long（JDK9+ 推荐 VarHandle）。 三大问题：ABA、自旋开销、只能保证单个变量。 记住这三个，这题就稳了。

CAS 的三个操作数与底层指令

// 语义：如果 obj 的 offset 处的值等于 expect，就更新为 update，返回 true
public final native boolean compareAndSwapInt(Object o, long offset, int expect, int update);

对应 x86 的 lock cmpxchg 指令。原子性由两条机制保证：总线锁定（老 CPU，锁内存总线，开销极大）或缓存锁定（现代 CPU，通过 MESI 独占缓存行，只锁缓存行）。lock 前缀的另一个作用是充当内存屏障（等价 StoreLoad），所以 CAS 本身也保证了可见性。

CAS 三大问题与解决方案

问题 现象 解决方案
① ABA 值从 A→B→A，CAS 认为「没变过」，误判成功 AtomicStampedReference（加版本号）/ AtomicMarkableReference（加 boolean 标记）
② 自旋开销大 高竞争下大量线程空转 CAS，CPU 打满 自适应自旋 / 限制重试次数 / 改用 LongAdder（分段）/ 退化成锁

问题① 代码实证：ABA 有多危险

import java.util.concurrent.atomic.AtomicStampedReference;
import java.util.concurrent.atomic.AtomicInteger;

public class AbaDemo {
    public static void main(String[] args) throws InterruptedException {
        // ---------- 危险版：AtomicInteger 无法识别 ABA ----------
        AtomicInteger money = new AtomicInteger(100);
        Thread t1 = new Thread(() -> {
            int expect = money.get();                       // 读到 100
            sleep(500);                                     // 这期间别人动手脚
            System.out.println("t1 CAS 结果: " + money.compareAndSet(expect, 50)); // 居然 true！
        });
        Thread t2 = new Thread(() -> {
            money.compareAndSet(100, 200);                  // A → B
            money.compareAndSet(200, 100);                  // B → A
            System.out.println("t2 已完成 ABA 操作");
        });
        t1.start(); Thread.sleep(100); t2.start(); t1.join(); t2.join();

        // ---------- 安全版：带版本戳 ----------
        AtomicStampedReference<Integer> ref = new AtomicStampedReference<>(100, 0);
        Thread t3 = new Thread(() -> {
            int[] stamp = new int[1];
            Integer expect = ref.get(stamp);                // 读到值 + 版本
            int expectStamp = stamp[0];
            sleep(500);
            System.out.println("t3 CAS 结果: " + ref.compareAndSet(expect, 50, expectStamp, expectStamp + 1));
            // false —— 因为版本号已经变了，这才是正确行为
        });
        Thread t4 = new Thread(() -> {
            int[] s = new int[1];
            ref.compareAndSet(100, 200, 0, 1);              // 值和版本都变了
            ref.compareAndSet(200, 100, 1, 2);
        });
        t3.start(); Thread.sleep(100); t4.start(); t3.join(); t4.join();
    }
    static void sleep(long ms) { try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } }
}

ABA 什么时候是真实危害：本质是「值没变」不等于「状态没变」。典型场景是无锁栈/无锁队列的节点复用——节点被弹出又压回，指针一样但中间链已经断了。而如果是纯粹的数值累加（计数器、库存），ABA 通常无害，所以别一上来就无脑上 AtomicStampedReference（它性能比 AtomicInteger 差）。

问题② 高竞争下的无锁退化：LongAdder 的分段思想

写方式 所有线程 CAS 同一个 value 线程哈希到不同 Cell，各自 CAS

import java.util.concurrent.atomic.AtomicLong;

public class AdderBench {
    static final int THREADS = 32, TIMES = 1_000_000;

    public static void main(String[] args) throws Exception {
        AtomicLong atomic = new AtomicLong();
        LongAdder adder = new LongAdder();

        System.out.println("LongAdder  耗时(ms): " + bench(adder::increment));

继续追问（面试官下一步会问什么）

Q：CAS 失败后为什么用 while(true) 自旋而不是阻塞？ 因为无锁编程的核心价值是避免线程阻塞/唤醒的内核态开销。如果 CAS 失败就阻塞，那和加锁没区别，还多了一次 CAS 开销。但自旋的代价是消耗 CPU，所以只在「临界区极短」时才划算——这正是 synchronized 轻量级锁和 AtomicInteger 共同的假设。

Q：AtomicInteger.getAndIncrement() 和 incrementAndGet() 区别？ 前者返回旧值，后者返回新值。内部都是 getAndAddInt 循环 CAS，只是返回值不同。面试可以补一句：getAndIncrement 更符合「先取票后加」的业务直觉。

Q：为什么 AtomicLong 的 sum 在 LongAdder 里不精确，但还能用于监控？ 监控统计（QPS、调用次数）只要求「最终收敛且量级正确」，不要求任意时刻精确。而库存、发号器要求精确，就必须用 AtomicLong 或加锁。「精度换吞吐」是这个取舍的本质。

Q：CAS 能替代锁吗？ 能替代简单原子操作，不能替代复合逻辑。if (map.containsKey(k)) map.put(k, v) 这种 check-then-act 用 CAS 表达极其痛苦（要自己搞状态机），直接 ConcurrentHashMap.computeIfAbsent（内部锁桶头）更清晰。工程上优先用 JDK 封装好的并发容器，而不是自己搓 CAS。

Q：AtomicStampedReference 有什么缺点？ ① 每次要额外维护版本号，多一次字段读写；② compareAndSet 要传 4 个参数，容易写错；③ 泛型 + int[] 取戳的 API 设计很别扭（返回戳要通过数组出参）。所以只在确认存在 ABA 风险时才用。

        static final Node SHARED = new Node();     // 共享模式标记
        static final Node EXCLUSIVE = null;        // 独占模式标记
        static final int CANCELLED =  1;           // 线程已取消（超时/中断）
        static final int SIGNAL    = -1;           // 后继节点需要被唤醒
        static final int CONDITION = -2;           // 在 Condition 队列里等
        static final int PROPAGATE = -3;           // 共享模式下需要向后传播唤醒
        volatile int waitStatus;
        volatile Node prev, next;
        volatile Thread thread;
        Node nextWaiter;                           // Condition 队列的后继 / 模式标记
    }
}

独占模式加锁流程（acquire）

public final void acquire(int arg) {
    if (!tryAcquire(arg) &&                                    // ① 先试一次（子类实现）
        acquireQueued(addWaiter(Node.EXCLUSIVE), arg))         // ② 失败才入队
        selfInterrupt();                                       // ③ 补中断标志
}

逐步骤展开：

  1. tryAcquire(arg) —— 子类实现，成功就直接返回（非公平锁的第一次插队就在这里）
  2. addWaiter(Node.EXCLUSIVE) —— 用 CAS 把当前线程包成 Node 挂到 tail 后面，形成双向链表
  3. acquireQueued(node, arg) —— 一个 for(;;) 循环：
final boolean acquireQueued(final Node node, int arg) {
    boolean failed = true;
    try {
        boolean interrupted = false;
        for (;;) {
            final Node p = node.predecessor();
            if (p == head && tryAcquire(arg)) {     // 只有前驱是 head 才有资格再试一次
                setHead(node);                      // 抢到了，自己变 head（出队）
                p.next = null;
                failed = false;
                return interrupted;
            }
            // 前驱是 SIGNAL 状态 → 安心 park；否则先把前驱置为 SIGNAL
            if (shouldParkAfterFailedAcquire(p, node) && parkAndCheckInterrupt())
                interrupted = true;
        }
    } finally {
        if (failed) cancelAcquire(node);            // 异常时把自己标记 CANCELLED 并出队
    }
}

private final boolean parkAndCheckInterrupt() {
    LockSupport.park(this);                          // 挂起，等待被 unpark
    return Thread.interrupted();                     // 返回并【清除】中断标志
}
  1. shouldParkAfterFailedAcquire —— 如果前驱的 waitStatus 是 SIGNAL(-1) 就返回 true（可以睡了）；如果是 CANCELLED(1) 就跳过所有已取消的前驱；否则用 CAS 把前驱置为 SIGNAL 再重试

释放与唤醒流程（release）

public final boolean release(int arg) {
    if (tryRelease(arg)) {                       // 子类实现：state 减到 0 才算真释放
        Node h = head;
        if (h != null && h.waitStatus != 0)
            unparkSuccessor(h);                  // 唤醒 head 的后继
        return true;
    }
    return false;
}

关键设计：唤醒时从头往后找第一个非 CANCELLED 的节点（unparkSuccessor），但是被唤醒的线程并不一定拿到锁——它醒来后还要再 tryAcquire 一次，失败就继续排。这是「非公平的本质」：唤醒有延迟，新来的线程可能抢先。

ReentrantLock 公平/非公平的唯一差别

// 非公平锁（默认）
final boolean nonfairTryAcquire(int acquires) {
    final Thread current = Thread.currentThread();
    int c = getState();
    if (c == 0) {
        if (compareAndSetState(0, acquires)) {        // ★ 直接抢，不看队列！
            setExclusiveOwnerThread(current);
            return true;
        }
    } else if (current == getExclusiveOwnerThread()) {  // 可重入
        int nextc = c + acquires;
        if (nextc < 0) throw new Error("Maximum lock count exceeded");
        setState(nextc);                                // 这里不用 CAS（已持锁，无竞争）
        return true;
    }
    return false;
}

// 公平锁
protected final boolean tryAcquire(int acquires) {
    final Thread current = Thread.currentThread();
    int c = getState();
    if (c == 0) {
        if (!hasQueuedPredecessors() &&                // ★ 多这一行！有人排队就不抢
            compareAndSetState(0, acquires)) {
            setExclusiveOwnerThread(current);
            return true;
        }
    } else if (current == getExclusiveOwnerThread()) { /* 可重入同上 */ }
    return false;
}

公平与非公平的差异就是 hasQueuedPredecessors() 这一行。这一行让公平锁的吞吐显著低于非公平锁——因为「唤醒一个等待线程」的上下文切换成本，远大于让新来的线程直接执行完（新线程有更热的 CPU 缓存，这是关键原因）。

维度 公平锁 非公平锁

吞吐 低（每次都要唤醒+切换） 高（减少上下文切换，缓存更热）
饥饿 不会 理论上可能（实测很难）
场景 实时性要求高、任务耗时差异大 绝大多数场景（默认）

ConditionObject 与 await/signal

public class BoundedBuffer<T> {
    private final Object[] items = new Object[100];
    private int count, putIdx, takeIdx;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition();   // 两个条件队列
    private final Condition notEmpty = lock.newCondition();

    public void put(T x) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length) notFull.await();     // 队列满 → 在 notFull 上等
            items[putIdx] = x;
            if (++putIdx == items.length) putIdx = 0;
            count++;
            notEmpty.signal();                                 // 只唤醒「非空」队列里的一个
        } finally { lock.unlock(); }
    }

    public T take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) notEmpty.await();
            T x = (T) items[takeIdx];
            if (++takeIdx == items.length) takeIdx = 0;
            count--;
            notFull.signal();
            return x;
        } finally { lock.unlock(); }
    }
}

await() 内部干了什么

  1. 检查当前线程是否持有锁（否则 IllegalMonitorStateException）
  2. fullyRelease(node) —— 把 state 一次性减到 0（即使重入了 N 次），完全释放锁
  3. addConditionWaiter() —— 把节点加进 ConditionObject 自己的单向队列（firstWaiter/lastWaiter），waitStatus = CONDITION
  4. LockSupport.park(this) 挂起
  5. 被 signal 唤醒后，通过 transferAfterCancelledWait / transferForSignal 把节点从 Condition 队列转移到 AQS 同步队列（等待重新抢锁）
  6. 重新 acquireQueued 抢锁成功后，acquire 时把 state 恢复成原来的重入次数（savedState）

signal() 干了什么：把 Condition 队列的第一个节点转移到 AQS 同步队列尾部（doSignal → transferForSignal → enq），并不会立即唤醒执行——它还得排 AQS 的队。

「一个队列」是 Object.wait 最大的缺陷：一个对象上既有「满了要等」又有「空了要等」，notify 唤醒的可能是错的那一类，被唤醒的线程发现条件不满足又继续 wait，导致信号丢失甚至死等。Condition 用多个队列彻底解决这个问题——这也是 ArrayBlockingQueue 用两个 Condition 的原因。

拓展

LockSupport.park 为什么优于 wait/notify

  1. 不需要持有锁（wait 必须先成为 monitor owner）。AQS 用 park 是为了在不依赖 monitor 的情况下实现阻塞，避免「用 synchronized 实现锁」的递归困境。
  2. 许可机制（permit）：unpark 可以先调用，会给线程发一张许可，之后的 park 立即返回不阻塞。这解决了 wait/notify 的「先 notify 后 wait 就丢信号」问题。
  3. 支持 parkNanos/parkUntil 和中断，且 park 不抛 InterruptedException（返回后自己查标志），更适合框架层实现。

AQS 的 CLH 变体与原始 CLH 的差别

原始 CLH（Craig, Landin, Hagersten） AQS 的变体
队列方向 单向，自旋在本地变量上 双向，便于取消节点
阻塞方式 纯自旋 自旋 + park 混合
节点状态 隐式（前驱是否释放） 显式 waitStatus（SIGNAL/CANCELLED/CONDITION/PROPAGATE）
取消支持 差 好（cancelAcquire）

AQS 的 state 为什么要 volatile：所有线程都要读它 → 可见性必须保证；所有修改都用 compareAndSetState（本质是 CAS）→ 原子性由 CAS 保证。AQS 本身就是一个教科书级的「volatile + CAS」组合案例（和第 6 题呼应）。

lock() 和 lockInterruptibly() 的关键差别

// lock()：即使收到中断也【不理会】，一直等到拿到锁，之后补上中断标志

// lockInterruptibly()：park 期间被中断就抛 InterruptedException 并放弃抢锁

    sync.acquireInterruptibly(1);
}

继续追问（面试官下一步会问什么）

Q：new ReentrantLock(true) 和 false 性能差多少？ 在竞争激烈时公平锁吞吐可能低一个数量级（因为每次释放都要唤醒队列里的线程 + 上下文切换）。默认用非公平，除非有明确的无饥饿需求。 实测差异随临界区长度和线程数变化，建议自己压测。

Q：tryLock() 为什么更「乐观」？ 因为它只是一次 tryAcquire + 最多几次 acquireQueued 尝试，失败就直接返回 false，不入队、不 park。所以它非常适合做「抢不到就算了」的场景——比如死锁预防里的超时重试（第 9 题）。

Q：Condition.await 后为什么要重新抢锁？ 因为 await 会完全释放锁（fullyRelease 把 state 归零）。被 signal 唤醒后，它和普通的新线程一样要重新竞争锁，所以 await 返回后必须重新检查条件（用 while）。

Q：AQS 队列是 FIFO 的吗？ 结构上是 FIFO（尾插入），但非公平模式下不保证 FIFO 出队——因为释放锁时新来的线程可以直接 CAS 抢走，排队的线程还在 park。只有公平锁模式才真正保证 FIFO。

Q：为什么 AQS 要设一个「虚拟 head」？ 因为 head 不存线程（它只是「已经拿到锁的那个节点」的标志）。判断「我有资格抢锁」的条件就是 node.prev == head。这比「自己是队列第一个」更好实现，也避免了 head 本身的取消逻辑。head 永远是「当前持锁者或刚释放锁者」。

Q：LockSupport.park 被唤醒后一定拿得到锁吗？ 不一定。unpark 只是让线程从 park 返回，返回后还要走 acquireQueued 的循环重新 tryAcquire。这也是为什么 AQS 的唤醒要「从头往后找第一个非取消节点」——因为中间可能有一堆已被唤醒但还没抢到锁的线程。

公平 vs 非公平面试标准答法

可重入的实现（ReentrantLock 源码要点）

// AQS 里的关键字段
private transient Thread exclusiveOwnerThread;   // 来自 AbstractOwnableSynchronizer
private volatile int state;                       // 重入计数

// 加锁：state 从 0 → 1 → 2 → 3 ...
// 释放：state 从 3 → 2 → 1 → 0，只有减到 0 才 release 成功并唤醒后继
protected final boolean tryRelease(int releases) {
    int c = getState() - releases;
    if (Thread.currentThread() != getExclusiveOwnerThread())
        throw new IllegalMonitorStateException();  // 没持锁就解锁 → 抛异常
    boolean free = false;
    if (c == 0) { free = true; setExclusiveOwnerThread(null); }
    setState(c);
    return free;                                   // 只有 true 才真正唤醒后继
}

不可重入会怎样：递归调用同一个同步方法时自己把自己锁死。这是「不可重入锁」的经典陷阱：

public void a() { lock.lock(); b(); lock.unlock(); }   // 不可重入锁在这里死锁
public void b() { lock.lock(); /* ... */ lock.unlock(); }

每线程的读锁次数怎么记：ReentrantReadWriteLock 用 ThreadLocal<HoldCounter>（readHolds）记录每个线程自己的读锁重入次数，因为 state 只有一个全局读计数，无法区分谁读了几次。这是它比 Semaphore 复杂的地方。

锁降级 vs 锁升级

// ✅ 锁降级：写锁 → 读锁（支持，是官方推荐用法）
rwLock.writeLock().lock();
try {
    updateCache();
    rwLock.readLock().lock();      // 在持有写锁的情况下获取读锁
} finally {
    rwLock.writeLock().unlock();   // 释放写锁，仍持有读锁 → 防止其他写线程插进来
}
try { readCache(); } finally { rwLock.readLock().unlock(); }

// ❌ 锁升级：读锁 → 写锁（不支持，会死锁！）
rwLock.readLock().lock();
rwLock.writeLock().lock();         // 等自己释放读锁 → 永远等不到 → 死锁

写锁饥饿问题：非公平模式下，如果读线程源源不断，写线程可能一直等不到（读锁只要没有写锁就能拿，写锁必须等所有读锁释放）。ReentrantReadWriteLock 的公平模式通过 hasQueuedPredecessors() 缓解，StampedLock 则用「乐观读 + 版本校验」绕开这个问题。

StampedLock：乐观读的威力

import java.util.concurrent.locks.StampedLock;

public class Point {
    private double x, y;
    private final StampedLock sl = new StampedLock();

    // ① 乐观读：不加锁，只拿一个版本戳
    public double distanceFromOrigin() {
        long stamp = sl.tryOptimisticRead();          // 无锁，性能极高
        double curX = x, curY = y;                    // 可能读到不一致的中间态
        if (!sl.validate(stamp)) {                    // 校验：期间有写操作发生吗？
            stamp = sl.readLock();                    // 有 → 退化成悲观读锁
            try { curX = x; curY = y; }
            finally { sl.unlockRead(stamp); }
        }
        return Math.sqrt(curX * curX + curY * curY);
    }

    // ② 写
    public void move(double dx, double dy) {
        long stamp = sl.writeLock();
        try { x += dx; y += dy; }
        finally { sl.unlockWrite(stamp); }
    }
}

StampedLock 的三个限制（必须说，否则会被追问打回）

  1. 不可重入 —— 同一线程重复获取会死锁（这是它比 ReentrantReadWriteLock 快的原因之一：省掉了 owner 判断）
  2. 不支持中断 —— 没有 lockInterruptibly，readLock 可能长时间拿不到
  3. 不支持 Condition —— 拿不到版本戳就无法实现

「锁降级」为什么是必要设计

考虑缓存更新场景：写线程更新完缓存后要立即读一次做校验。如果先释放写锁再拿读锁，中间窗口可能被另一个写线程改掉。先拿读锁再放写锁保证「从写到读」的连贯性。而「升级」之所以不支持，是因为两个读线程同时想升级会互相等待对方的读锁释放 → 死锁。JVM 没法判定该让谁升，所以干脆禁止。

Semaphore vs CountDownLatch vs CyclicBarrier（第 13 题详讲，这里先给一句话）

  • Semaphore：N 个许可，可以反复 acquire/release，用于限流
  • CountDownLatch：倒计数到 0 放行，一次性，用于「等 N 件事都完成」
  • CyclicBarrier：N 个线程互相等，可循环复用，用于「分片任务同时起跑」

synchronized 与 ReentrantLock 的可中断性对比实测

// synchronized 不可中断：线程 interrupt 后仍然阻塞
synchronized (lock) { sleep(10000); }   // 另一个线程 interrupt 它 → 无效，还是等满 10s

// ReentrantLock 可中断：
lock.lockInterruptibly();               // 另一个线程 interrupt → 抛 InterruptedException 立即返回

这个差异在「超时降级」场景很关键：分布式任务抢锁失败要快速失败，而不是无限等。

README 级的常识：ReentrantReadWriteLock 在读少写多的场景下比 ReentrantLock 还慢（多了 state 高低位拆分的开销，却拿不到读并发收益）。只有读远多于写（比如 10:1 以上）才值得用。

Q：读写锁会不会饿死写线程？ 会（非公平模式下）。只要读锁不断到来，写锁永远要等所有读锁释放。ReentrantReadWriteLock 的公平模式可以缓解，StampedLock 的乐观读不占锁所以能显著缓解。 更极端的方案是 ConcurrentHashMap 那种「CAS 无锁读 + 锁桶头写」。

Q：StampedLock 的乐观读怎么知道「期间被改过」？ tryOptimisticRead() 返回一个版本号（stamp），每次写锁释放会把这个版本号 +1。validate(stamp) 先检查 (stamp & SBITS) == (state & SBITS)，再读一次 state 确认没变。只要期间发生过任何写，版本号必然变化。

Q：ReentrantLock 能重入多少次？ 理论上限是 Integer.MAX_VALUE，超过抛 Error("Maximum lock count exceeded")。同理 ReentrantReadWriteLock 的写锁重入上限是 65535（低 16 位）。

Q：ReentrantLock 忘记 unlock() 会怎样？ 锁永久不释放，其他线程永久阻塞 → 线程池线程全部卡死 → 服务不可用。这也是推荐优先用 synchronized 的核心理由（编译器自动插入 monitorexit）。用 ReentrantLock 必须严格遵守：

lock.lock();
try { /* 业务 */ } finally { lock.unlock(); }   // resolve 必须写在 finally

Q：Semaphore 的 release() 可以在没 acquire() 的情况下调用吗？ 可以，而且会把许可数再加上去（超过初始值）——这叫「许可膨胀」，是个真实的 bug 来源。所以 release() 一定要在 finally 里且只有 acquire() 成功后才调。

死锁最小复现（可以直接跑）

public class DeadLockDemo {
    private static final Object LOCK_A = new Object();
    private static final Object LOCK_B = new Object();

    public static void main(String[] args) {
        new Thread(() -> {
            synchronized (LOCK_A) {
                System.out.println(Thread.currentThread().getName() + " 拿到 A，等待 B");
                sleep(1000);
                synchronized (LOCK_B) { System.out.println("t1 拿到 B"); }
            }
        }, "t1").start();

        new Thread(() -> {
            synchronized (LOCK_B) {                       // 顺序反了！
                System.out.println(Thread.currentThread().getName() + " 拿到 B，等待 A");
                sleep(1000);
                synchronized (LOCK_A) { System.out.println("t2 拿到 A"); }
            }
        }, "t2").start();
    }
    static void sleep(long ms) { try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } }
}
// 输出：两人各拿一把，然后永久卡住

四个必要条件（缺一不可）

条件 含义 本案例的体现 破坏方式
互斥 资源同一时刻只能一个线程用 锁本身互斥 难破坏（改用无锁/CAS/不可变对象/ThreadLocal）
持有并等待 拿着一个，还去申请另一个 t1 持 A 等 B 一次性申请所有资源（先拿全部再干活）
不可剥夺 锁不能被强行抢走 synchronized 无法被抢 tryLock(timeout) 超时主动放弃并释放已持有的锁

一句话：破环最快，破「持有并等待」最通用，破「互斥」成本最高。

预防死锁的四种手段（按推荐度排序）

① 锁排序（最常用，零成本）

// 反例：顺序不一致 → 死锁
synchronized (a) { synchronized (b) { ... } }   // 线程1
synchronized (b) { synchronized (a) { ... } }   // 线程2 ❌

// 正例：按对象的 hashCode（或其他全局唯一序）排序后再加锁
public void transfer(Account from, Account to, long amount) {
    Account first  = from.id() < to.id() ? from : to;   // 固定顺序
    Account second = from.id() < to.id() ? to : from;
    synchronized (first) {
        synchronized (second) {
            from.debit(amount); to.credit(amount);
        }
    }
}

注意坑：用 System.identityHashCode() 排序时可能冲突（两个对象 hashCode 相同），此时需要加第三把「平局锁」。这个细节面试讲出来很加分。

② tryLock 超时（最通用）

// 破坏「不可剥夺」条件：拿不到就主动放弃并回滚
public boolean transferWithTimeout(Account from, Account to, long amount) throws InterruptedException {
    long deadline = System.nanoTime() + TimeUnit.SECONDS.toNanos(3);
    while (System.nanoTime() < deadline) {
        if (from.lock.tryLock(100, TimeUnit.MILLISECONDS)) {      // 带超时的 tryLock
            try {
                if (to.lock.tryLock(100, TimeUnit.MILLISECONDS)) {
                    try { from.debit(amount); to.credit(amount); return true; }
                    finally { to.lock.unlock(); }
                }
            } finally { from.lock.unlock(); }                     // 拿不到第二把就必须放掉第一把！
            Thread.sleep(ThreadLocalRandom.current().nextInt(1, 10)); // 随机退避，避免活锁
        }
    }
    return false;                                                 // 超时 → 快速失败
}

③ 一次性申请所有资源（破坏「持有并等待」）：把需要的锁/资源在开始时全部拿到，拿不全就全放掉重来。适合资源种类少的场景。

④ 减少锁范围/避免嵌套锁（破坏「互斥」的持有范围）：能用无锁（CAS、AtomicReference、不可变对象 record）就不加锁；能用 ThreadLocal 就不共享。最彻底的方案是「不需要锁」。

死锁 vs 活锁 vs 饥饿

死锁 活锁 饥饿
线程状态 BLOCKED/WAITING（不动了） RUNNABLE（一直在动但没进展） RUNNABLE（一直抢不到资源）
现象 卡死，CPU 不涨 CPU 高但业务无进展（如两个线程互相退让） 某线程永远得不到锁
原因 循环等待 冲突后都退避，步调一致 优先级低 / 非公平锁长期插队
解决 锁排序、tryLock 超时 随机退避（打乱步调） 公平锁、优先级调整
jstack 能检测出来 检测不出来（需要看 profiling） 检测不出来

活锁的典型例子：两个线程都检测到冲突 → 都释放锁 → 都随机等 1ms → 又同时重试 → 又冲突。解决就是把固定退避改成随机退避，上面代码里的 ThreadLocalRandom 就是这个作用。

重要结论：DB 死锁通常不会「卡死」，只会有一个事务被回滚报错（Deadlock found when trying to get lock; try restarting transaction）。所以业务层要对这类异常做重试。而 JVM 死锁是永久的，只能人工介入——这是两者最本质的差别。

减少 DB 死锁的三个实操

  1. 加索引：UPDATE ... WHERE 无索引字段 会走全表扫描 + 锁所有扫描行 → 极易死锁
  2. 固定更新顺序：批量更新时按主键排序，ORDER BY id
  3. 缩小事务：事务里不要做 RPC、不要等待用户输入

为什么 synchronized 死锁比 ReentrantLock 死锁更难查

两者 jstack 都能查出。但 synchronized 不能超时、不能被中断，所以一旦发生就是「必须重启进程」的死局；而 ReentrantLock 的 tryLock(timeout) 至少能让代码自己走出来。这就是「用 ReentrantLock 换可诊断性」的理由。

继续追问（面试官下一步会问什么）

Q：jstack 能检测出所有死锁吗？ 不能。它只能检测 Java 层 monitor（synchronized）和 AQS 相关的死锁（通过对象图）。以下检测不出来： - 活锁（线程在动） - LockSupport.park 手工阻塞（没有锁的持有关系，AQS 之外的自定义阻塞） - native 层死锁（JNI 调用链里） - ThreadPoolExecutor 循环依赖（A 任务提交给池子等 B 任务，B 任务也在同一个池子里等不到线程 —— 这是最隐蔽的一类「死锁」，实际上是线程饥饿）

最后一条在生产里非常常见：在同一个线程池里，任务 A 用 future.get() 等任务 B，而 B 还在队列里排着。线程全被 A 占满 → B 永远没机会执行 → 永久卡住。预防：不同层次的异步用不同的线程池（第 10、13 题都会讲）。

Q：什么是「锁顺序死锁」最隐蔽的形态？ 不是代码里显式的嵌套 synchronized，而是通过第三方方法间接持有：

class TaxPayer {
    public void pay(Account other, double amount) {
        synchronized (this) {                    // 持有 this
            other.collect(amount);               // 调用外部方法 —— 它内部可能锁 other，甚至回调回来
        }
    }
}

防御原则：在持有锁时，绝不要调用外部可覆写的方法（open call 问题）。这是《Java 并发编程实战》里的经典建议。

Q：tryLock 超时后，为什么必须释放已持有的锁？ 因为「不可剥夺」的破法有两种：① 拿不到就不拿（但你要把已拿的还回去）；② 让超时的那个线程回滚。如果只放弃不释放，被放弃的那把锁还握着，别人照样卡。所以代码模式必须是：

if (lock1.tryLock()) {
    try {
        if (!lock2.tryLock()) { return false; }   // 失败：finally 会释放 lock1
        try { work(); } finally { lock2.unlock(); }
    } finally { lock1.unlock(); }                  // 保证释放
}

Q：只用一把锁还会有死锁吗？ 单把锁不会有「循环等待」死锁，但可能有「自己等自己」：ReentrantLock 可重入所以没事，StampedLock 不可重入 → 同一线程重复获取同一把 StampedLock 就是死锁。这是 StampedLock 的经典坑。

Q：怎么在 CI 里提前发现死锁？ ① 单元测试里用多线程并发跑 + 超时断言（@Test(timeout = 5000)）；② 静态扫描工具（SpotBugs 的 DEADLOCK 规则、IDEA 的 Deadlock 检查）能发现部分「加锁顺序不一致」；③ 压力测试时开 -XX:+UnlockDiagnosticVMOptions -XX:+PrintConcurrentLocks。

源码骨架（ThreadPoolExecutor.execute）：

public void execute(Runnable command) {
    int c = ctl.get();
    if (workerCountOf(c) < corePoolSize) {                    // ① 核心线程
        if (addWorker(command, true)) return;
        c = ctl.get();
    }
    if (isRunning(c) && workQueue.offer(command)) {           // ② 入队
        int recheck = ctl.get();
        if (!isRunning(recheck) && remove(command))
            reject(command);                                  // ②b 二次检查：池已关闭则拒绝
        else if (workerCountOf(recheck) == 0)
            addWorker(null, false);                           // ②c 保证至少有个线程来消费队列
    }
    else if (!addWorker(command, false))                      // ③ 扩容到 max
        reject(command);                                      // ④ 拒绝
}

为什么是「先入队，再扩容」而不是反过来？

因为 max 通常远大于 core 的设计意图是「应对突发尖峰」而不是「常态并发」。如果先扩容到 max： 1. 每次小高峰都创建大量线程 → 线程创建/销毁成本、栈内存（1MB/线程）开销巨大 2. 任务处理完又全部空闲回收 → 抖动 3. 队列存在就没意义了（永远不会用上）

所以设计上是「队列兜住常规积压，队列满了说明是真的扛不住了才扩容，再扛不住才拒绝」。理解这一点，就理解了为什么「用无界队列时 maximumPoolSize 完全失效」（队列永远不满，永远不会扩容到 max）——这是上面那个 Or 型问题的答案。

Executors 四个工厂方法的坑（阿里的原因）

工厂方法 队列类型 坑 后果
newFixedThreadPool(n) LinkedBlockingQueue（无界，容量 Integer.MAX_VALUE） 队列几乎永远不满 → maximumPoolSize 形同虚设；任务无限堆积 OOM: Java heap space（队列里的任务对象撑爆堆）
newSingleThreadExecutor() LinkedBlockingQueue（无界） 同上，单线程消费慢 → 堆积更快 OOM
newCachedThreadPool() SynchronousQueue（不存储） + max = Integer.MAX_VALUE 来一个任务就建一个线程，无上限 OOM: unable to create new native thread（线程数爆掉：1000 线程 = 1GB 栈）
newScheduledThreadPool(n) DelayedWorkQueue（无界） 同上，延迟任务无限堆积 OOM

阿里规约原文：「线程池不允许使用 Executors 去创建，而是通过 ThreadPoolExecutor 的方式，这样的处理方式让写的同学更加明确线程池的运行规则，规避资源耗尽的风险。」

生产级自定义线程池（可直接复制）

import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class ThreadPoolFactory {

    /** 通用业务线程池：有界队列 + 有界线程 + 有意义的线程名 */
    public static ThreadPoolExecutor build(String bizName, int core, int max, int queueCapacity) {
        ThreadFactory factory = new ThreadFactory() {
            private final AtomicInteger seq = new AtomicInteger(1);
            @Override
            public Thread newThread(Runnable r) {
                Thread t = new Thread(r, bizName + "-" + seq.getAndIncrement());
                t.setDaemon(false);                                 // 非守护，JVM 不提前退出
                t.setUncaughtExceptionHandler((thread, e) ->
                    System.err.println("[FATAL] " + thread.getName() + " 未捕获异常: " + e));
                return t;                                            // ★ 命名！jstack 里一眼认出来
            }
        };

        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                core,
                max,
                60L, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(queueCapacity),             // ★ 有界队列
                factory,
                new ThreadPoolExecutor.CallerRunsPolicy());          // ★ 反压而非丢任务

        pool.allowCoreThreadTimeOut(false);                          // 核心线程不回收（默认）
        pool.prestartAllCoreThreads();                               // 预热，避免首波请求慢
        return pool;
    }

    public static void main(String[] args) {
        int cpu = Runtime.getRuntime().availableProcessors();
        ThreadPoolExecutor pool = build("rrm-opt", cpu, cpu * 4, 200);
        for (int i = 0; i < 50; i++) pool.execute(() -> { /* 调优计算 */ });
        // 优雅关闭
        pool.shutdown();
    }
}

IO 密集型 2N 或 N × (1 + 等待时间/计算时间) 等待时间占比越高，线程越多

// K8s 优雅停机的标准写法（配合 preStop hook / SIGTERM）
public void gracefulShutdown(ThreadPoolExecutor pool) throws InterruptedException {
    pool.shutdown();                                        // ① 不再接新任务
    if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {     // ② 等 30s 让存量跑完
        List<Runnable> dropped = pool.shutdownNow();        // ③ 超时强停
        System.err.println("未执行完的任务数: " + dropped.size());
        // ④ 把这些任务落库/落 MQ，重启后补偿
        if (!pool.awaitTermination(10, TimeUnit.SECONDS))
            System.err.println("线程池未能终止");
    }
}

注意：shutdownNow() 的 interrupt() 只是发信号，如果你的任务不检查中断（while(true) 里没有 isInterrupted()），它根本停不下来。

线程池的五个状态（ctl 高 3 位）

private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0));
// ctl = 高 3 位 = 运行状态，低 29 位 = 线程数
private static final int COUNT_BITS = Integer.SIZE - 3;    // 29
private static final int CAPACITY   = (1 << COUNT_BITS) - 1; // 约 5.36 亿

RUNNING    = -1 << 29 = 111  // 接收新任务 + 处理队列任务
SHUTDOWN   =  0 << 29 = 000  // 不接新任务，但处理队列任务
STOP       =  1 << 29 = 001  // 不接新任务、不处理队列、中断正在执行的任务
TIDYING    =  2 << 29 = 010  // 所有任务终止、workerCount = 0（会调 terminated()）
TERMINATED =  3 << 29 = 011  // terminated() 执行完毕

为什么用一个 AtomicInteger 同时存状态和线程数：一次 CAS 就能同时更新两者，避免状态和计数不一致的竞态。这个设计非常巧妙，面试能说出来是加分项。

// 情况一：execute() 提交 → 异常会【吞掉并打印栈】，且线程会死掉被替换
pool.execute(() -> { throw new RuntimeException("boom"); });
// 现象：控制台有异常栈，但这个任务"消失"了，也不影响后续任务（会新建线程替代）

// 情况二：submit() 提交 → 异常被【完全吞掉】，只有 future.get() 才抛出来
Future<?> f = pool.submit(() -> { throw new RuntimeException("boom"); });
// 现象：什么都不会打印！必须 f.get() 才会抛 ExecutionException

这是生产事故的高发点：用 submit() 又不去 get()，异常静默丢失，任务「莫名没执行」。解决方案： 1. submit() 必须 get() 或者用 CompletableFuture 的 exceptionally/handle 2. execute() 用带 UncaughtExceptionHandler 的 ThreadFactory 3. 重写 afterExecute 统一兜底：

ThreadPoolExecutor pool = new ThreadPoolExecutor(4, 8, 60, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(100)) {
    @Override
    protected void afterExecute(Runnable r, Throwable t) {
        super.afterExecute(r, t);
        if (t == null && r instanceof Future<?>) {            // submit 包装的异常在这里
            try { ((Future<?>) r).get(); }
            catch (CancellationException ce) { t = ce; }
            catch (ExecutionException ee) { t = ee.getCause(); }
            catch (InterruptedException ie) { Thread.currentThread().interrupt(); }
        }
        if (t != null) {
            log.error("线程池任务异常: {}", t.getMessage(), t);
            // 上报监控/告警
        }
    }
};

SynchronousQueue 的两种模式

newCachedThreadPool() 用的 SynchronousQueue 是「不存储元素的阻塞队列」：offer 必须有另一个线程正在 take 才能成功。它有公平/非公平两种模式（默认非公平，用栈实现；公平模式用队列实现，吞吐低但更有序）。

LinkedBlockingQueue 与 ArrayBlockingQueue 的选择

ArrayBlockingQueue LinkedBlockingQueue
底层 数组，容量必须指定 链表，可不指定（= Integer.MAX_VALUE）
锁 一把锁 + 两个 Condition（存取互斥） 两把锁（putLock/takeLock），存取可并行
吞吐 中 高（两把锁）
内存 预分配，固定占用 动态增长（无界时是 OOM 风险源）
推荐 生产首选（有界天然反压） 需要高吞吐且必须显式给容量

为什么 LinkedBlockingQueue 能有两把锁：因为链表节点的 next 由 putLock 保护、head 由 takeLock 保护，入队和出队操作的是不同字段，所以可以并行。而数组的 putIndex/takeIndex 有交叠，必须一把锁。这是个很漂亮的优化，追问时能讲。

ForkJoinPool（另一种线程池）

  • 每个线程有自己的双端队列（Deque），fork 把子任务压到自己队列头，join 时先处理自己队列，空了就 work-stealing 从别人队列尾偷任务
  • 适合分治型、可递归拆分的任务（归并排序、并行流、树形计算）
  • commonPool 默认并行度 = CPU 核数 - 1（-Djava.util.concurrent.ForkJoinPool.common.parallelism 可调）
  • parallelStream() 默认就用它 → 里面如果做阻塞 IO，会把 commonPool 打满，影响全 JVM 所有并行流（这是个经典坑，必须显式传自定义 pool）

K8s 环境下的两个坑

  1. availableProcessors() 在容器里：JDK8u191 之前不识别 cgroup limit，容器限制了 2 核却报了宿主机 64 核 → 线程池开成 128 个线程。JDK10+ 默认开 -XX:+UseContainerSupport 修复。 这个问题现在已经被 K8s 环境自动注入的 CPU limit 解决了（JVM 会读 cgroup）。
  2. preStop hook + SIGTERM：K8s 删 pod 时给的是 SIGTERM，JVM 默认会执行 shutdown hook。必须在 shutdown hook 里 shutdown() + awaitTermination，否则队列里的任务全丢。
继续追问（面试官下一步会问什么）

Q：线程池的核心线程会被回收吗？ 默认不会（allowCoreThreadTimeOut=false）。调 allowCoreThreadTimeOut(true) 后核心线程也会在 keepAliveTime 后销毁。一般不建议开——核心线程被回收后，突发流量又要重新创建，得不偿失。

Q：maximumPoolSize 小于 corePoolSize 会怎样？ 构造函数直接抛 IllegalArgumentException。这是防御性编程的示例，面试可以提一句。

Q：为什么有时候任务提交了却不执行？ 三个可能：① 走了 DiscardPolicy（静默丢弃）；② 池已经 shutdown 了（走拒绝策略）；③ 任务在 submit() 里抛异常被 Future 吞了。排查就三件事：看拒绝策略日志、看池状态、看 Future.get()。

Q：线程池里的线程为什么不能随便用 ThreadLocal？ 因为线程复用，上次任务的 ThreadLocal 值会残留给下个任务（内存泄漏 + 脏数据）。必须在 finally 里 remove()（详见第 11 题，这是最真实的考点）。

Q：prestartAllCoreThreads() 有必要吗？ 有价值。它避免「第一批请求来的时候才创建线程」的冷启动延迟。但如果池很大（几百个），预热会拖慢启动——按需决定，一般只对核心池小的关键服务做。

Q：ThreadPoolExecutor 能动态调参吗？ 能。setCorePoolSize() / setMaximumPoolSize() 是线程安全的，立即生效（调小 maximum 时会中断多余的空闲线程）。这是「无需重启动态调整线程数」的实现基础——美团的 DynamicTp、阿里的 SOFA 都这么做。

③ 你做过 node-ffi 生产级调用 C 算法 .so 库 —— 这个点在 Java 里有个精确对应：node-ffi 的调用是同步阻塞的，会占住 libuv 的线程池（默认 4 个线程，UV_THREADPOOL_SIZE 环境变量可调）。如果并发调用很多，libuv 线程池会被打满，所有异步 IO 都卡住。这跟 Java 里「把阻塞 IO 任务提交到线程池，线程不会释放」是完全同构的问题 —— 面试时可以主动做这个类比：

「我们做过 Node.js 通过 node-ffi 调 C 算法 .so 库，这是同步阻塞调用，会占住 libuv 线程池（默认只有 4 个）。这和 Java 线程池里执行阻塞任务会占住工作线程是一样的——所以线程数的设定必须和下游的阻塞特性匹配，不是越大越好。」

ThreadLocal：`ThreadLocalMap`、内存泄漏与跨线程传递 ★

概念

每个 Thread 内部有一个 ThreadLocalMap（字段名 threadLocals），key 是 ThreadLocal 的弱引用，value 是强引用。 泄漏的成因：key 被 GC 回收变成 null，但 value 还被 Map 强引用着；在线程池里线程永不销毁 → value 永远不释放。 唯一正确姿势：try { ... } finally { threadLocal.remove(); }。

数据结构（这是全部理解的基础）

public class Thread implements Runnable {
    ThreadLocal.ThreadLocalMap threadLocals = null;                  // ★ 每个线程一个 Map
    ThreadLocal.ThreadLocalMap inheritableThreadLocals = null;        // 给 InheritableThreadLocal 用
}

public class ThreadLocal<T> {
    public void set(T value) {
        Thread t = Thread.currentThread();
        ThreadLocalMap map = getMap(t);                              // 拿的是【当前线程】的 map
        if (map != null) map.set(this, value);                       // key 是 this（ThreadLocal 对象本身）
        else createMap(t, value);
    }
    public T get() {
        ThreadLocalMap map = getMap(Thread.currentThread());
        if (map != null) {
            ThreadLocalMap.Entry e = map.getEntry(this);
            if (e != null) return (T) e.value;
        }
        return setInitialValue();                                    // 没设过 → 调 initialValue()
    }
    public void remove() {
        ThreadLocalMap m = getMap(Thread.currentThread());
        if (m != null) m.remove(this);                               // ★ 必须手动调用
    }
}

关键结论：数据存在 Thread 里，不在 ThreadLocal 里。 ThreadLocal 只是「查表用的 key」。所以： - 同一个 ThreadLocal 对象在不同的线程里，get() 出来的值不同 → 线程隔离 - ThreadLocal 对象本身被所有线程共享（通常是 static final）

ThreadLocalMap 的 Entry（弱引用的位置）

static class ThreadLocalMap {
    static class Entry extends WeakReference<ThreadLocal<?>> {       // ★ key 是弱引用
        Object value;                                                // ★ value 是强引用
        Entry(ThreadLocal<?> k, Object v) {
            super(k);                                                // key 交给 WeakReference
            value = v;
        }
    }
    private Entry[] table;                                           // 用开放地址法（线性探测）解冲突
    private int threshold;                                           // len * 2 / 3，超过则扩容
}

内存泄漏的完整链路（必须能讲清每一步）

  1. 业务方法 threadLocal.set(bigObject) → Entry 被放进当前线程的 ThreadLocalMap
  2. 方法结束，栈上的 threadLocalRef 消失，只剩 Entry.key 这个弱引用指向 ThreadLocal 对象
  3. 发生 GC → 弱引用的 key 被回收，Entry.key 变成 null
  4. 但 Entry.value 是强引用，ThreadLocalMap → Entry → value 这条链还在 → bigObject 无法被回收
  5. 如果这个线程是线程池里的常驻线程（corePoolSize 个线程永不销毁）→ 这条链永远存在 → 内存泄漏

关键点：泄漏的是 value，不是 key。 弱引用 key 的设计是「至少别让 key 也泄漏」——如果 key 是强引用，那 ThreadLocal 对象本身也会被这条链永久拽住，泄漏两份。

为什么 ThreadLocalMap 不做自动清理

它其实做了一点：get() / set() / remove() 触发时，会调 expungeStaleEntry() 清理探测路径上 key 为 null 的 Entry。所以「只要这个线程还在用这个 ThreadLocalMap，陈旧 Entry 会被顺手清掉」。

但问题在于：如果线程此后再也不碰这个 ThreadLocalMap（典型场景：线程池线程处理完这个请求，之后处理的都是不需要这个 ThreadLocal 的任务，但 Map 里还挂着上次的值），清理逻辑永远不会触发 → 泄漏。

内存泄漏复现（可以直接跑）

import java.util.concurrent.*;

public class ThreadLocalLeakDemo {
    // 注意：这里刻意不设 static final，为了能模拟 ThreadLocal 对象被回收
    private static ThreadLocal<byte[]> local = new ThreadLocal<>();

    public static void main(String[] args) throws Exception {
        // 固定 1 个线程的池子，线程永不销毁
        ExecutorService pool = Executors.newFixedThreadPool(1);

        for (int i = 0; i < 100; i++) {
            pool.submit(() -> {
                local.set(new byte[10 * 1024 * 1024]);   // 每次塞 10MB
                // ❌ 忘记 remove() —— 线程复用，Value 一直被拽住
            });
            Thread.sleep(50);
            // 观察：堆内存持续上涨，Full GC 也回收不掉 → OOM
        }
        // ✅ 正确写法：try/finally + remove()，或者把 local 设成 static final 减少 key 被回收
    }
}

验证是否泄漏：jmap -dump 后 MAT 里搜 ThreadLocalMap$Entry，看有多少个 key == null 的 Entry —— 这些就是「已泄漏但没被清理」的残留。

为什么 ThreadLocal 建议 static final

private static final ThreadLocal<UserContext> CTX = new ThreadLocal<>();   // ✅

因为： 1. static final 让 ThreadLocal 对象始终有强引用（类变量），Entry.key 就不会变成 null → 至少避免了「key 被回收但 value 残留」这个最难处理的情况 2. 避免每次 new ThreadLocal() 造成多个 key，Map 里堆积无用 Entry 3. 注意：static final 只能延缓问题，value 泄漏依然需要 remove() 解决——别把它当成万能药（这是常见误解）

InheritableThreadLocal 与线程池的致命缺陷

private static final InheritableThreadLocal<String> TRACE = new InheritableThreadLocal<>();

public static void main(String[] args) {
    TRACE.set("trace-001");
    // ① 普通 new Thread：子线程能拿到父线程的值（Thread 构造时 copy）
    new Thread(() -> System.out.println("新线程读到: " + TRACE.get())).start();   // trace-001 ✅

    // ② 线程池：线程是复用的，不会重新 copy！❌
    ExecutorService pool = Executors.newFixedThreadPool(1);
    TRACE.set("trace-A");
    pool.submit(() -> System.out.println("池任务1: " + TRACE.get()));   // trace-A
    TRACE.set("trace-B");
    pool.submit(() -> System.out.println("池任务2: " + TRACE.get()));   // 可能还是 trace-A ❌
}

原因：InheritableThreadLocal 的值是通过 Thread 构造方法里的 ThreadLocal.createInheritedMap(parent.inheritableThreadLocals) 拷贝的——只在「创建线程」时拷贝一次。线程池的线程在第一次 submit 时就创建好了，之后复用，不会再拷贝。

TransmittableThreadLocal（TTL，阿里开源）

import com.alibaba.ttl.TransmittableThreadLocal;
import com.alibaba.ttl.threadpool.TtlExecutors;

private static final TransmittableThreadLocal<String> TRACE = new TransmittableThreadLocal<>();

public static void main(String[] args) {
    // 关键：把线程池包装成 TTL 感知的
    ExecutorService raw = Executors.newFixedThreadPool(1);
    ExecutorService pool = TtlExecutors.getTtlExecutorService(raw);

    TRACE.set("trace-A");
    pool.submit(() -> System.out.println("任务1: " + TRACE.get()));   // trace-A ✅
    TRACE.set("trace-B");
    pool.submit(() -> System.out.println("任务2: " + TRACE.get()));   // trace-B ✅
    TRACE.remove();
}

TTL 的实现原理（三步，面试能说出来就是高手）：

  1. 捕获（capture）：任务被提交时，把当前线程的 TTL 快照存进被包装的 TtlRunnable
  2. 回放（replay）：任务在池线程里执行前，把快照设进当前线程的 TTL
  3. 恢复（restore）：任务执行完，把池线程原来的 TTL 值还原回去（避免污染下一个任务）

这正是它比 InheritableThreadLocal 强的地方——不是「创建时拷贝一次」，而是「每次执行前后都做快照/回放/还原」。

三种方案对比

方案 跨 new Thread 跨线程池 原理 适用
ThreadLocal ❌ ❌ 只存当前线程 单线程内上下文
InheritableThreadLocal ✅ ❌ Thread 构造时拷贝一次 手工创建的子线程
TransmittableThreadLocal ✅ ✅ 提交时捕获 + 执行前回放 + 执行后恢复 线程池 + 链路追踪 + 事务

线程池里传递上下文的三种工程做法

  1. TTL（推荐）：TtlExecutors.getTtlExecutorService(pool) 包装一下，无侵入
  2. 手工传参：任务提交时显式把上下文作为参数传给 Runnable（最笨但最可靠，没有隐式依赖）
  3. CompletableFuture + 装饰器：重写 Executor 的 execute 方法，在里面做 set/remove（TTL 的本质做法）

remove() 的正确写法（模板）

private static final ThreadLocal<UserContext> CTX = new ThreadLocal<>();

public void handleRequest(Request req) {
    try {
        CTX.set(buildContext(req));
        doBusiness();                                     // 业务逻辑
    } finally {
        CTX.remove();                                     // ★ 无论如何都要清理
    }
}

为什么必须 finally：业务抛异常时 set 已经执行了，若没有 finally，这个线程下次被复用时就会拿到上一个请求的用户上下文 → 这是越权的安全事故（用户 A 看到用户 B 的数据），比内存泄漏更严重。

拓展

ThreadLocalMap 的哈希与扩容（细节追问用）

  • 哈希值：ThreadLocal 用 threadLocalHashCode = nextHashCode() 生成，每次 +0x61c88647（黄金分割数，让哈希分布均匀）
  • 冲突解决：开放地址法（线性探测），不是链表法。set 时若槽位被占就往后找空位
  • 扩容：size >= threshold（len * 2 / 3）且没有可清理的槽位时，容量翻倍（resize()），并对所有 Entry 重新哈希
  • 清理时机：expungeStaleEntry() 会在探测路径上顺手清理 key 为 null 的 Entry；cleanSomeSlots() 在 set 时启发式地清理

为什么不用链表法：ThreadLocal 数量通常很少（几个到几十个），开放地址法缓存友好、无额外对象开销，比链表更划算。这是「为典型场景做优化」的设计范例。

最重要的两个推论（面试直接能用）

  1. Spring 事务为什么必须同一个线程？ 因为 Connection 是存在 ThreadLocal 里按线程绑定的。一旦你在事务方法里开新线程执行 SQL，那个线程的 ThreadLocal 里没有绑定的 Connection → 新线程自己开一个连接、自己提交，脱离事务控制。这就是「事务失效」的根因之一。

  2. @Async / 线程池里的操作为什么会脱离事务和登录上下文？ 同理 —— ThreadLocal 不跨线程。解法：TTL 传递上下文，或者把事务操作收拢在主线程里。

继续追问（面试官下一步会问什么）

Q：既然 key 是弱引用，为什么不用强引用 + 自动清理？ 如果 key 是强引用，ThreadLocalMap → Entry → ThreadLocal 这条链会让ThreadLocal 对象本身也无法回收（即使业务代码早就不用它了），泄漏更严重。弱引用是「两害相权取其轻」：至少保证 key 能被回收，value 靠手动 remove() 兜底。这是 JDK 团队在「自动」和「可控」之间的妥协。

Q：ThreadLocal 的 get() 为什么会创建 Map 并调 setInitialValue()？ setInitialValue() 会调 initialValue()（默认返回 null），并把返回值放进 Map。所以 get() 后 Map 里就有 Entry 了——即使你只想读不想写，也会产生 Entry。这解释了为什么「只 get 不 remove」也会泄漏。

Q：ThreadLocal 的 remove() 和 set(null) 有什么区别？ remove() 会删掉整个 Entry（key 和 value 都断开）；set(null) 只是把 value 设为 null，Entry 还在（key 如果是活的会一直存在）。所以 remove() 才是正确做法，set(null) 治标不治本。

Q：父线程的 ThreadLocal 值，子线程能读到吗？ 普通 ThreadLocal 读不到（每个线程独立）。InheritableThreadLocal 能读到，但仅在 new Thread 时拷贝一次，线程池复用场景失效。

Q：CompletableFuture 里能拿到 ThreadLocal 吗？ thenApply 等回调默认在 ForkJoinPool.commonPool 或其他线程上执行，不继承调用方的 ThreadLocal。同样需要 TTL 或者显式传上下文。这是异步链路里 traceId 丢失的根因。

Q：怎么检测线上 ThreadLocal 泄漏？ jmap -dump + MAT 搜 ThreadLocalMap，看 key == null 的 Entry 数量和它们 value 的总大小。retained size 排序就一目了然（和手册 07 第 12 题的 MAT 用法一致）。

并发容器：`ConcurrentHashMap`、`CopyOnWriteArrayList`、`BlockingQueue` ★

概念

ConcurrentHashMap 的两个版本差异是必考：JDK7 用 Segment 分段锁（默认 16 段）；JDK8 改成「CAS 插空桶 + synchronized 锁桶头 + 红黑树」，锁粒度从「段」细化到「桶」。 CopyOnWriteArrayList 写时复制，读无锁写加锁，适合读多写少的白名单/监听器列表。 BlockingQueue 是生产者-消费者模型的基石，记住 ArrayBlockingQueue（有界）和 LinkedBlockingQueue（默认无界，危险）。

// putVal：JDK8 的经典实现
final V putVal(K key, V value, boolean onlyIfAbsent) {
    if (key == null || value == null) throw new NullPointerException();   // ★ 不允许 null
    int hash = spread(key.hashCode());                                    // 扰动函数
    int binCount = 0;
    for (Node<K,V>[] tab = table;;) {
        Node<K,V> f; int n, i, fh;
        if (tab == null || (n = tab.length) == 0)
            tab = initTable();                                            // ① 懒初始化
        else if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {
            if (casTabAt(tab, i, null, new Node<K,V>(hash, key, value)))
                break;                                                    // ② 空桶：CAS 无锁写入
        }
        else if ((fh = f.hash) == MOVED)                                  // -1，ForwardingNode
            tab = helpTransfer(tab, f);                                   // ③ 正在扩容：协助扩容
        else {
            V oldVal = null;
            synchronized (f) {                                            // ④ 非空桶：锁头节点
                if (tabAt(tab, i) == f) {
                    if (fh >= 0) {                                        // 链表
                        for (Node<K,V> e = f;; ++binCount) {
                            if (e.hash == hash && (e.key == key || key.equals(e.key))) {
                                oldVal = e.val; if (!onlyIfAbsent) e.val = value; break;
                            }
                            Node<K,V> pred = e;
                            if ((e = e.next) == null) { pred.next = new Node<>(hash,key,value); break; }
                        }
                    } else if (f instanceof TreeBin) {                    // 红黑树
                        // ... 树插入 + 平衡（这里还会加读写锁的 WRITER 位）
                    }
                }
            }
            if (binCount != 0) {
                if (binCount >= TREEIFY_THRESHOLD) treeifyBin(tab, i);    // ⑤ 树化
                if (oldVal != null) return oldVal;
                break;
            }
        }
    }
    addCount(1L, binCount);                                                // ⑥ 计数
    return null;
}

关键设计点： - synchronized (f) 锁的是桶的头节点 —— 这是「锁粒度细化到桶」的实现。因为 synchronized 在 JDK6 后有锁升级优化，性能已经和 ReentrantLock 相当，且代码更简洁、不会忘记释放 - tabAt / casTabAt 用的是 Unsafe 的 volatile 读和 CAS —— 数组元素的 volatile 语义不能用 tab[i] 直接表达（Java 数组元素的 volatile 读写在语言层不支持），所以必须用 Unsafe/VarHandle

为什么 JDK8 要换成这把锁：① synchronized 在 JDK6 后已优化，性能不再是瓶颈；② 代码更简单（不用维护 Segment 的锁对象和继承结构）；③ 并发度不再受段数限制（理论上等于桶数）。

核心原因（Doug Lea 的原话大意）：并发场景下 get(key) 返回 null 有二义性——「这个 key 不存在」还是「这个 key 存在但值是 null」？单线程可以用 containsKey 先判断，但并发下这两步之间值可能被改，判断结果不可靠。直接禁止 null 就从根上消除了歧义。

size() 的实现与弱一致性

// JDK8：baseCount + CounterCell[] 分段计数（和 LongAdder 一个套路）
public int size() {
    long n = sumCount();                      // baseCount + 遍历 counterCells 累加
    return ((n < 0L) ? 0 : (n > (long)Integer.MAX_VALUE) ? Integer.MAX_VALUE : (int)n);
}

为什么弱一致：遍历 counterCells 时其他线程还在 addCount → 结果只是某个瞬间的近似值。同理 isEmpty()、containsValue()、keySet().size() 都是弱一致的。

所以正确用法是：不要用 size() 做业务判断（if (map.size() > 0)），要用 map.isEmpty() 或者直接 get() 判空。

扩容：ForwardingNode 与协助扩容

  1. 扩容时创建新数组 nextTable（容量 2 倍），并把 sizeCtl 设成负数作为「扩容中」的标记
  2. 逐桶搬迁：把旧桶的头节点替换为 ForwardingNode（hash = MOVED = -1），它内部持有 nextTable 引用
  3. 其他线程 put 时遇到 ForwardingNode → 调 helpTransfer() 一起帮忙搬（这就是「多线程协助扩容」）
  4. 搬迁完成 → table = nextTable

为什么能多线程协助：每个线程通过 transferIndex 这个 AtomicInteger 用 CAS 认领一段桶区间，互不干扰。这是并发容器设计里最精妙的一处，面试能讲出来非常加分。

生产者-消费者完整示例

import java.util.concurrent.*;

public class ProducerConsumer {
    public static void main(String[] args) {
        BlockingQueue<Task> queue = new ArrayBlockingQueue<>(100);   // ★ 有界

        // 生产者
        ExecutorService producers = Executors.newFixedThreadPool(2);
        for (int i = 0; i < 2; i++) {
            producers.submit(() -> {
                try {
                    while (true) queue.put(new Task());              // 队列满则阻塞（反压）
                } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            });
        }

        // 消费者
        ExecutorService consumers = Executors.newFixedThreadPool(4);
        for (int i = 0; i < 4; i++) {
            consumers.submit(() -> {
                try {
                    while (true) {
                        Task t = queue.take();                       // 队列空则阻塞
                        process(t);
                    }
                } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            });
        }
    }
    static void process(Task t) { /* 业务处理 */ }
    static class Task {}
}

弱一致性迭代器（Weakly Consistent）

ConcurrentHashMap 的迭代器不抛 ConcurrentModificationException，但可能： - 看到迭代开始后新加入的元素（也可能看不到） - 保证不会重复、不会返回 null

对比三种迭代行为：

类型 代表 遍历时修改
fail-fast HashMap、ArrayList 立刻抛 ConcurrentModificationException（靠 modCount 校验）
fail-safe / 弱一致 ConcurrentHashMap、CopyOnWriteArrayList 不抛异常，可能看到旧快照或部分新数据
快照 CopyOnWriteArrayList 的迭代器 看到的是创建迭代器那一刻的完整快照

为什么 HashMap 要 fail-fast：它能提前暴露并发 bug（而不是默默产出错误结果）。但这也让 HashMap 在多线程下「不可用」——JDK7 的 HashMap 并发 put 甚至会导致链表成环 + CPU 100%（经典的死循环 bug，JDK8 已修复）。

ConcurrentHashMap 的 computeIfAbsent（并发下的正确姿势）

// ❌ check-then-act：并发下可能重复创建
if (!map.containsKey(k)) map.put(k, createValue(k));

// ✅ 原子操作（computeIfAbsent 内部对桶加锁，保证只执行一次）
map.computeIfAbsent(k, this::createValue);

// 其他原子复合操作：
map.compute(k, (key, v) -> v == null ? 1 : v + 1);      // 原子的读改写
map.merge(k, 1, Integer::sum);                          // 原子累加（最常用）
map.computeIfPresent(k, (key, v) -> v + 1);             // 存在才更新

注意坑：computeIfAbsent 的 mapping function 不要做慢操作（RPC、大查询），因为它持有桶的锁；更要命的是不要在 mapping function 里再操作同一个 map（可能死锁或递归）。

LongAdder 的兄弟：ConcurrentHashMap 的 CounterCell

size() 的计数用的就是和 LongAdder 一样的分段累加（Striped64 思想）：高并发下 CAS 一个 baseCount 会失败率极高，所以分散到 CounterCell[] 数组上，每个线程更新自己的 Cell。「高并发计数分段化」是 JDK 里反复出现的模式（LongAdder、ConcurrentHashMap.size()、JVM 的分代年龄），值得作为一个「设计模式」记住。

Q：JDK8 ConcurrentHashMap 的 synchronized 会不会成为瓶颈？ 理论上锁的是「桶头」，并发度等于桶数（初始 16，扩容后更高）。只有哈希冲突到同一个桶才会互斥。实践中比 JDK7 的 16 段好得多。但如果大量 key 的 hash 相同（恶意构造或 poor hashCode），会退化到锁一个桶 → 全部串行。这就是哈希碰撞攻击（HashDoS），用红黑树树化（O(log n) 而非 O(n)）可以缓解遍历性能，但锁竞争依然存在。

Q：ConcurrentHashMap 遍历时能安全删除吗？ 不能直接 map.remove() 配合迭代器（remove 本身是线程安全的，但可能在遍历中错过元素）。正确做法：

// ✅ JDK8：用 remove 的重载，原子地「检查后删除」
map.remove(key, expectedValue);

// ✅ 或者用 forEach / search / reduce 的原子遍历
map.forEach((k, v) -> { if (needRemove(v)) map.remove(k, v); });

Q：CopyOnWriteArrayList 能替代 ArrayList 吗？ 不能。① 写操作 O(n) 全量复制，频繁写会疯狂触发 GC；② 内存双倍（大列表可能直接 OOM）；③ 迭代器看到的是快照，做不到读取最新数据。只在「读极多、写极少、数据量不大」时才用——最典型的就是「配置/白名单，一天改一次，每秒读百万次」。

CountDownLatch 标准用法

int taskCount = 10;
CountDownLatch latch = new CountDownLatch(taskCount);          // 计数 N

for (int i = 0; i < taskCount; i++) {
    pool.submit(() -> {
        try { doWork(); }
        finally { latch.countDown(); }                          // ★ 必须 finally，否则异常时永远等下去
    });
}
latch.await();                                                  // 主线程阻塞直到归零
// latch.await(3, TimeUnit.SECONDS);                            // 带超时更稳（防止死等）

CyclicBarrier 标准用法

int parties = 3;
CyclicBarrier barrier = new CyclicBarrier(parties,
        () -> System.out.println("--- 所有线程到齐，执行 barrierAction（只由一个线程执行）---"));

for (int round = 0; round < 3; round++) {
    for (int i = 0; i < parties; i++) {
        final int id = i;
        new Thread(() -> {
            try {
                System.out.println("线程" + id + " 完成本阶段计算");
                barrier.await();                                 // 等其他人（可循环！）
                System.out.println("线程" + id + " 进入下一阶段");
            } catch (Exception e) { Thread.currentThread().interrupt(); }
        }).start();
    }
    Thread.sleep(2000);
}

重要坑：只要有一个线程在 await 前被中断或超时，其他所有等待的线程都会抛 BrokenBarrierException，屏障「破损」。此时 isBroken() 返回 true，必须调 reset() 才能继续用。

Semaphore 限流（生产级模板）

public class RateLimiter {
    private final Semaphore permits;

    public RateLimiter(int maxConcurrent) {
        this.permits = new Semaphore(maxConcurrent, true);        // true = 公平模式（防饥饿）
    }

    /** 带超时的获取：拿不到就快速失败，避免请求堆积 */
    public <T> T executeWithLimit(Supplier<T> task) {
        boolean acquired = false;
        try {
            acquired = permits.tryAcquire(500, TimeUnit.MILLISECONDS);   // ★ 带超时
            if (!acquired) throw new RejectedExecutionException("系统繁忙，请稍后重试");
            return task.get();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException("被中断", e);
        } finally {
            if (acquired) permits.release();                      // ★ 只有拿到了才释放！
        }
    }
}

为什么 release() 要有 acquired 判断：如果 tryAcquire 超时失败但你在 finally 里无条件 release()，会造成许可膨胀（许可数越来越多，限流彻底失效）。这是很隐蔽的生产 bug。

    CompletableFuture<User>    userF   = CompletableFuture.supplyAsync(() -> userService.get(uid), pool);

    return CompletableFuture.allOf(userF, orderF, pointsF)
            .thenApply(v -> new UserVO(userF.join(), orderF.join(), pointsF.join()));

超时控制（JDK8 没有 orTimeout，必须自己写）

      .exceptionally(ex -> { log.warn("调用超时，走降级"); return Fallback.INSTANCE; });

// JDK8：手工实现（面试常问「JDK8 怎么加超时」）
public static <T> CompletableFuture<T> withTimeout(CompletableFuture<T> future,
                                                   long timeout, TimeUnit unit) {
    final CompletableFuture<T> result = new CompletableFuture<>();
    ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor(r -> {
        Thread t = new Thread(r, "cf-timeout"); t.setDaemon(true); return t;
    });
    scheduler.schedule(() -> result.completeExceptionally(
            new TimeoutException("调用超时")), timeout, unit);
    future.whenComplete((v, e) -> {
        if (e != null) result.completeExceptionally(e);
        else result.complete(v);
    });
    return result;
}

继续追问（面试官下一步会问什么）

Q：CyclicBarrier 为什么不用 AQS？ 因为它是多个线程互相等（对称关系），不是「持有者/等待者」的非对称关系。用 ReentrantLock + Condition 更直观：每个线程 await 时先 lock，count-- 到 0 就 signalAll 并重置，否则 condition.await()。AQS 的设计适合「一个资源多个竞争者」，不适合「对等同步」。

Q：CountDownLatch 的 await() 会释放锁吗？ CountDownLatch 没有锁的概念，await() 走的是 AQS 的共享模式 acquireSharedInterruptibly：state != 0 就入队 + park。它不「持有」任何锁，所以没有释放的问题。（对比 Object.wait 必须先持锁再释放，这是两套机制。）

Q：Semaphore 的许可数可以为负吗？ 可以。release() 会让 state 增加，如果之前有线程在等，许可会直接传给等待者，此时 state 可能短暂为负。所以 availablePermits() 返回负数不代表出错——它表示「有多少线程在排队等许可」。

Q：CompletableFuture.allOf 里有一个失败会怎样？ allOf 返回的 future 会立即以异常完成，但其他任务不会被取消（它们继续跑）。如果想「一个失败就取消全部」，需要自己维护 CompletableFuture 列表并逐个 cancel(true)。JDK9 之后有 CompletableFuture.delayedExecutor 等工具，但仍没有内置的「取消全部」。 这是个真实的痛点。

Q：thenApply 和 thenApplyAsync 有什么区别？ thenApply 在完成上一个任务的那个线程上执行回调（可能是 main、可能是池线程）；thenApplyAsync 重新提交到线程池执行。差别在于「回调在哪跑」：如果回调里有阻塞 IO，必须用 Async 版本（并传自己的池），否则会阻塞上一个任务所在线程。

概念

Redis 分布式锁的最小正确实现：SET key value NX EX 30（原子地「不存在才设置 + 设过期」），释放时用唯一值比对 + Lua 脚本原子删除。 必须解决三个问题：加锁原子性、锁误删、锁过期业务没完。 前两个靠 NX + 唯一值 + Lua，第三个靠看门狗自动续期（Redisson 的 RLock）。

从错误到正确的四步演进（这段演进过程本身就是面试答案）

// ❌ 版本一：SETNX 没设过期 → 进程崩溃则永久死锁
jedis.setnx("lock:ap:1001", "1");
// 业务
jedis.del("lock:ap:1001");

// ❌ 版本二：分两步设置（非原子）→ setnx 成功但 expire 前崩溃 → 依然死锁
jedis.setnx("lock:ap:1001", "1");
jedis.expire("lock:ap:1001", 30);

// ❌ 版本三：原子设置了，但删除时不校验 → 误删别人的锁
//    线程A 超时释放 → 线程B 拿到锁 → A 执行完 del 把 B 的锁删了！
jedis.set("lock:ap:1001", "1", "NX", "EX", 30);
jedis.del("lock:ap:1001");

// ✅ 版本四：唯一值 + Lua 原子比对删除（生产可用）
String token = UUID.randomUUID().toString();
String result = jedis.set("lock:ap:1001", token, "NX", "EX", 30);
if ("OK".equals(result)) {
    try { doBusiness(); }
    finally { releaseLock("lock:ap:1001", token); }
}

-- release.lua：先比对再删除，两个操作必须在 Redis 端原子完成
-- 如果分成 GET + DEL 两步（Java 侧），中间锁过期被别人拿到 → 依然误删
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end

SET key value NX EX 的原子性：一条命令同时完成「判断不存在」和「设置 + 过期」，由 Redis 单线程模型保证原子。SETNX + EXPIRE 两条命令就不行（中间可能崩溃）。

锁过期但业务没执行完 —— 看门狗（Watch Dog）

// Redisson：自动续期的分布式锁（生产首选）
Config config = new Config();
config.useSingleServer().setAddress("redis://127.0.0.1:6379")
      .setTimeout(3000).setConnectionPoolSize(64);
RedissonClient redisson = Redisson.create(config);

RLock lock = redisson.getLock("lock:ap:" + apSN);
boolean locked = lock.tryLock(3, 30, TimeUnit.SECONDS);   // 最多等 3s，锁租期 30s
if (!locked) { log.warn("抢锁失败，跳过本次调优"); return; }
try {
    doApOptimize(apSN);
} finally {
    if (lock.isHeldByCurrentThread()) lock.unlock();      // ★ 必须判断持有者，否则抛异常
}

看门狗原理（RedissonLock 源码）：

  1. 加锁成功后，如果没有显式指定 leaseTime，Redisson 会启动一个后台定时任务
  2. 默认每隔 lockWatchdogTimeout / 3 = 10 秒（默认 lockWatchdogTimeout = 30_000 毫秒）执行一次续期
  3. 续期逻辑是 Lua 脚本：pexpire 把锁的过期时间重置为 30 秒，前提是锁还是自己的
  4. 业务执行完 unlock() → 取消定时任务 → 锁正常释放
  5. 如果进程崩溃 → 定时任务没了 → 锁在 30 秒后自动过期 → 不会死锁

注意：只有不传 leaseTime 时看门狗才生效。tryLock(3, 30, SECONDS) 里传了 leaseTime=30 → 看门狗不启用，30 秒后锁自动过期，业务没做完就有人抢走。这是个必须知道的细节。

RedLock：争议与结论

算法（Antirez 版本）：部署 5 个独立的 Redis 主节点（不是主从），客户端： 1. 记录起始时间 2. 依次向 5 个节点请求加锁（相同 key + 唯一值，带短超时） 3. 超过半数（≥3）成功，且总耗时 < 锁的有效期 → 认为加锁成功 4. 实际有效期 = 初始有效期 − 加锁消耗时间

Martin Kleppmann 的质疑（面试能说出来就是高手）：

  1. RedLock 依赖各节点的时钟。如果某个节点发生时钟跳跃（NTP 校准、GC 停顿），锁可能提前过期
  2. 它无法提供「fencing token」（栅栏令牌） —— 客户端拿到锁后如果发生长时间 GC 停顿（STW），醒来时锁已过期，此时它依然会去写共享资源，而存储层无法识别这是过期的持有者
  3. 结论：RH 的锁只适合作「效率优化」，不适合作「正确性保证」。要正确性，就该让被保护的资源自己带版本号/乐观锁（这正好回到第 2 题）

Antirez 的回应：时钟跳跃可以靠「不依赖系统时钟的单调时钟 + 不人为修改时钟」缓解；fencing token 需要客户端和存储层配合，属于另一层问题。

工程结论（面试标准答案）：

「能用幂等 + 乐观锁解决的，不要用分布式锁。必须用锁时：优先用单节点 Redis 锁（容忍极端情况下的极小概率失效），需要强一致就用 etcd / ZooKeeper（基于共识算法和会话机制，不会因为主从切换丢锁）。 RedLock 理论上有争议，且运维 5 个独立节点成本高，大多数业务不值得。」

ZooKeeper 锁的实现要点：

// Curator（Apache 官方推荐封装）：InterProcessMutex

为什么 ZK 的「临时节点」比 Redis 的「过期时间」更可靠：Redis 锁依赖「客户端在过期前完成」或「看门狗续期」；ZK 的锁是会话级的——客户端进程崩溃 → session 超时（sessionTimeout，默认协商值通常 10~20 秒）→ ZK 自动删除临时节点。但 ZK 也有代价：session 超时期间锁不释放，且如果客户端因为 GC 停顿导致 session 超时，ZK 会认为它死了，而它醒来后仍然以为自己持有锁 —— 这个「GC 停顿导致的双持有者」问题和 RedLock 的 fencing token 问题是同源的。

拓展

Redis 锁的 key 设计

String lockKey = "rrm:lock:ap:optimize:" + apSN;         // 业务前缀 + 粒度标识
// 原则：① 前缀区分业务（便于排查）② 粒度尽量细（按 apSN 而不是全局一把锁）

粒度是性能的关键：如果锁 key 是 rrm:lock:optimize（全局一把），那么所有 AP 的调优都会串行 —— 本可以并行的工作被强制串行，QPS 直接掉到 1。按 apSN 分锁，同一 AP 互斥、不同 AP 并行，这才是正确粒度。

Redisson 的 unlock() 注意事项

// ❌ 错误：直接 unlock，如果不是自己持有会抛 IllegalMonitorStateException
lock.unlock();

// ✅ 正确：先判断持有者
if (lock.isHeldByCurrentThread()) lock.unlock();

为什么 unlock() 不判断会出事：RLock 内部是可重入的（用 Redis Hash 存 线程标识 → 重入次数）。如果 tryLock 失败（返回 false），你却在 finally 里 unlock()，就会去减一个不存在的重入计数 → 抛异常，同时也可能破坏别人的锁。

Redis 锁的「可重入」怎么实现（Redisson 的 Hash 结构）

HSET myLock 线程ID(UUID:threadId) 1     -- 第一次加锁，重入计数 = 1
HINCRBY myLock 线程ID 1                 -- 重入，计数 +1
HINCRBY myLock 线程ID -1                -- 解锁，计数 -1
DEL myLock                              -- 计数为 0 才真正删除

用 Hash 而不是 String 就是为了支持重入 —— 这是 RLock 相比裸 SET NX 的额外价值。

发布订阅实现的「阻塞等待锁」

裸 SET NX 抢不到锁只能轮询（while(!tryLock) sleep(100)），浪费 CPU 且有延迟。Redisson 用Redis 的 Pub/Sub：抢锁失败时 subscribe 锁的释放频道，锁释放时收到通知立即重试。这就是「唤醒」而不是「轮询」——和 AQS 的 park/unpark 思想一致（第 7 题）。

分布式锁的三条生产铁律

  1. key 必须带过期时间 —— 否则进程崩溃 = 永久死锁
  2. value 必须是唯一标识（UUID + 线程 ID） —— 否则会误删别人的锁
  3. 必须在 finally 里释放，且释放前判断持有者 —— 否则异常路径下锁不释放

MongoDB 也能做分布式锁（和你的技术栈贴合）

// MongoDB 的 findOneAndUpdate 是原子的，可用于分布式锁
db.locks.findOneAndUpdate(
  { _id: "ap:1001", $or: [{ locked: false }, { expireAt: { $lt: new Date() } }] },
  { $set: { locked: true, holder: podId, expireAt: new Date(Date.now() + 30000) } },
  { upsert: false }
);
// 返回非 null 表示拿到锁；返回 null 表示被别人持有

注意：你们 RRM 的 MongoDB 是副本集（不是分片集群的事务场景），这个方案可用但性能不如 Redis。单文档原子更新是 MongoDB 最强的并发原语（第 2 题已经讲过）。

继续追问（面试官下一步会问什么）

Q：Redis 主从架构下，主节点写完锁还没同步就挂了，锁会不会丢？ 会。这就是 Redis 锁的根本缺陷：Redis 是 AP 系统，主从是异步复制。主节点加锁成功但未同步 → 主挂了 → 从升主 → 锁没了，另一个客户端能拿到。缓解手段：① 接受这个极小概率（多数业务可接受）；② 用 RedLock（有争议）；③ 用 ZK/etcd（CP）；④ 最彻底：让业务本身幂等。

Q：看门狗会不会一直续期导致死锁？ 不会，因为：① 续期任务只存在于持有锁的进程内，进程崩溃任务就没了；② 业务执行完 unlock() 会取消续期。但如果业务逻辑卡死（比如死循环），看门狗会一直续期 → 锁永远不释放。所以必须给业务加超时（比如 future.get(30, SECONDS)），不能只依赖看门狗。

Q：为什么不用 DEL 而要用 Lua？ 因为「GET 判断值 + DEL」是两步。如果两步之间锁过期被别人拿到，你的 DEL 就会删掉别人的锁。Lua 脚本在 Redis 里是原子执行的（Redis 单线程执行脚本期间不会处理其他命令），所以判断和删除是一个原子操作。这是「用服务端的原子性替代客户端的多次往返」的经典案例。

Q：分布式锁能替代 synchronized 吗？ 不能。粒度完全不同：synchronized 是纳秒/微秒级的进程内互斥，分布式锁要经过网络往返（毫秒级）。在单进程内用分布式锁是严重的性能浪费。「单机用 synchronized/ReentrantLock，跨进程用分布式锁」——这是分层原则。

Q：分布式锁和「多 pod 消费 Kafka 同一分区」哪个更好？ 分区归属更好。因为它把「唯一性」下沉到了 Kafka 的消费组机制上——一个分区天然只被一个消费者处理，不依赖任何锁的正确性。「用架构消除竞争」永远优于「用锁解决竞争」（这也是第 12 题「分而治之」思想的延续）。锁是兜底手段，不是第一选择。

挂到我的项目上

这个点有非常硬的真实现场：

① 多 pod 同时触发同一 AP 调优 —— rrmcontrol 的 newApUpScheduler 每 60 秒跑一次新 AP 调优，多 pod 部署时会重复触发：

「我们的 newApUpScheduler 每 60 秒触发一次新 AP 调优。多 pod 部署时，同一个 AP 可能被两个 pod 同时处理，所以我们做了幂等处理（靠 {taskId, apSN, RI} 复合索引保证不重复写入）。如果要更严格地串行化，我会用 Redis 分布式锁按 apSN 加锁——粒度和锁范围是 rrm:lock:ap:{apSN}，这样不同 AP 可以并行，只有同一个 AP 会互斥。」

② 多 pod 手 assign 消费指定 Kafka 分区 —— 这是「用架构消除竞争」的真实案例：

「我们多 pod 部署时是手工 assign 消费指定的 Kafka 分区，每个 pod 只处理自己分到的分区。这比用分布式锁更可靠——分区归属是静态的、不需要网络交互、不存在锁过期和主从切换丢锁的问题。这也是我理解分布式锁的边界的地方：能用任务分配解决的，就不要用锁。」

③ Redis 是你们技术栈的一部分：

「Redis 在我们的技术栈里主要用于缓存和会话，我理解它在分布式锁上的能力（SET NX EX + Lua + 看门狗续期），也知道它的短板是主从异步复制可能丢锁 —— 所以如果锁的正确性影响资金类业务，我会选 ZooKeeper 或 etcd 这类 CP 系统，而且业务层必须做幂等兜底。」

这三段回答的共同特点是：每一段都以「我实际怎么做的」开头，以「如果换方案我会怎么选」结尾。 这是面试官最想听到的结构。

为什么「RUNNABLE 多」不等于「CPU 高」（必考细节）

Java 的 RUNNABLE 包含了内核里的 IO 等待：

"http-nio-8080-exec-5" ... nid=0x5a01 runnable
   java.lang.Thread.State: RUNNABLE
        at java.net.SocketInputStream.socketRead0(Native Method)   ← 阻塞在 socket 读
        at java.net.SocketInputStream.read(...)

这个线程状态是 RUNNABLE，但它根本没在消耗 CPU。所以判断 CPU 高必须用 top -Hp 看实际占用，不能只看 jstack 的状态统计。这是最容易答错的一个点。

jstack 的状态统计一行命令

jstack 12345 | grep "java.lang.Thread.State" | sort | uniq -c | sort -rn
#    210 java.lang.Thread.State: WAITING (parking)          ← 大量线程在等
#     45 java.lang.Thread.State: TIMED_WAITING (sleeping)
#     12 java.lang.Thread.State: BLOCKED (on object monitor)  ← 有锁竞争
#      8 java.lang.Thread.State: RUNNABLE

判读：WAITING(parking) 最多 + 都是同一个栈 → 线程池积压（任务在等下游）；BLOCKED 多 → 锁竞争。

一个反直觉的经验

「线程池满了」的直接原因往往是下游慢，而不是线程池小。 盲目调大线程池只会把压力转移到 DB/Redis 上，让问题从「排队」变成「雪崩」。正确顺序是：先找下游瓶颈（DB 慢查询、第三方超时、锁竞争），再考虑调整线程池。

「我们做过 node-ffi 生产级调用 C 算法 .so 库。node-ffi 是同步阻塞调用，会占住 libuv 线程池（默认只有 4 个线程，UV_THREADPOOL_SIZE 环境变量可调）。所以并发量大的时候，libuv 线程池被打满，连文件读取这类异步 IO 都会排队 —— 现象是『接口莫名变慢但 CPU 不高』。这跟 Java 里线程池被阻塞任务占满是完全同构的问题，排查思路也一样：先确认是『忙』还是『等』，再看是哪个资源池被打满了。」

继续追问（面试官下一步会问什么）

Q：CPU 100% 但 jstack 里全是 WAITING，怎么回事？ 矛盾说明你的观察有误——大概率是：① 抓 jstack 的时机和 CPU 高的时机错开了（问题间歇性出现）；② CPU 是其他进程吃掉的（用 top -c 确认）；③ GC 线程在跑（GCTaskThread / VM Thread，jstack 里可能看不到）。要抓间歇性问题，就得用异步采样工具（async-profiler、JFR），或者写脚本定时抓。

Q：怎么抓一个「偶发」的问题？ ① 周期性抓栈：写个 shell 脚本每 10 秒 jstack 一次，连续抓 10 分钟，然后统计「出现频率最高的栈」；② async-profiler 长时间采样（开销 < 1%）；③ JFR 长期开启（-XX:StartFlightRecording=duration=0 持续记录）；④ 加业务埋点（关键路径耗时打点）。

Q：为什么用 printf "%x" 转十六进制？ 因为 jstack 里的 nid 是十六进制的（nid=0x3044），而 top -Hp 显示的是十进制 TID。所以必须转换才能对上。这一步忘记等于白干，是最容易漏的细节。

Q：容器里 top 看到的 CPU 是宿主机的还是容器的？ 取决于 top 的版本和 cgroup 挂载。容器里 top 常常显示宿主机的总 CPU 核数和全局负载，容易误判。更准的方式：看 /sys/fs/cgroup/cpu/cpu.stat 里的 nr_throttled 和 throttled_time（CPU 限流次数和时长），这是判断「容器被 CPU 限流」的直接证据。

cat /sys/fs/cgroup/cpu/cpu.stat
# nr_periods 1234
# nr_throttled 456          ← 被限流的周期数
# throttled_time 7890123    ← 被限流的总时长（纳秒）

「CPU throttled」是一个 K8s 里极常见的隐藏问题：Limit 设得太低 + 突发流量 → 容器被限流 → 接口 P99 延迟飙升但平均 CPU 看起来不高。这个问题只能靠 throttled_time 发现。

Q：怎么判断是「锁竞争」还是「下游慢」？ 看 jstack 里 BLOCKED 线程等的锁对象： - 等的是业务对象/synchronized → 锁竞争（去看第 9 题的死锁/热点锁排查） - 等的是 parking to wait for <...ReentrantLock$NonfairSync> 且栈顶是 parkAndCheckInterrupt → AQS 排队（第 7 题） - 栈顶是 socketRead0 / socketWrite0 且状态 RUNNABLE → 下游慢（网络/DB/第三方） - 栈顶是 DataSource.getConnection / HikariPool.getConnection → 连接池耗尽

这个「按栈顶分类」的技巧是排查效率的关键，比逐条看业务代码快得多。
