四、三类必死题预演

概念

问题：Kafka消息消费失败了怎么处理？

面试官会怎么问
  • 四、三类必死题预演？
查看答案与原理

必死题1：消息队列可靠性

标准回答骨架：

1. 失败不commit → 自动重投（At-Least-Once）
2. 重试次数用完 → 进死信队列(DLQ)人工处理
3. 业务层加幂等 → 唯一索引防止重复处理
4. 关键数据不丢失 → 落库后再commit


必死题2：分布式锁原理

问题：Redis分布式锁怎么实现？有什么坑？

标准回答骨架：

1. 实现方式：SET key value NX EX 300（原子性）
2. 过期问题：设长一点 or 看门狗续期
3. 主从切换：可能丢锁，接受 or 用Redlock
4. 业务层兜底：检查-执行竞态，锁内二次验证


必死题3：架构质疑

问题：为什么要拆成4个微服务？不是一个服务不行吗？

标准回答骨架：

1. 拆分原因：计算密集(rrmcompute) vs IO密集(rrmcontrol) vs 独立演进(aioptimize)
2. 扩展性：各服务独立扩缩容
3. 故障隔离：一个挂了不影响其他
4. 代价：运维复杂度↑、事务一致性难、网络开销

五、技术债清单（项目重来会改什么）

概念

位置：newApUpService.js 的分布式锁

面试官会怎么问
  • 五、技术债清单（项目重来会改什么）？
查看答案与原理

债1：分布式锁无看门狗续期

改法：接入Redisson，它有看门狗自动续期机制，或者把锁粒度从shop级别细化到更小的维度


债2：下游DB连接信息硬编码

位置：syncDistributedRrm.js

改法：依赖wlanpub统一配置中心，避免环境差异导致的连接失败


债3：四分支同步靠人工

位置：acceptance/develop/release/international

改法：CI流水线自动检测分支差异，触发cherry-pick或通知维护者
