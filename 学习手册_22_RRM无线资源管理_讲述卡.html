一、60秒电梯陈述


"我做过3年的无线资源管理系统RRM，这是企业级WiFi网络的核心组件，负责信道的自动分配、功率调整、负载均衡。说白了就是让企业的无线网络'自己管自己'，网管不用天天盯着。
**技术亮点**：我主导了AI RRM的重构，核心解决一个问题——原来所有计算都在云端，海量数据传输压力大。后来改成'设备侧计算+云端管控'的架构，适配现网98%的组网类型，计算压力分流到AC设备上，云端只负责下发配置和收集结果。
**架构细节**：4个Node.js微服务（rrmcontrol/rrmserver/rrmcompute/aioptimize），用Kafka做数据上报，Redis做分布式锁，MongoDB分表存储。
**战场声明**：我熟悉微服务间的异步通信、分布式锁、消息可靠性这些面试高频考点，下面的场景都是我在代码里真实解决过的。"

四、三类必死题预演


必死题1：消息队列可靠性

问题：Kafka消息消费失败了怎么处理？

标准回答骨架：

1. 失败不commit → 自动重投（At-Least-Once） 2. 重试次数用完 → 进死信队列(DLQ)人工处理 3. 业务层加幂等 → 唯一索引防止重复处理 4. 关键数据不丢失 → 落库后再commit

必死题2：分布式锁原理

问题：Redis分布式锁怎么实现？有什么坑？

标准回答骨架：

1. 实现方式：SET key value NX EX 300（原子性） 2. 过期问题：设长一点 or 看门狗续期 3. 主从切换：可能丢锁，接受 or 用Redlock 4. 业务层兜底：检查-执行竞态，锁内二次验证

必死题3：架构质疑

问题：为什么要拆成4个微服务？不是一个服务不行吗？

标准回答骨架：

1. 拆分原因：计算密集(rrmcompute) vs IO密集(rrmcontrol) vs 独立演进(aioptimize) 2. 扩展性：各服务独立扩缩容 3. 故障隔离：一个挂了不影响其他 4. 代价：运维复杂度↑、事务一致性难、网络开销

五、技术债清单（项目重来会改什么）


债1：分布式锁无看门狗续期

位置：newApUpService.js 的分布式锁

改法：接入Redisson，它有看门狗自动续期机制，或者把锁粒度从shop级别细化到更小的维度


债2：下游DB连接信息硬编码

位置：syncDistributedRrm.js

改法：依赖wlanpub统一配置中心，避免环境差异导致的连接失败


债3：四分支同步靠人工

位置：acceptance/develop/release/international

改法：CI流水线自动检测分支差异，触发cherry-pick或通知维护者



六、印象最深的Bug（四段式）


Bug：设备上报"write after end"错误（fd4ed739）


现象：

国际环境Kafka消费日志出现大量错误，部分调优结果状态不对

定位：

查日志发现是rrmcompute OOM后重启，Kafka消费位点丢失，设备重复上报导致状态冲突

修复：

1. 增加内存限制（5Gi→5.5Gi）
2. 消费端加幂等处理
3. 硬编码功率上限绕过设备bug（临时方案）

反思：

"这个bug教会我两件事：一是消息消费要有幂等设计，不能假设消息只来一次；二是OOM不能只靠加内存，要分析是谁在用，为什么爆了——后来定位是rrmcompute的算法缓存没清理。"
