Q1. Describe your most challenging project.（英文版项目介绍）
My most challenging project was rebuilding the RRM system — Radio Resource Management for wireless networks. The legacy system was a single-process module under heavy operational pressure. I redesigned it into a distributed high-concurrency service using Node.js, Kafka, Redis and MongoDB. The key challenge was routing computation between the device side and the cloud side based on network topology. We achieved a 98% network adaptation rate and rolled it out at scale.
Q2. How do you optimize database performance?（数据库优化）
I mainly focus on three things: indexing, query analysis, and data governance. First, I design composite indexes based on the query patterns — for example a compound index on taskId, AP serial number and radio index. Second, I use explain() to find full collection scans and replace them with index scans. Third, I apply TTL indexes to auto-clean old data and archive cold data. In one real case, I reduced a query's P95 latency from 1.2 seconds to 80 milliseconds by adding a proper compound index.
Q3. How do you handle high concurrency?（高并发）
I use a combination of caching, async processing and message queues. Redis caches hot data and provides distributed locks to prevent race conditions. Kafka handles traffic peaks asynchronously, so the downstream service is not overwhelmed. On the producer side I use ack=all with retry; on the consumer side I make processing idempotent with unique keys — so messages are neither lost nor duplicated.

Two reasons. First, the tech stack matches my experience very well — Node.js, MongoDB and containerized deployment are my daily tools. Second, I'm looking for an international environment. 7 💾 MongoDB 深度准备（JD 第一硬骨头）

⚠️ MongoDB 是这场面试的第一权重——JD 第二条职责整段都是它。你 RRM 4 微服务全在用，这是真正的差异化优势，但面试官会追问到设计细节，必须准备充分。

📌 必准备 5 个深度问题与标准答案

可能被问标准答案（按 STAR 结构）
① 你们的 MongoDB 怎么分库分表的？RRM 4 微服务的 MongoDB 按业务域拆分（rrmcontrol 放配置数据、rrmserver 放调度数据、rrmcompute 放计算结果、aioptimize 放 AI 模型数据），每个库内部再按 {taskId, apSN, RI} 复合索引走 shard key；冷热数据物理分库（在线业务 vs 历史归档），控制单库 100GB 内
② 慢查询怎么排查？讲一个真实案例db.collection.s.find({apSN: 'X'}).explain('executionStats') 看 executionTimeMillis + IXSCAN/COLLSCAN；典型案例：AP 状态查询接口超时（P95 1.2s）→ explain 发现 COLLSCAN → 加复合索引 {apSN:1, timestamp:-1} → P95 降到 80ms
③ 索引设计原则？你建的索引是不是越少越好？不是越少越好，是越精越好。原则：① 高频查询字段 + 高基数字段先建；② 复合索引遵循 ESR 法则（Equality / Sort / Range）；③ 避免在低基数字段建（如 boolean）；④ 索引写入会拖慢，需 balance 读写比。线上索引数量通常 5-15 个/集合，太多会拖写入
④ MongoDB 副本集 vs 分片集群怎么选？副本集（Replica Set） = 主从 + 自动故障切换，1 主 2 从起步，单机数据放得下就够用（< 2TB）；分片集群（Sharded Cluster） = 数据水平拆分到多 shard，适合数据 > 2TB 或写并发 > 10K/s。我们 RRM 单业务 < 100GB 走副本集就够，未来可平滑扩展到分片
⑤ 数据治理怎么做？（TTL、归档、冷热分离）① TTL 索引：db.collection.s.createIndex({expireAt: 1}, {expireAfterSeconds: 0}) 自动清理过期数据（如设备日志保留 30 天）；② 冷热分层：热数据 MongoDB、温数据降采样到时序库、冷数据归档到 S3/OSS；③ 定期清理脚本：cron 跑 db.collection.s.deleteMany({timestamp: {$lt: cutoffDate}})，带监控告警防误删
🎤 1 分钟 MongoDB 自我介绍（讲到 MongoDB 时直接套用）："我 RRM 项目 4 个微服务都基于 MongoDB，按业务域分库分表，复合索引 {taskId, apSN, RI} 是核心。线上一个真实案例：AP 状态查询 P95 从 1.2s 降到 80ms，靠的就是 explain 定位 COLLSCAN + 加复合索引。数据治理上用 TTL 索引自动清理 30 天前日志，定期归档到 OSS。"

11 🧭 RRM 架构介绍话术 + 追问预判（面试官不懂无线，必背）

⚠️ 这场面试官是 Node.js 后端背景，大概率不懂无线 RRM。介绍核心策略：不要从"RRM=无线资源管理"讲起，要翻译成他熟悉的分布式后端语言——一句话定位业务，再直接讲架构分工，把重点落在 Kafka/Redis/MongoDB/K8s 上。
🎤 30 秒架构介绍（开场被问"介绍一下你做的系统"直接背）：
"我做的是一个无线网络的自动调优后端系统。企业 WiFi 信号会互相干扰，RRM 负责自动给每个 AP 分信道、调功率、改带宽，让网络一直处于最优状态——相当于无线网络的自动驾驶系统。

技术上拆成 4 个 Node.js 微服务，职责非常清晰：rrmcontrol 是控制入口（收 HTTP 请求、做调度、给设备下发配置）；rrmserver 管数据采集和业务处理；rrmcompute 是核心计算引擎（算最优信道/功率）；aioptimize 做基于流量的 AI 自动调优。

服务之间用 RabbitMQ 异步通信，设备数据走 Kafka 上报，Redis 做分布式锁和缓存，MongoDB 持久化并分库分表，整体跑在 K8s 上。

我主导了这套系统从"云端集中计算"到"设备侧+云端分流计算"的重构——现在系统纳管 19.6 万+ 设备，单月调优任务 14.7 万次。"
翻译对照表：面试官听不懂 RRM → 说"无线网络自动驾驶系统"；问 4 个服务为什么拆 → 讲 IO 密集(rrmcontrol) vs CPU 密集(rrmcompute，会 OOM 需单独内存) vs AI 独立演进(aioptimize)，可独立扩缩容+故障隔离；无线部分他不懂 → 全部落到他懂的中间件实战。

🎯 高频追问 7 连 · 标准答案

可能被问标准答案（STAR / 直接背）
① 为什么拆成 4 个服务？一个不行吗？三类资源特征不同：rrmcontrol IO 密集（HTTP+设备长连接）、rrmcompute CPU 密集（跑算法会 OOM，需单独内存配额，我们单独从 5Gi→5.5Gi）、aioptimize AI 独立演进（模型迭代不影响主链路）。拆后独立扩缩容 + 故障隔离：计算服务挂了不影响控制面
② 服务间怎么通信？为什么用两套 MQ？RabbitMQ 走服务间业务调用（rrmcontrol→rrmcompute 任务分发，需确认）；Kafka 走设备侧高频数据上报（AP 状态/调优结果回传），吞吐高可重放。选型对应：RabbitMQ 适合复杂路由、Kafka 适合日志流/高吞吐
③ 设备上报失败怎么办？消息不丢？Kafka 消费手动 commit offset——处理成功才提交，失败自动重投；超限进死信队列兜底；MongoDB 加 {taskId, apSN, RI} 唯一索引做幂等，重复消费不写脏数据
④ Redis 分布式锁用在什么场景？怎么实现？定时任务防重复触发（K8s 多副本，同一 shop 任务可能被多 pod 同时扫到）。`SET key value NX EX 300` 原子获取，300s 过期防死锁；锁内二次检查开关状态（入队→执行间用户可能关开关，检查-执行竞态单靠锁不够）
⑤ MongoDB 怎么分库分表？4 微服务按业务域分库（配置/调度/计算/AI 数据分开）；冷热物理分层，在线库控制 100GB 内；历史明细 TTL 索引自动清理+定期归档；核心集合 {taskId, apSN, RI} 复合索引
⑥ 什么是"设备侧+云端双计算"？为什么这么设计？原架构所有 AP 数据传云端算，带宽运维压力大→功能只能白名单小范围开。现网 98% 是 AC+fitap 组网，AC 本身有算力 → AC+fitap 计算下沉设备侧（云端只管策略），云 AP 沿用云端计算。计算压力分流，云端成本大降，功能才敢全量放开——架构层面解决"系统不敢用、用不起"
⑦ 最自豪/最难的 bug？OOM / write-after-end / 竞态修复故事，用现象→定位→修复→反思四段式（见手册 22 Bug 故事）
✅ 必背 3 句防卡壳：①"系统纳管 19.6 万+ 设备，单月调优 14.7 万次"（冷场就补数字）②"我主导了从云端集中到设备侧+云端分流的架构重构"（证明架构能力）③"Kafka 手动 offset + 幂等索引保消息不丢不重"（证明可靠性功底）
