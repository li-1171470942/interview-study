1. 什么情况索引会失效

一句话结论：违背"最左前缀、类型一致、不破坏索引结构"原则的查询都会让索引失效。

详细解释（高频场景）： 1. 违反最左前缀：联合索引 (a,b,c)，只查 b 或 c 不查 a → 失效 2. 对索引列做计算/函数：WHERE YEAR(create_time)=2026、WHERE a+1=5 → 失效 3. 隐式类型转换：WHERE phone=13800138000（phone 是 varchar）→ 失效 4. 前导模糊查询：LIKE '%abc' 失效；LIKE 'abc%' 可以用 5. OR 连接非索引列：a=1 OR b=2（b 无索引）→ 全表扫 6. NOT IN / != / IS NOT NULL 可能失效（优化器决定） 7. 索引列参与运算、排序不一致（ASC/DESC 混用）等

面试话术：按"结构/类型/写法"三类归纳（最左前缀、类型转换、函数/模糊/OR），比零散背场景更能让面试官觉得你系统化。

例题/追问：LIKE '%abc' 为什么失效？→ B+ 树按前缀有序，前导通配无法定位起始位置只能全扫。如何优化？→ 全文索引/倒排索引。

2. 为什么 MySQL 用 B+ 树做索引

一句话结论：B+ 树矮胖、非叶子节点只存键、叶子节点链表有序，一次 IO 读更多数据、范围查询高效。

详细解释（对比 B 树 / 红黑树 / 哈希）： - 磁盘 IO 次数：树高决定 IO 次数。B+ 树非叶子节点只存键（不存数据），一页 16KB 能存上千个键 → 千万级数据树高只有 3-4 层 → 3-4 次 IO - B 树 vs B+ 树：B 树非叶子也存数据，单节点存键少 → 树更高；且 B+ 树叶间有链表，范围查询（BETWEEN、ORDER BY）直接走链表不用回父节点 - 红黑树：内存结构（二叉树高几十层），不适合磁盘（IO 次数爆炸） - 哈希索引：等值查询 O(1) 极快，但不支持范围查询/排序（哈希无序）

面试话术："磁盘 IO 视角 + 三层对比"：为什么不用红黑树（太高）、为什么不用哈希（不能范围查）、为什么比 B 树好（节点小+叶子链表）。

例题/追问：B+ 树为什么范围查询快？→ 叶子节点双向链表 + 有序。为什么不存数据到非叶子？→ 减少单页占用、增加扇出、降低树高。

3. InnoDB 和 MyISAM 的区别

一句话结论：InnoDB 支持事务/行级锁/崩溃恢复（默认引擎），MyISAM 只支持表级锁、无事务（已被淘汰）。

详细解释：

维度 InnoDB MyISAM
事务 ✅ ACID ❌
锁粒度 行级锁（并发高） 表级锁（写阻塞）
外键 ✅ ❌
崩溃恢复 ✅ redo log 恢复 ❌ 易损坏
索引结构 聚簇索引（数据和索引一体） 非聚簇（数据文件独立）
count(*) 慢（要扫） 快（有元数据）
存储 .ibd .frm/.MYD/.MYI

面试话术：结论"InnoDB 完胜，只有读多写少+不要事务的极简场景才可能用 MyISAM"；补充"MySQL 5.5 后默认 InnoDB，现在几乎不用 MyISAM"。

例题/追问：MyISAM 的 count(*) 为什么快？→ 单独存了行数元数据；InnoDB 有 MVCC 各事务可见行数不同，不能缓存。

4. 聚集索引 和 非聚集索引

一句话结论：聚集索引（主键索引）叶子节点直接存整行数据；非聚集索引（二级索引）叶子存主键值，查数据要回表。

详细解释： - 聚簇索引：InnoDB 主键即聚簇索引，数据行就存在索引的叶子节点上 → 按主键查一次 IO 就拿到整行 - 二级索引：叶子节点存"索引列 + 主键值" → 查非主键列 = 先查二级索引拿到主键 → 再回聚簇索引查整行（回表） - 为什么主键建议自增：聚簇索引按主键有序排列，自增主键插入永远追加在尾部（避免页分裂）；随机主键（UUID）会导致大量页分裂、随机 IO

面试话术：一句话"主键索引=书的正文章节，二级索引=书末尾的索引目录（查到页码再翻正文）"，比喻说完立刻讲回表。

例题/追问：什么情况下查二级索引不用回表？→ 覆盖索引（查询的列都包含在索引里，如 SELECT a,b FROM t WHERE a=1 且 (a,b) 是联合索引）。

5. 事务四大特性（ACID）及实现原理

一句话结论：原子性靠 undo log、一致性靠约束+其他三特性、隔离性靠锁+MVCC、持久性靠 redo log。

详细解释： - 原子性 Atomicity：要么全成功要么全回滚 → undo log（记录修改前的值，回滚时逆操作） - 一致性 Consistency：事务前后数据完整性不被破坏 → 应用层约束 + 其他三特性配合保证 - 隔离性 Isolation：并发事务互不干扰 → MVCC + 锁 - 持久性 Durability：提交后不丢失 → redo log（记录修改后值，崩溃重放）

面试话术："每个特性对应哪个机制"直接背：原子性-undo、持久性-redo、隔离性-锁/MVCC、一致性-兜底。面试官常考这个映射关系。

例题/追问：为什么需要 undo 和 redo 两份日志？→ undo 回滚、redo 前滚，崩溃恢复 = 用 redo 重放已提交 + 用 undo 回滚未提交。

6. 事务隔离级别

一句话结论：读未提交 → 读已提交 → 可重复读 → 串行化；级别越高隔离越好性能越差，MySQL 默认可重复读。

详细解释（并发三大问题）：

问题 表现 被哪个级别解决
脏读 读到别的事务未提交的数据 读已提交解决
不可重复读 同一事务两次读同一条记录值不同（被改） 可重复读解决
幻读 同一事务两次查询结果行数不同（被插入） 串行化解决（MySQL 用 MVCC+间隙锁在 RR 也基本解决）
  • 读未提交：最松，读别人没提交的
  • 读已提交：只能读已提交（Oracle 默认）
  • 可重复读：快照读保证事务内读一致（MySQL 默认）
  • 串行化：全串行，读写都加锁

面试话术：背"三个问题 × 解决级别"表 + "MySQL 默认 RR 且用 MVCC+间隙锁把幻读也基本干掉（相比标准 RR 更强）"。

例题/追问：可重复读怎么实现？→ MVCC 快照。MySQL 的 RR 下还会幻读吗？→ 快照读不会；当前读（SELECT ... FOR UPDATE）靠间隙锁/临键锁防插入。

7. MVCC 原理（多版本并发控制）

一句话结论：MVCC 让读不加锁，通过 undo log 链 + 隐藏字段（trx_id、roll_pointer）+ ReadView 实现多版本快照读。

详细解释： - 隐藏字段：每行有 trx_id（最后修改它的事务 id）和 roll_pointer（指向 undo log 中的旧版本） - undo log 版本链：每次修改生成一个新版本，通过 roll_pointer 串成链，旧版本存 undo log - ReadView（读视图）：事务开始（或首次读）时生成，记录活跃事务列表： - 比 ReadView 里最小 trx_id 还小 → 已提交，可见 - 在活跃列表里 → 不可见，沿版本链找上一个版本 - 大于最大 trx_id → 未来事务，不可见 - 效果：每个事务看到自己"开始时刻"的一致快照 → 可重复读

面试话术：讲清"版本链 + ReadView 判断可见性"两步，这是 MySQL 最值钱的一道题，能完整讲出来就是区分度。

例题/追问：快照读 vs 当前读？→ 快照读（普通 SELECT）读快照不加锁；当前读（FOR UPDATE/LOCK IN SHARE MODE/UPDATE/DELETE）读最新并加锁。

8. MySQL 三大日志：binlog / redo log / undo log

一句话结论：redo log 保证崩溃恢复（InnoDB 层），undo log 支持回滚与 MVCC（InnoDB 层），binlog 用于主从复制与数据恢复（Server 层）。

详细解释：

日志 层级 内容 作用
redo log InnoDB 物理修改（页的变化） 崩溃恢复，保证持久性；WAL 先写日志后写数据
undo log InnoDB 逻辑回滚（旧版本） 事务回滚 + MVCC 版本链
binlog Server 逻辑 SQL/行变更 主从复制、数据恢复、canal 订阅
  • redo vs binlog：redo 是物理页、InnoDB 层、循环写；binlog 是逻辑语句、Server 层、追加写。两者配合才有两阶段提交（保证崩溃时两份日志一致）
  • WAL（Write-Ahead Logging）：先写 redo log 再刷数据页 → 崩溃后按 redo 重放

面试话术："三层/两用途"记忆法：redo 前滚、undo 回滚、binlog 复制。再补两阶段提交一句话（"binlog 和 redo 用两阶段提交保证一致，这是崩溃恢复安全的关键"）。

例题/追问：主从复制用哪个日志？binlog。canal 中间件原理？→ 模拟 slave 拉取 binlog 解析成事件。

9. 主从复制原理

一句话结论：主库写 binlog → 从库 IO 线程拉取写中继日志 → SQL 线程重放，异步复制有延迟。

详细解释： 1. 主库更新数据 → 写 binlog 2. 从库 IO 线程 连主库，拉取 binlog 写入本地 relay log（中继日志） 3. 从库 SQL 线程 重放 relay log，应用到从库数据 - 复制模式：异步（默认，有延迟可能丢数据）/ 半同步（主库等至少一个从库确认）/ 同步（全确认，性能差） - 一致性保障：GTID（全局事务 id）避免重复执行；主从延迟用并行复制缓解 - 用途：读写分离、灾备、报表库

面试话术："两个线程一条日志"（IO 线程 + SQL 线程 + relay log）讲流程，再讲三种同步模式和延迟问题。

例题/追问：主从延迟怎么解决？→ 半同步、并行复制、读写分离的业务降级（读主库）、缓存。

10. 分库分表

一句话结论：数据量大时，分库扛并发、分表扛数据量；核心是分片键选择与路由，难点是跨库事务与查询。

详细解释： - 垂直拆分：按业务分库（订单库/用户库）；按字段分表（大字段拆出去） - 水平分表：按分片键取模/范围/哈希（如 user_id % 16 → 16 张表） - 分片键选择：选查询最频繁且均匀的字段；按分片键查快，非分片键查要广播（all 路由） - 全局主键：雪花算法（时间戳+机器+序列）、号段模式 - 中间件：ShardingSphere / MyCat - 难点：跨库 join（冗余/应用层组装）、分布式事务（TCC/Saga）、扩容（一致性哈希迁移）

面试话术：先说拆分动机（数据量 → 分表；连接数/吞吐 → 分库），再说分片键路由，最后老实说跨库 join 的三种解法（冗余/汇总表/应用层）。

例题/追问：分片后怎么分页排序？→ 各分片查 TopN 再归并。你项目里 MongoDB 分库分表怎么做的？→ 按 taskId/AP 维度分片，索引 {taskId, apSN, RI}（结合 RRM 实战）。

11. count(*)、count(1)、count(col) 的区别

一句话结论：count(*) 统计所有行数最快，count(1) 等价，count(col) 只统计该列非 NULL 的行。

详细解释： - count(*)：优化器直接遍历索引统计，不取值 → 最快（InnoDB 下和 count(1) 基本一样） - count(1)：每行固定值 1 计数，等价 count() - count(col)：跳过 col 为 NULL 的行 - 所以 count(*) vs count(col) 的差异在于是否统计 NULL*

面试话术：纠正常见误解"count(1) 比 count() 快"——实际上 count() 经过优化最快；差别在 count(col) 不计 NULL。

例题/追问：count(*) 在 InnoDB 为什么比 MyISAM 慢？→ 见上面 MyISAM 元数据。

12. SQL 优化思路

一句话结论：先看执行计划 EXPLAIN，再按"索引 → 写法 → 表结构 → 缓存"顺序优化。

详细解释（EXPLAIN 关键列）： - type：system > const > eq_ref > ref > range > index > ALL（最好到 ref/range，避免 ALL 全扫） - key / possible_keys：实际用没用索引 - rows：预估扫描行数（越小越好） - Extra：Using filesort（文件排序，要优化）、Using temporary（临时表）、Using index（覆盖索引，好） - 优化手段：加联合索引覆盖高频查询、避免 select *、分页深翻页优化（WHERE id > 上次最大id LIMIT 20 代替 LIMIT 200000,20）、大字段拆表、读写分离

面试话术："EXPLAIN 是入口"——面试官最想听到你会看执行计划，讲 type 和 rows 两个字段就够显专业。

例题/追问：深分页为什么慢？→ offset 200000 要先扫 20 万行再丢弃。怎么优化？→ 游标分页（where id > last_id）。

13. 索引的分类

一句话结论：按结构分 B+树/哈希/全文，按用途分主键/唯一/普通/联合，按存储分聚簇/非聚簇。

详细解释：

分类维度 类型 说明
结构 B+ 树 / 哈希 / 全文 哈希只支持等值，全文用于 like 文本检索
用途 主键索引 聚簇，唯一非空
唯一索引 唯一允许 NULL
普通索引 仅加速
联合索引（复合） 多列，最左前缀
前缀索引 字符串前 N 位建索引
存储 聚簇 / 非聚簇 数据是否和索引一起

面试话术：按"用途"分类背最常用（主键/唯一/普通/联合），再补"联合索引最左前缀"和"什么时候不建索引"（数据量小、区分度低、频繁更新、查询列）。

例题/追问：为什么不建议在性别字段建索引？→ 区分度低（就两个值），索引选择性差，优化器可能仍全扫。

14. 快照读 和 当前读

一句话结论：快照读读的是历史版本（不加锁，靠 MVCC），当前读读最新并加锁（靠锁机制）。

详细解释： - 快照读：普通 SELECT——读 ReadView 里可见的版本，不加锁、不阻塞 - 当前读：SELECT ... FOR UPDATE、LOCK IN SHARE MODE、UPDATE、DELETE、INSERT——读最新已提交版本并加锁（行锁/间隙锁/临键锁） - 幻读为什么当前读也防住：当前读走临键锁（记录锁+间隙锁），锁住范围禁止插入 → 防幻读

面试话术：这个和 MVCC、隔离级别三题联动——"MVCC 管快照读，锁管当前读"。

例题/追问：可重复读级别下 FOR UPDATE 两次查，另一个事务插入新行会怎样？→ 被间隙锁阻塞直到事务结束（防幻读）。

15. drop / delete / truncate 的区别

一句话结论：delete 逐行删可回滚（走事务，保留表结构）、truncate 清空表不可回滚（保留结构）、drop 连表结构一起删。

详细解释：

操作 删除内容 可回滚 速度 触发触发器
DELETE 行数据 ✅（DML 走事务 undo） 慢（逐行） ✅
TRUNCATE 全表数据（保留表结构） ❌（DDL） 快 ❌
DROP 表结构+数据+索引全删 ❌ 最快 ❌

面试话术：三行表直接背，关键词：DML vs DDL、可回滚 vs 不可回滚。

例题/追问：清空大表用 truncate 还是 delete？→ truncate（快、不产生大量 binlog），但注意不可回滚。
