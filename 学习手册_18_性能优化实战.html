📘 学习手册 18 · 性能优化实战（把经验变成面试弹药）

来源：同事 Java 面试侧重点——"性能优化必须有实践经验" ⚠️ 你有真实案例（RRM 生产环境）但没组织成"可讲的案例"。本册把你的经验 + Java 面试高频性能题结合 案例讲法模板（背熟）：背景 → 现象 → 定位方法 → 方案 → 量化效果 → 可迁移 每个案例 2 分钟内讲完，面试官要的是"你真的排查过"的细节

0. 性能优化通用方法论（Java 面试高频题）

一句话结论：性能问题四大类（慢查询/高延迟、内存/GC、吞吐/并发、资源泄漏），排查顺序：先指标定位（CPU/内存/IO/GC）→ 再代码定位 → 最后针对性优化。 详细解释（面试常问"项目怎么优化的"，分层答）：

层 手段 你已有的实战
数据库层 索引/慢 SQL/分库分表/连接池 MongoDB 索引与分表、MySQL 八股
缓存层 Redis 缓存、分布式锁、防击穿 RRM 配置缓存、Redis 锁
消息层 批量/异步/削峰/消费优化 Kafka 上报链路
内存/GC 堆调优、对象复用、泄漏排查 rrmcompute OOM 调优
代码层 批量代替循环、连接复用、池化、异步化 node-ffi Buffer 复用
系统层 线程池参数、连接池、日志降级 日志级别优化

话术/例题："我优化过的点分四类：DB（索引/分表）、内存（OOM 调堆）、消息（积压）、日志（降级）"——先给分类框架再展开一个案例。

案例① rrmcompute OOM 内存调优（你的招牌案例）

一句话结论：高量调优任务并发导致内存超限 OOM 重启，通过"分析内存构成 → 调 requests/limits + 限流任务"解决。 完整讲法： - 背景：RRM 云端计算微服务 rrmcompute，高量任务（大 AP 场所调优）时频繁 OOM 重启 - 现象：Pod OOMKilled，K8s 重启，任务中断用户投诉 - 定位：看 K8s events（OOMKilled）→ 内存监控曲线（峰值超 limits）→ 分析是单个大任务（大批 AP 数据一次载入）还是并发累积 - 方案：① 内存配额 5Gi→5.5Gi（requests 保持 3Gi，limits 上调留余量）② 大任务分批处理/限制单任务内存 ③ 消息消费限流（防突发堆积全进内存） - 效果：OOM 重启消失，服务稳定 - 可迁移（Java）：Java 对应 -Xmx 调优 + 大对象/集合无界增长排查 + 线程池队列限制 追问应对："为什么 requests 和 limits 都要配？"→ requests 决定调度（Node 内存够才调度），limits 是上限（超了 OOM kill）；只配 limits 会高估导致 Node 超卖。

案例② Kafka 消费积压排查

一句话结论：消费速度跟不上生产速度 → 积压，先看积压量定位是"生产暴涨"还是"消费卡住"，再对症处理。 完整讲法： - 背景：设备调优结果上报量大，消费处理慢，页面数据延迟 - 定位：查消费者组 lag（Kafka lag 监控）→ 确认积压持续增长 → 看消费端日志：是 DB 写入慢还是处理逻辑慢 - 方案：① 批量消费（攒一批一次入库，减少 DB 往返）② 加分区/消费者并行度 ③ 消费端慢 SQL 优化（加索引） - 效果：lag 回落，数据实时 - 可迁移（Java）：Spring Kafka 消费者并发（concurrency）、批量 Listener、手动提交 offset 追问应对："消息会不会丢？"→ 生产 acks=all + 消费先处理再提交 offset + 幂等去重（你手册 04 全套）。

案例③ MongoDB 慢查询与索引优化

一句话结论：上报数据量大查询慢 → explain 看是否走索引 → 建复合索引 + 分片，查询从秒级到毫秒。 完整讲法： - 背景：按 taskId+AP 查调优历史慢（数据千万级） - 定位：explain() 看 COLLSCAN（全集合扫）→ 无合适索引 - 方案：建复合索引 {taskId, apSN, RI} 命中查询 + 按任务维度分库分表分散热点 + 限制返回字段（projection） - 效果：查询毫秒级 - 可迁移（Java/MySQL）：EXPLAIN 看 type（ref/range vs ALL）、联合索引最左前缀、覆盖索引 追问应对："复合索引顺序怎么定？"→ 等值字段在前（taskId）、范围字段在后（时间/RI），最左前缀匹配。

案例④ Redis 缓存与配置中心优化

一句话结论：高频读取走缓存 + 缓存一致性（先写库再删缓存）+ 防击穿，把 DB 压力降到 1/10。 完整讲法： - 背景：配置/基础数据每次请求都查 Mongo，高峰 DB 压力大 - 方案：① 热点配置缓存到 Redis（TTL 兜底）② 变更时先写库再删缓存（Cache Aside）③ 分布式锁防并发重建 - 效果：DB QPS 大幅下降，接口延迟降低 - 可迁移（Java）：Spring Cache/Redisson、缓存穿透/击穿/雪崩方案（手册 03 全链路） 追问应对："缓存和 DB 不一致怎么办？"→ 删缓存 + 延迟双删/Canal 兜底 + TTL（手册 03 第 5/9 题）。

案例⑤ 日志降级优化（非关键日志）

一句话结论：把无业务价值的 error 级日志降为 info/warn，减少磁盘与 IO 开销、降低告警噪音。 完整讲法： - 背景：rrmcontrol 大量流程性日志用 ERROR 打印（如 'empty autoOptDoc' 每 60s 一次），日志量大、告警噪音 - 方案：分析日志分类（错误 vs 流程事件）→ 流程事件降级 console.info/warn，仅保留真错误为 ERROR - 效果：日志量下降、告警准确率提升、IO 开销降低 - 可迁移（Java）：log4j2/logback 级别配置、按类调整级别、日志异步化 追问应对："为什么流程事件也用 ERROR 是问题？"→ 掩盖真错误（告警疲劳）+ 额外 IO；日志策略：ERROR=需要人处理，INFO/WARN=可观测即可。

案例⑥ 性能优化高阶题（Java 面试通用）

一句话结论：线程池参数、连接池、批量 IO、异步化、GC 调优——五类高频考点，每类备一句实践理解。 详细解释： 1. 线程池：核心/最大/队列怎么定？→ CPU 密集 = 核数+1，IO 密集可大；队列有界防 OOM（手册 06 第 13 题联动） 2. 连接池：DB/Redis/HTTP 连接都池化（避免频繁建连）；池大小 = 峰值并发 × 单连接耗时/预期响应 3. 批量 IO：批量入库/批量查询替代 N+1（一次循环查一次库是反模式） 4. 异步化：非核心逻辑异步（MQ/线程池），削峰填谷 5. GC 调优：目标是少 Full GC；大对象/缓存无界增长是元凶（手册 07） 话术/例题：挑 2-3 类结合真实场景讲（批量入库 + 异步上报你都在 RRM 做过）。追问：如何定位 Java 线上性能问题？→ top/arthas（dashboard/thread/ognl）+ jstat 看 GC + jmap 堆转储（手册 07 第 8 题命令）。
